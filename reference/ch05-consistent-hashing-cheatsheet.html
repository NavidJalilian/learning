5.1 Ring math Quest 5.1 →

The rehashing problem
serverIndex = hash(key) % N spreads keys evenly, but a key keeps its server only if hash % N equals hash % (N±1). Change N and almost every key remaps. In a cache that's a miss storm on the database.
The ring
Take the hash space (SHA-1: 0 to 2160−1) and join its ends. Hash servers (IP or name) and keys with the same function onto it. A key belongs to the first server clockwise. No % N anywhere.
What an arc is worth
A server owns the arc from the previous server (anticlockwise) up to itself.
share = ((pos − prev) mod S) / S
S = size of the space. The mod handles the wrap past 0. Toy: s0 at 32, prev at 240, S = 256 → 48/256 = 18.75%.

Modulo gets worse as the cluster grows; the ring gets better. The book's rule: on average only k/n keys move (k keys, n servers).

Lookup in code
Keep server positions (tokens) in a sorted array. Binary-search for the first token ≥ hash; none → wrap to the first token. O(log T): 256,000 tokens ≈ 18 steps. 
let lo = 0, hi = tokens.length; // not length-1
while (lo < hi) {
  const mid = (lo + hi) >> 1;
  if (tokens[mid] < h) lo = mid + 1;
  else hi = mid;
}
return tokens[lo % tokens.length]; // wrap
Classic bug: hi = length − 1 can never say "past the end", so it never wraps.
Which keys move
  • Join: from the new server go anticlockwise to the previous server. Those keys move to the new server, all from its clockwise neighbour.
  • Leave: from the leaving server go anticlockwise to the previous server. Those keys go to its clockwise neighbour.
  • Virtual nodes: same rule once per position → many small arcs from (or to) many servers.
  • Nothing else on the ring changes.
Traps that move everything
  • Changing the hash function (SHA-1 → Murmur3): every key and server gets a new spot. Plan a migration.
  • Hashing an unstable IP: a reboot with a new IP = a remove + an add. Hash a stable server ID.
  • Real hash spaces: Dynamo hashes keys with MD5 (128-bit); Cassandra's Murmur3 tokens run −263 … 263−1.

"With hash mod N, going from 20 to 21 servers moves about 20 in 21 keys, roughly 95%, so the whole cache misses at once. On a ring, a lookup is a binary search for the first position at or after the key's hash, wrapping at the top. A new server takes only the arc between itself and the previous server, from its clockwise neighbour: about 1/(N+1) of the keys."

Caveats: N/(N+1) and 1/(N+1) assume uniform hashes and, for the ring, equal arcs; with one random position per server a join can take far more or less. "Move" in a cache is one miss; in a database the arc must be copied before the new owner serves it (the book stops at "which keys"). SHA-1 is broken for security, which doesn't matter for placement.

5.2 Cracks in the ring, and who rides it Quest 5.2 →

Crack 1: uneven partitions
  • You don't choose where a server lands; its hash does, and servers come and go.
  • 4 even servers, remove one → its clockwise neighbour owns 50%.
  • N random servers: largest arc ≈ HN/N (HN = 1 + ½ + … + 1/N ≈ ln N + 0.58): 52% at N = 4, 29% at 10, 5.2% at 100, i.e. ~ln N × fair share. More servers make it relatively worse.
Crack 2: uneven keys
  • Even with equal arcs, random keys bunch: 8 keys on 4 arcs leave some server empty ~38% of the time.
  • Heals with scale: noise ≈ 1/√(keys per server), ~3% at 1,000 each.
  • One hot key is different: it hashes to one spot, one server. Virtual nodes or more servers can't split it → cache, replicate or split that key.
The patch: virtual nodes
  • Place each server at many positions (s0#0, s0#1…; Dynamo/Cassandra call them tokens).
  • Share = sum of many small arcs → spread ≈ 1/√V. Halving it costs 4× the vnodes.
  • A dead server's arcs scatter over many survivors.
  • Heterogeneity: vnodes ∝ capacity (2× server → 2× vnodes).

Maglev vs ring
Backends take turns claiming their next preferred free slot (offset + skip) in a table of M slots (65,537 in the paper). Even balance (M/N ± 1 slots each), paid for with a little extra disruption: when a backend leaves, a few survivors' slots move too. A ring is the reverse deal.
Other alternatives
  • Rendezvous hashing: each key picks the server with the highest hash(key, server).
  • Jump consistent hash: no table, tiny memory, but only for numbered shards added or removed at the end.

"The basic ring has two problems: arcs are uneven because positions come from the hash, so the biggest can be around ln N times fair share and a removal dumps a whole arc on one neighbour; and keys can bunch, though that fades with scale. Virtual nodes fix the arcs: spread is about one over root V, so a few hundred per server gets you to 5–10%, at the cost of ring metadata on every router, and bigger servers get more. One hot key still lives on one server, so cache or replicate it. Dynamo, Cassandra, Discord and Akamai use rings; Maglev uses a lookup table for even balance."

Caveats: HN/N and 1/√V are idealised maths for random placement; Dynamo later moved to equal-sized fixed partitions ("Strategy 3", §6.2) and Cassandra 4.0 allocates tokens deliberately, which is why 16 is enough. The book's 5% at 200 vnodes is optimistic (a simple simulation gives ~6–7%): teach the trend. Discord and Akamai internals may have changed since their public write-ups.

Curveballs, one line each

  • "Swap SHA-1 for Murmur3, just config?" No: nearly every key remaps. Migrate (run old and new rings side by side while the new one warms).
  • "A server rebooted with a new IP." It's a remove + an add, two moved arcs. Hash a stable server ID.
  • "Two clients disagree on the server list." A few extra misses for the moved arc; both converge via membership.
  • "One server holds 30%." One position per server: add virtual nodes. Removing it would dump its arc on one neighbour.
  • "Why not a key → server table?" 500M rows to store and sync; the ring needs only the server list.
  • "We rarely resize, why not % N?" Every crash is a resize, and N/(N+1) of keys move each time.
  • "C died, then its neighbour D." Cascade: C's whole arc doubled D's load. Virtual nodes scatter it.
  • "Now it's a database." Stream the new node's arcs from the current owners first, then cut over.

Step 4, wrap up: recap the benefits (few keys move, even load, easy scale-out), name who runs it (Dynamo, Cassandra, Discord, Akamai, Maglev), and admit the limits (hot key, vnode metadata) with alternatives (rendezvous, jump hash, Maglev). Don't just say "done".

"With hash mod N, changing the fleet from N to N+1 servers remaps about N/(N+1) of keys, a miss storm on the database, so I'd use consistent hashing. Servers and keys share one hash space bent into a ring; a key belongs to the first server clockwise, which the client library finds by binary search over sorted positions. A join or leave moves only one arc, about k/n keys, and walking anticlockwise to the previous position tells me exactly which. Each server gets a few hundred virtual nodes, more for bigger machines, which also spreads a failed server's load. Clients get the server list from a membership service. A single hot key still needs caching or replication, and this is the partitioning Dynamo and Cassandra use."

Honest caveats (where real systems differ from the book)

  • The neat fractions are averages. 1/(N+1) on a join assumes equal arcs; with one random position per server, a join can take far more or less.
  • 5% at 200 virtual nodes is optimistic. Random placement gives ~1/√V (≈ 7% at 200). 4× the vnodes halves the spread.
  • Real systems place tokens on purpose. Dynamo's "Strategy 3" uses equal-sized fixed partitions; Cassandra 4.0's allocator makes 16 tokens enough.
  • Hot keys. The book says consistent hashing mitigates hotspots; true for many keys that cluster, not for one very hot key.
  • "Move" ≠ "copy". For a cache a moved key is a miss; a database must stream the arc before the new owner serves it. The book stops at which keys move.
  • Beyond the chapter. Membership (ZooKeeper, etcd, gossip), the cache-fleet framing and "hash a stable ID" are the course's additions; the book hashes servers by IP or name.
  • Toy rings. The quests use 0–99, 0–255 or 0–359 so every key is visible; real rings have 264 to 2160 positions. Maglev's toy uses 7 slots; the paper uses 65,537.
