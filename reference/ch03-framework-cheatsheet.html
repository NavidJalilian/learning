3.1 Rules of the Room Quest 3.1 →

The session imitates two coworkers working a vague problem to a workable answer. Nobody expects a finished product in under an hour, and there is no single right answer. The diagram is a by-product; the interviewer records signal (the evidence behind hire / no hire).

What gets graded: 5 signals
  • Design skill: why a cache cuts read latency; two options with trade-offs
  • Collaboration: asks what worries them about your choice; checks in
  • Under pressure: re-plans calmly when a requirement lands late
  • Ambiguity: turns a fuzzy prompt into a stated scope
  • Good questions: asks about scale before drawing
The 3 red flags the book names
  • Over-engineering: design purity over trade-offs. e.g. three-region active-active and home-made consensus for a 1,000-user internal tool
  • Narrow-mindedness: one idea, no alternatives. e.g. "NoSQL is always better, let's move on"
  • Stubbornness: won't adjust to a valid concern. e.g. repeats the same plan after a real objection
Healthy look-alikes (not flags)
  • A simple design for a small scale ("one DB now, shard later")
  • Defending a choice with a reason, then updating when new facts arrive
  • Asking for a hint after a real try

Dos & don'ts (paraphrased)

✓ Do

  • Clarify; never treat your own assumption as fact
  • Remember there's no single best answer (startup ≠ millions of users)
  • Think out loud
  • Offer more than one approach
  • Big picture first, then detail the most critical parts
  • Treat the interviewer as a teammate; ask for feedback early and often
  • Never give up

✗ Don't

  • Show up unprepared for the common prompts
  • Jump into a solution before requirements and assumptions are clear
  • Go deep on one component at the start
  • Be shy about asking for a hint when stuck
  • Think in silence
  • Assume you're done when the boxes are drawn: you're done when the interviewer says so

"I treat it as a design session with a colleague. For the first 3 to 10 minutes I pin down scope and assumptions, then about 10 to 15 on a high-level sketch the interviewer agrees with, most of the rest on a deep dive into what they care about, and the last few minutes on bottlenecks and next steps. I think out loud, offer options with trade-offs, and avoid over-engineering."

3.2 Ask Before You Build (step 1) Quest 3.2 →

A fast answer earns no bonus points, and designing before you know the requirements is a big red flag. Hidden requirements found late (video, 5,000 friends) force rework that eats your deep dive: fast start, slow finish.

4 question families
  • Features: what exactly are we building?
  • Users: how many? (DAU = different people per day)
  • Growth: what scale in 3, 6, 12 months?
  • Stack: what does the company already run that we can reuse?
A good question changes a box. Brand colours, Java vs Go and team size don't.
Answer or assume, then write it down
  • The interviewer answers → Requirements column
  • "You decide" → state a simple, realistic assumption with a reason → Assumptions column
  • A silent assumption is a hidden risk that surfaces at minute 25
  • Stalling ("I can't go on until you decide") wastes the clock

3.3 Blueprint & Buy-in (step 2) Quest 3.3 →

Goal: a rough blueprint plus buy-in (the interviewer agrees it's a sound base). Sketch the main boxes in a few minutes, then ask "does this shape work before I go deeper?" Do rough maths only if they want it, and walk a concrete use case ("Alice posts, Bob opens his feed") to surface edge cases.

The box toolkit
  • Client: where requests start (app / browser)
  • Load balancer: spreads traffic over web servers
  • Web servers: handle requests; stateless so you can add more
  • Database: durable storage
  • Cache: hot data in memory
  • CDN: static media from servers near users
  • Message queue: hand slow work to workers later
Zoom level: APIs and schema now?
  • Google search, YouTube → boxes only
  • News feed → boxes + key APIs (POST /v1/me/feed, GET /v1/me/feed)
  • Poker backend, URL shortener → boxes + APIs + schema
  • Unsure → ask the interviewer
When they push back
  • Adjust if the point is valid (slow video → add CDN; slow posting → fan-out behind a queue)
  • Defend with one reason if it isn't (cache: reads ≫ writes)
  • Park deep questions for step 3 (celebrity fan-out)
  • Ask when vague ("faster at what?")

The two flows (book's high-level figures)

  • Publish: user → load balancer → web servers → post service (post cache + post DB), fanout service (writes the post ID into each friend's news feed cache) and notification service (tells friends). All three hang off the web servers.
  • Read: user → load balancer → web servers → news feed service → news feed cache (a ready-made list of post IDs per user, newest first).
  • Reusable trick: almost every system has a write path and a read path. Draw them as two flows.

"Two flows. Publishing goes through a load balancer to stateless web servers, which call the post service to save the post behind a cache, the fanout service to push the post ID into each friend's feed cache, and a notification service to ping them. Reading hits the news feed service, which returns the ready-made list of IDs from that cache. Media lives in object storage behind a CDN. Does this shape match what you want to focus on?"

3.4 Dive Deep, Land Clean (steps 3 & 4) Quest 3.4 →

Pick targets with the interviewer
  • URL shortener → the hash function for short codes
  • Chat → latency and online/offline presence
  • News feed → fan-out first, then feed retrieval
  • Some (often senior) loops want performance and bottleneck talk instead of component detail
Signal per minute
  • Book's rabbit hole: explaining Facebook's EdgeRank ranking formula. Interesting, proves nothing about scale
  • Also low-signal: JSON libraries, pagination style, pixel layout
  • Most critical components first
  • If they point somewhere, follow them

Fan-out preview (built properly in Ch. 11)

Push (fan-out on write)Pull (fan-out on read)
When Alice postsWrite her post ID into every friend's feed: up to 5,000 writesOne write, to her own post list
When Bob readsOne cache lookup, feed is pre-builtFetch and merge every friend's recent posts
Breaks onCelebrities: 10M followers = 10M writes, queue backs upUsers with many friends: slow reads every time
Common answerHybrid: push for most users, pull for celebrity accounts

Wrap-up checklist (step 4, last 3–5 min)

  • Bottleneck + improvement: never call the design perfect
  • Recap, most useful if you weighed several options
  • Error cases: a server fails, the network drops
  • Operations: metrics, error logs, safe rollout
  • Next scale step: what changes from 1M to 10M users
  • Refinements you'd make with more time
  • Not over until the interviewer says so

"The biggest bottleneck is fan-out for huge accounts, so I'd pull those at read time and push for everyone else. If a feed cache node dies, rebuild from the post store and fall back to pull meanwhile. I'd watch feed latency, fan-out queue depth and error rates, and roll out gradually. At ten times the users I'd shard the post DB and add cache tiers."

BOSS · Run the Room: the full mock interview Boss quest →

1 · Scope (3–10 min)
  • Find all six facts unprompted
  • "You decide" on order → newest first, said and written down
  • Skip brand colours, "just use Kafka", "how would you do it?"
2 · High-level (10–15 min)
  • Draw both flows; fanout hangs off the web servers
  • Ask for buy-in, then hear the hint: "curious about fan-out"
  • Videos → object storage + CDN
  • No blockchain, custom consensus or ML ranking
3 · Deep dive (10–25 min)
  • Plan: fan-out first, then retrieval; no EdgeRank
  • Stuck on 10M followers → think aloud, propose pull for celebrities
  • "Why not pull for everyone?" → compare, then hybrid
4 · Wrap (3–5 min)
  • Bottleneck, failures, operations, next scale curve, recap
  • "Any questions?" → ask about their real challenges

Final design

Grading the other seat (Riley)

Good technical pieces (two clean flows, reasoned push choice, CDN for video) but six process flags: no scoping, no buy-in, an 8-minute EdgeRank detour, brushing off the interviewer's idea, a silent stall, and "no real weaknesses". Verdict: lean no hire. Interviewers grade how you work, not just what you draw.

Your scorecard's five signals

Design skill · Collaboration · Under pressure · Ambiguity · Good questions. Each red flag you trigger (jumped ahead, unspoken assumption, over-engineering, no buy-in, rabbit hole, silence, narrow-mindedness, stubbornness, caving without reasons, claiming perfection, ending early, late redesign) caps the verdict.

"I scoped first: mobile and web, posting and viewing friends' posts, newest first by assumption, up to 5,000 friends, 10 million daily users, images and video. I sketched two flows, publishing via the post and fanout services into a feed cache and reading from the news feed service out of that cache, with media on a CDN, and checked the shape. The deep dive was fan-out, push for most users and pull for celebrities, then retrieval. I closed with the celebrity bottleneck, cache-failure recovery, the metrics I'd watch, and what changes at ten times the scale."

Honest caveats

  • The minutes are a guide. They're the book's rough split for a 45-minute slot. Many loops run 45–60 minutes or use other shapes (a written requirements doc first). Treat them as proportions.
  • Rubrics vary. The three red flags are the book's list; companies add their own. Senior candidates are usually expected to drive the agenda themselves.
  • Requirements lists. Many interviewers now expect explicit functional and non-functional requirements at the end of step 1. Saying both is a cheap win.
  • Estimation timing varies. The book puts rough maths in step 2 as a sanity check; some interviewers want it in step 1, some never. Ask.
  • Illustrative numbers. 5,000 friends and 10M DAU are the book's example values, not Facebook's real figures. The reads-per-second sum is our extension.
  • EdgeRank is history. Facebook moved to machine-learned ranking long ago; the book uses it only as a rabbit-hole example.
  • Beyond Chapter 3. Push/pull/hybrid fan-out and CDN-for-media come from Chapter 11 and common practice. The game clock and hire verdicts in the boss are teaching devices, not how real decisions are made.
