12.1 Open the pipe: polling, long polling, WebSocket Quest 12.1 →

Phones never talk directly. A chat service sits in the middle with three jobs:
  1. Receive messages from senders
  2. Find the recipients and relay to them
  3. Hold messages for offline recipients until they return
Sending is the easy side. HTTP is client-initiated, and the sender is the client. keep-alive reuses one TCP connection, so each message skips a new handshake.
Receiving is the hard side: the server has news for B, and plain HTTP gives it no way to speak first.
OptionHow it worksWeakness
PollingClient asks "anything new?" on a timerMost answers are empty; a message waits up to one interval
Long pollingServer holds the request open until a message or a timeout, then the client asks again(1) A round-robin load balancer can put the sender on a server that isn't holding the receiver's request. (2) Hard to tell a quietly dead client from an idle one. (3) Idle users time out and reconnect over and over.
WebSocket book's pickStarts as HTTP, upgrades, then one long-lived two-way connectionServers become stateful: each holds live connections, so connection management is the core problem
GET + Upgrade: websocket→101 Switching Protocols→same TCP connection, frames both ways
  • Runs on ports 80 / 443, so it usually gets through firewalls.
  • The book uses WebSocket for sending too: one two-way connection keeps client and server simpler.
  • Rule of thumb: real-time two-way → WebSocket; WebSocket blocked → long polling fallback; rare updates nobody waits on → polling.

"Sending is easy: the client starts an HTTP request. Receiving is the hard part, because the server must speak first. Polling wastes requests, and long polling breaks behind a stateless load balancer and can't spot dead clients. So I'd use WebSocket for both directions over 443, and accept that chat servers become stateful."

12.2 The switchboard: services, scale, discovery Quest 12.2 →

KindWhatWhy
StatelessAPI servers: login, signup, profile, group management; service discoveryRequest in, response out. Any copy behind the load balancer can answer.
StatefulChat servers; presence serversEach client keeps one WebSocket to one server and stays on it while that server is up.
Third-partyPush notifications (APNs / FCM)Reaches a phone when the app isn't running (Chapter 10).
Can one box hold everyone?
1,000,000 connections × 10 KB = 10 GB. It fits in memory, but it's a single point of failure: one crash disconnects every user. Proposing it is a red flag, so scale out.
The adjusted design
  • Chat servers: send / receive (WebSocket)
  • Presence servers: online / offline (WebSocket)
  • API servers: everything else (HTTP via load balancer)
  • Notification servers: push to offline phones
  • KV store: chat history

Login → get a chat server (service discovery)

1 · A logs in→2 · LB → API servers→3 · authenticated; ZooKeeper picks chat server 2→4 · A opens WebSocket to server 2
  • Every live chat server registers with service discovery (the book's example: Apache ZooKeeper). It picks a server by location and capacity.
  • A chat server dies: open sockets can't move, so its clients notice the drop, ask service discovery for a new server, reconnect, and fetch what they missed from storage.
  • Beyond the book: add random backoff (jitter) to reconnects, or hundreds of thousands of phones stampede the survivors at once (a thundering herd).

"Login, signup and profiles are stateless API servers behind a load balancer. Chat and presence servers are stateful, each client holding one WebSocket. On login, service discovery picks a nearby chat server with room. One box could hold 1M connections in about 10 GB, but it's a single point of failure, so I scale out; if a chat server dies, its clients reconnect via service discovery with jittered backoff."

12.3 The message vault: storage, tables, IDs Quest 12.3 →

Generic data → relational DB
Profiles, settings, friend lists, group membership. Small, structured, must be correct. Replicate for availability, shard for scale.
Chat history → key-value store
  • Huge: ~60 billion messages a day (2016)
  • Recent chats get almost all the reads
  • Old messages still need random access (search, mentions, jump-to)
  • Read : write ≈ 1 : 1 for 1-on-1 chat
Why a KV store
  • Scales out horizontally
  • Very low latency by key
  • Relational indexes handle the long tail badly once they outgrow RAM
  • Proven: HBase (Facebook Messenger), Cassandra (Discord)

  • Group primary key = (channel_id, message_id). Every group query runs inside one channel, so the whole channel lives on one partition, sorted by message_id.
  • Order by message_id, never created_at: two messages can share a timestamp, and server clocks drift.

Minting message IDs: unique and sortable by time

OptionVerdict
auto_increment✗ NoSQL stores (Cassandra, HBase) usually don't offer it
Global 64-bit generator (Snowflake, Quest 7.3)✓ Works; unique and time-sorted across every channel (Discord uses Snowflake IDs)
Local sequence per channel✓ book's pick Order only matters inside one chat, and it's easier to build. IDs repeat across channels, which is fine because the key is (channel_id, message_id).
  • Local IDs + the 1-on-1 table: keyed by message_id alone, two chats' message #3 would clash. Treat each 1-on-1 chat as a two-person channel keyed by (channel_id, message_id).
  • Someone still hands out "next": one owner per channel or an atomic counter, or two servers mint the same number.

"Profiles and friends go in a replicated, sharded relational DB. Chat history is huge, about 1:1 read to write, mostly recent with some random access, so it goes in a key-value store like Cassandra, partitioned by channel_id and sorted by message_id. I order by message_id, not created_at, because timestamps tie. A per-channel sequence is enough since order only matters within a chat; a global Snowflake ID also works."

12.4 Special delivery: flows, sync, groups, resend Quest 12.4 →

1-on-1 flow (Alice → Bob)
  1. Alice's app → chat server 1 (WebSocket)
  2. Chat server 1 gets a message ID from the ID generator
  3. It puts the message on the message sync queue
  4. The message is stored in the KV store
  5. 5a Bob online → forwarded to chat server 2, where Bob is connected
    5b Bob offline → push notification servers send a push
  6. Chat server 2 pushes it down Bob's WebSocket
Multi-device sync
Each device keeps its own cur_max_message_id: the newest ID it already has. A message is new for that device when
  • it was sent to the logged-in user, and
  • its ID > that device's cur_max_message_id
Lose the cursor (reinstall) → it resyncs everything above 0. Fetch in pages.
Group sizeFan-outCost of one message
Small (≤ 100; WeChat ≤ 500)Copy per inbox (fan-out on write): one copy in each member's sync queuemembers − 1 writes; each client reads only its own inbox
Huge (100,000)Store once per channel; members read the channel (fan-out on read, beyond the book)1 write instead of 99,999
  • Resend: the book names retry and queueing. Retries mean a message can arrive twice (at-least-once).
  • Beyond the book: ack only after storing; the client stamps a client_msg_id and reuses it on every retry; the server dedupes on it, so a send is idempotent.

"Alice's client sends over its WebSocket to chat server 1, which gets an ID, queues the message and stores it in the KV store. If Bob is online it goes to his chat server and down his socket; if not, a push goes out. Each device syncs with its own cursor (one per conversation with per-channel IDs). Small groups copy into each member's inbox; huge ones store once. Retries carry a client message ID so duplicates are dropped."

12.5 The green dot: online presence Quest 12.5 →

EventWhat happens
LoginOnce the WebSocket to the presence servers is up, they save status = online + last_active_at in the KV store
LogoutHTTP → API servers → presence servers → status = offline
DisconnectDon't flip on every drop: tunnels and lifts would make the dot flap, each flip fanned out to every friend
HeartbeatClient sends "still here" every 5 s; no heartbeat for x = 30 s → offline. Short drops stay invisible.
Fan-out by pub/sub
One channel per friend pair: A's change is published to A-B, A-C, A-D, and each friend gets it over their WebSocket. Cheap for small friend lists.
Huge groups
100,000 members = 100,000 events per status change. Instead, fetch status only when a user opens the group or refreshes. Dots can be stale; fine for a hint.
Tuning the dial
Short timeout → notices departures fast but flickers. Long timeout → calm but leaves "ghosts" online. Faster heartbeats cost load (1 s = 1M/s at 1M users) and battery.

"Presence servers hold a WebSocket to each client and write status plus last_active_at to the KV store. I don't mark users offline on every disconnect, because mobile links flap; a heartbeat every 5 seconds with a 30-second timeout decides. Changes fan out over a pub/sub channel per friend pair, but in a 100,000-member group that's 100,000 events, so there I fetch status when someone opens the group."

Wrap-up extensions (the book's five)

🖼️ Media files
Far bigger than text: compress, keep in cloud storage, show thumbnails.
🔐 End-to-end encryption
Only sender and recipient can read (WhatsApp). The server can still route, but can't search or moderate content.
💾 Client-side cache
Keep recent messages on the device; less data over the wire.
⚡ Load time
Slack's Flannel: a geographically distributed edge cache of users, channels and more.
🛟 Error handling
Chat server dies → service discovery hands out a new one. Message resend → retry and queueing.

"Scope: 1-on-1 and groups up to 100, mobile and web, 50 million DAU, text only, presence, multi-device, push, history forever. Clients hold a WebSocket to a chat server picked by service discovery; login and profiles are stateless API servers behind a load balancer. On send, the chat server gets a per-channel, time-sortable ID, queues the message and stores it in a key-value store keyed by channel_id and message_id, then forwards it to the recipient's chat server or sends a push. Each device syncs with its own cursor, per conversation. Small groups fan out into inboxes; huge ones read the channel. Presence uses 5-second heartbeats, a 30-second timeout and pub/sub to friends. Next: media, E2E, client caching, and failure handling."

Honest caveats (where the book simplifies)

  • Per-channel IDs vs one cursor. The book picks local per-channel IDs, then syncs devices with a single cur_max_message_id. "ID > cursor" means nothing across channels whose counters each start at 1. Keep a cursor per conversation on each device, or give each user's inbox its own rising sequence. Say it out loud if pushed.
  • Storage has moved on. Messenger left HBase for MyRocks (MySQL on RocksDB) around 2018; Discord left Cassandra for ScyllaDB in 2022. Name the access pattern first, the product second.
  • Hot partitions. Discord's real key is (channel_id, bucket), a time window, so one busy channel doesn't become one giant partition.
  • At-least-once + dedupe. "Exactly once" isn't achievable over a network. Ack after storing, retry with a client message ID, drop repeats.
  • Reconnect storms. A dead chat server sends hundreds of thousands of clients reconnecting at once; use jittered exponential backoff and spare capacity.
  • Finding Bob's server. Step 5a needs a user → chat-server route table (often Redis) or a per-user topic. The book leaves it implicit.
  • Per-user presence channels. A channel per friend pair means millions of tiny channels; many systems use one channel per user that friends subscribe to, or batch updates.
  • Heartbeats cost battery, and dead connections need them for WebSocket and long polling alike. Presence is eventually consistent by design: a dot can be ~30 s stale.
  • 10 KB per connection is a round number. WhatsApp ran 2M+ connections on one tuned Erlang/FreeBSD server in 2012. The memory maths is a sanity check; the single point of failure is the real reason to scale out.
  • Our numbers vs the book's. 200,000 polls/s and 200,000 heartbeats/s are our worked examples from the book's 1M concurrent users.
