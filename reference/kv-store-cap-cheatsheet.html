6.1 The store

Key-value pair
Unique key → one value. API: put(key, value), get(key).
Keys
Plain text (last_logged_in_at) or hashed (253DDEC4). Short = faster, less memory.
Values
Anything (string, list, object). Treated as an opaque blob — never inspected. e.g. Dynamo, Memcached, Redis.

Book's design requirements

  • Pairs are small (< 10 KB), but total data is big.
  • High availability, high scalability, automatic scaling, low latency.
  • Tunable consistency — the caller can trade correctness for speed per request.

Single server → distributed

One server = an in-memory hash table. Stretch it with compression and hot data in memory, cold on disk — but it still hits a ceiling. Big data needs a distributed key-value store (a distributed hash table), with each piece of data copied to several replicas.

CAP — pick what survives a split

CConsistency
All clients see the same, latest data from any node.
AAvailability
Every request gets a response, even with nodes down.
PPartition tolerance
Keeps working when the network between nodes breaks.

You can't have all three. Networks will break, so P is mandatory → CA can't exist in practice. The real choice during a partition: CP or AP.

What happens when n3 is cut off from n1 + n2

WritesReads from n3When the network healsUse for
CPRefused (error) — can't copy to every replicaRefused — can't vouch it's latestNothing to fix; never divergedBank balances, seat booking, unique usernames
APAccepted on the reachable sideAnswered — possibly staleMissed writes synced to n3 ("eventually consistent"); conflicts if both sides were writtenShopping carts, likes, presence dots, view counts

Caveat: the book's CP blocks n1 + n2 too. Many real CP systems (majority voting / Raft) keep the majority side working and only stop the minority. Real databases often don't fit a single CP/AP label (Kleppmann).

Rule of thumb

If a wrong answer causes real harm → CP. If a missing answer hurts more → AP.

Say it in the interview

"It depends which guarantee we keep during a partition. CP refuses writes it can't replicate — errors, but never wrong data, like a bank. AP keeps every node answering; the cut-off replica may be stale and syncs when the network heals — fine for a shopping cart. For a general key-value store I'd make it tunable per request."

6.2 Data partition: consistent hashing

Goals
  • Spread data evenly across servers
  • Move as little data as possible when servers join/leave
Hash ring
  • Hash servers and keys onto one ring (SHA-1: 0…2160−1, ends joined)
  • Key → first server clockwise
  • Join/leave moves only one slice ≈ k/n keys
Virtual nodes
  • Each server at many ring points → even slices (book: ~10% spread at 100, ~5% at 200)
  • Dead server's load spreads to all
  • Points ∝ capacity (heterogeneity)
hash % NRingRing + vnodes
Even spread✓✗ lumpy✓
Keys moved when N changesmost (4→5: ~80%)~k/n~k/n, taken from many servers
Server diesalmost all keys remapone neighbour gets it allshared by all
  • Used by Dynamo, Cassandra, Discord, Akamai, Maglev.
  • Caveat: one very hot key still lives on one server.

"I'd partition with consistent hashing: keys go to the first server clockwise on a hash ring, so adding a server moves only ~k/n keys, and virtual nodes keep load even and let bigger servers take more."

6.3 Data replication — which N servers hold a key

Walk clockwise
Hash the key to a spot on the ring, walk clockwise, take the first N servers = the preference list. Every node can compute it — no directory.
Unique machines
With virtual nodes the walk can hit the same machine twice. Skip positions whose machine is already listed — N copies must mean N machines.
Spread data centers
Servers in one DC fail together (power, network, disasters). Place replicas in distinct DCs linked by fast networks.
PlanSurvivesCost
1 copynothing1× disk
3 copies, one DCdead servers, rolling restarts3× disk
3 copies, many DCsa whole-DC outage3× disk + slower cross-DC copies
  • Asynchronous: "OK" can return before every copy lands → brief window of stale reads. How many must confirm = W (Quest 6.4).
  • Real systems: Dynamo's list holds > N nodes to route around failures; Cassandra's NetworkTopologyStrategy sets a count per DC and spreads copies across racks.

"I hash the key onto the ring, walk clockwise and take the first N distinct physical machines, spread across data centers so one outage can't take every copy."

6.4 Quorum consensus (N, W, R)

N = replicas per key (usually 3). W = acks needed before a write counts. R = answers needed before a read returns.
Coordinator = the node that takes the client request, sends it to all N replicas in parallel, and replies after W acks / R answers. W=1 still sends to all N.
Cost: latency is set by the slowest replica you wait for. Bigger W/R → fresher but slower, and fails if too many nodes are down.
W + R > N → the write group and read group share at least one replica → the read sees the latest write (return the newest version).
Setting (N=3)Gives you
R=1, W=3Fast reads (feature flags, product catalog)
W=1, R=3Fast writes (heavy ingest, rare reads)
W=2, R=2Strong + survives 1 node down (Dynamo's (3,2,2))
W=1, R=1 (W+R ≤ N)Fastest, may be stale → eventual
  • Strong: always the latest write. Weak: may miss it. Eventual: replicas converge given time (Dynamo, Cassandra, the book's choice).
  • Tunable: caller picks per request, e.g. Cassandra ONE / QUORUM (n/2+1) / ALL.
  • Partition with W=R=2: the majority side keeps serving; the lone node can't reach a quorum.
  • Caveat: sloppy quorums, concurrent writes, and failed writes that aren't rolled back can still give stale reads.

"With N=3, W=R=2, every read overlaps the last write's replicas, so it sees the latest value, at the cost of waiting for the second-slowest replica; I'd make W and R tunable per request."

6.5 Versioning & vector clocks

Versioning
Every write creates a new, unchangeable version. Without extra info, two replicas holding different values can't tell which is newer, or that they conflict.
Vector clock
D([S1,v1],[S2,v2],…). A write handled by Si adds 1 to vi if the pair exists, otherwise adds [Si,1].
Compare
Missing pair = 0. X ≤ Y on every server → X is an ancestor (drop it). Each side ahead somewhere → siblings (conflict).
StepRead fromHandled byClock
D1—Sx[Sx,1]
D2D1Sx[Sx,2]
D3D2Sy[Sx,2],[Sy,1]
D4D2Sz[Sx,2],[Sz,1] ← sibling of D3
D5D3 + D4, mergedSx[Sx,3],[Sy,1],[Sz,1]
  • Who resolves: the store keeps both siblings; the next client reads both, merges them (cart = union) and writes back.
  • Costs: merge logic in the client; clocks grow → cap them (Dynamo's example: 10) and drop the oldest pair, which can cause false conflicts (Dynamo: never seen in production).
  • Side effect: union merges never lose an add, but deleted items can come back (Dynamo §4.4).
  • Alternative: last-write-wins (Cassandra): keep the newest timestamp. Simple, but silently drops one concurrent write and trusts drifting clocks. Fine when only the latest value matters (sessions, sensor readings).

"Each version carries a vector clock; if neither clock is ≤ the other, the writes were concurrent, so we keep both siblings and let the client merge — or, where only the latest value matters, use last-write-wins and accept the dropped write."

6.6 Handling failures

📡 Detect — gossip
  • Each node bumps its own heartbeat counter, sends its membership list to a few random peers
  • Counter not rising past a timeout → suspect; down only when ≥2 independent sources agree
  • All-to-all pinging is N×(N−1) messages; gossip ≈ N×k
🔀 Cover — sloppy quorum + hinted handoff
  • Use the first W/R healthy servers clockwise, skipping dead ones
  • The stand-in stores a hint ("belongs to s2") and hands the data back on recovery
  • Cost: W+R>N no longer guarantees the latest read; hints are best effort
🌳 Repair — anti-entropy with Merkle trees
  • Buckets → hash keys → hash per bucket → hash up to the root
  • Equal roots = identical; otherwise descend only into differing children
  • Data synced ∝ differences (e.g. 1M buckets for 1B keys ≈ 1,000 keys/bucket)
🌍 Survive a site — multi-DC replication
  • Each key's replicas span data centers
  • Trade-off: cross-DC latency (e.g. Cassandra LOCAL_QUORUM)
FailureMechanism
Is it dead?Gossip + timeout + confirmation
Short outageSloppy quorum + hinted handoff
Lost data / driftMerkle-tree anti-entropy
Whole data center downCross-DC replication

"Detect with gossip, cover with a sloppy quorum and hinted handoff, repair with Merkle-tree anti-entropy, and replicate across data centers to survive a site loss."

6.7 Write & read path (one node's storage engine)

Architecture
  • Clients call get(key) / put(key, value) on any node; that node is the coordinator (proxy to the replicas).
  • Ring + consistent hashing, data replicated, fully decentralized.
  • Every node has the same jobs: client API, failure detection, conflict resolution, failure repair, replication, storage engine → no single point of failure.
Write path
  • 1. Append to commit log (disk, append-only) — replayed after a crash.
  • 2. Insert into memtable (RAM, sorted by key) → ack client.
  • 3. Memtable hits threshold → flush to an SSTable: immutable file of sorted <key, value>.
  • Fast because every disk write is sequential.
Read path
  • 1. Check memtable → hit? return.
  • 2. Ask each SSTable's Bloom filter, newest first.
  • 3. Read only the "maybe" SSTables; first (newest) hit wins.
  • 4. Return result to client.
Skip this……and this breaks
Commit logAcknowledged writes lost on crash
MemtableRandom disk writes; no sorted flush
Bloom filterEvery get opens every SSTable
  • Bloom filter = bit array + k hash functions. Any bit 0 → definitely not; all 1 → maybe. False positives yes, false negatives never.
  • SSTables are never edited: updates = newer copy, deletes = tombstone, compaction merges.

"Writes go to an append-only commit log for durability, then a sorted in-memory memtable that's flushed to immutable SSTables; reads check the memtable, then use per-SSTable Bloom filters to skip files that definitely don't have the key."

BOSS · Design it live: the 45-minute interview

1 · Scope (3–10 min)
  • Pairs < 10 KB, big data
  • High availability, high scalability, auto-scaling
  • Tunable consistency, low latency
2 · High-level (10–15 min)
  • get/put API → any node is coordinator
  • Consistent-hashing ring + virtual nodes
  • Replicate to next N unique servers clockwise
  • AP / eventual, tunable via N, W, R
3 · Deep dive (10–25 min)
  • Walk the goal → technique table below
  • Answer "what if X fails?" with a mechanism
4 · Wrap (3–5 min)
  • Recap + trade-offs; bottlenecks (hot keys, compaction)
  • Error cases; ops: metrics, alerts, logs
  • Never say it's perfect
