9.1 Scope & napkin math Quest 9.1 →

What crawlers are for
  • Indexing: feed a search engine (Googlebot). The most common use, and this chapter's.
  • Archiving: keep pages for the future (national libraries).
  • Mining: pull facts out of pages (finance firms reading annual reports).
  • Monitoring: hunt for copyright or trademark misuse.
The core loop
  • Start from seed URLs.
  • Fetch the pages, pull out their links, queue the new ones, repeat.
  • The web is a graph: pages are nodes, links are edges. Crawling is walking it.
  • Naive version: re-fetches pages and never stops on cycles (A → B → D → A).
Requirements you ask for
  • Purpose: search indexing
  • Scale: 1 billion pages a month
  • Content: HTML only
  • Freshness: pick up new and edited pages
  • Retention: store HTML up to 5 years
  • Duplicates: ignore pages whose content we already have

Four traits of a good crawler

TraitMeansIncident it prevents
ScalableBillions of pages, so fetch in parallel on many machines"One box does 50 pages/s; we need 400"
RobustKeep going through broken HTML, silent servers, crashes, harmful linksA malformed page kills a worker
PoliteSpace out visits to any one siteA small site goes down under our load
ExtensibleNew content type = small change, not a rewrite"Images next quarter" means rebuilding the downloader

Three traits are about our system. Politeness is about other people's servers.

Caveats: 1B ÷ 2.59M s is really 386 pages/s; rounding to 400 is expected. A crawler sets its own pace, so "peak = 2×" is a rule of thumb: the real risk is load on one host, not total load. 500 KB is generous for HTML (often tens of KB, and it compresses), so 30 PB is an upper bound. Storage scales in a straight line: 100 KB pages make it 6 PB.

"I'd confirm it's for search indexing: a billion HTML pages a month, new and edited pages, five years of storage, duplicates skipped. That's about 400 pages a second, 800 at peak; at 500 KB a page, 500 TB a month and 30 PB over five years. It has to be scalable, robust, polite and extensible."

9.2 The pipeline: eleven boxes Quest 9.2 →

BoxIts job, in one line
Seed URLsThe starting addresses. Pick them for coverage: slice the web by country and by topic, seed each slice.
URL FrontierThe to-do list of URLs still waiting to be fetched (9.3 makes it smart).
HTML DownloaderFetches the page behind each URL it's handed.
DNS ResolverTurns a host name into the IP address to connect to.
Content ParserReads the HTML and rejects broken pages. Its own box, so slow parsing never holds up downloads.
Content Seen?Drops a page when we already hold identical content (compares fingerprints).
Content StorageKeeps the pages we save: mostly on disk, popular ones cached in memory.
URL ExtractorPulls the links out of a page and makes them full URLs.
URL FilterThrows out links we never want: certain file types, broken links, blocklisted sites.
URL Seen?Skips links we already fetched or already queued.
URL StorageThe record of every URL the crawl has already handled.

Trace one page round the loop

  • Seeds enter the frontier → a downloader takes a batch, asks DNS for each host's IP, fetches the HTML.
  • Parser: broken page? It stops here. Valid page → Content Seen?: same fingerprint as a stored page? It stops here, links never read.
  • New content goes two ways: saved to Content Storage, and handed to the URL Extractor (plug-in modules sit right beside it, 9.5).
  • Each link → URL Filter (junk stops here) → URL Seen? (known URLs stop here) → recorded in URL Storage and added to the frontier. The loop closes.

Two different "seen?" questions

Content Seen? · "same bytes?"
  • Hash each page into a short fingerprint; look it up in a set
  • Char-by-char against billions of pages is hopeless; one lookup is constant time
  • Catches http/https twins, mirrors, / vs /index.html
  • Exact hash: one changed character → different fingerprint
URL Seen? · "same address?"
  • Stops repeat fetches, extra load on sites, endless A → B → A loops
  • Hash table: exact, but memory-hungry
  • Bloom filter: bit array + k hashes. Any bit off → definitely new; all on → probably seen
  • False positive = a new URL silently skipped. No false negatives.
Be the URL Extractor (on en.wikipedia.org/wiki/Spider)
  • /wiki/Web → https://en.wikipedia.org/wiki/Web
  • Arachnid → …/wiki/Arachnid (replaces last segment)
  • #History → the same page: drop the fragment
  • Already absolute → leave it alone
Remember 1 billion URLs with…MemoryAssumption
Raw URL strings~100 GB~100 bytes per URL
Hash set of fingerprints~8 GB8 bytes each, before table overhead (often 1.5–2×)
Bloom filter, 1% false positives~1.2 GB~9.6 bits per URL

Caveats: near-duplicates (a new date, an ad block) need shingling or SimHash, not an exact hash. Real crawlers normalise URLs before URL Seen? (lower-case host, drop #fragment and default port, resolve ..). The 29% figure is an industry estimate: say "roughly a third". Bloom filters can't delete and get worse as they fill, so size them up front and rebuild now and then. The sizing table is beyond the book.

"Seeds go into the URL frontier; downloaders take URLs, resolve DNS and fetch. A parser validates the HTML, then Content Seen? fingerprints the page and drops it if we have that hash, since about 29% of pages are duplicates. New pages are stored and their links extracted as absolute URLs, filtered, and checked against URL Seen?, a hash table or a Bloom filter if memory is tight. New URLs are recorded and go back into the frontier."

9.3 The URL frontier Quest 9.3 →

DFS vs BFS
  • DFS (stack): dives one chain; the web can be extremely deep. Usually a bad fit.
  • BFS (FIFO queue): the usual choice, fetches in the order found.
  • Plain BFS problem 1: most links point to the same host → impolite bursts.
  • Problem 2: every URL waits its turn → no priority.
Priority signals
  • PageRank (how many important pages link here)
  • Website traffic
  • Update frequency
Apple's home page beats a forum post that mentions Apple.
Freshness and storage
  • Recrawl by update history: pages that change often get revisited often
  • Recrawl important pages first and more often
  • Hundreds of millions of URLs: disk for the bulk, memory buffers for enqueue and dequeue, flushed in batches

Two layers: what comes out next, and when a host may be hit

Front queues · priority
Prioritizer scores each URL→f1 (high) … fn (low)→Selector: random, biased toward high
Back queues · politeness
Router+Mapping table host → queue→b1 … bn, one host each→Selector: one queue per worker→Worker: one page at a time, pause between
ComplaintPart that fixes it
"Your bot sends us 20 requests a second"Back queues: one host, one queue, one worker, a delay
A week spent on spam forumsFront queues: score news sites higher
Low-priority URLs never crawledBiased random selector, not strict priority (which starves f2…fn)
Stale prices / yesterday's headlinesRecrawl policy: update history + importance
Restart wiped 200M queued URLs / every enqueue waits on diskStorage: disk + memory buffers

Caveats: the web has hundreds of millions of hosts, so Mercator keeps a fixed number of back queues (about 3× the workers), refills an empty one with a new host, and uses a heap of "earliest next contact" times (beyond the book). Politeness is really per server: many small sites share one IP. Google adapts each site's crawl rate to how the server responds. PageRank is just the book's example. Recrawling strictly by change rate can backfire on pages that change constantly (Cho & Garcia-Molina).

"Plain BFS hammers one host and ignores importance, so the frontier has two layers. Front queues handle priority: a prioritizer scores URLs by PageRank, traffic and update frequency, and a selector picks queues randomly but biased toward high priority. Back queues handle politeness: a host-to-queue table puts each host in its own queue, each worker drains one queue a page at a time with a pause. I recrawl by update history and importance, and keep the frontier on disk with memory buffers."

9.4 Downloader & robustness Quest 9.4 →

robots.txt (Robots Exclusion Protocol)
  • Read it before crawling a site
  • User-agent: who the group is for (* = any bot)
  • Disallow: /cart/ blocks paths starting with /cart/
  • Allow: re-opens part of a blocked path; the longer match wins
  • A bot with its own group ignores the * group
  • Cache it per site, refresh periodically, or you double your requests
Four speed-ups
  • Distributed crawl: many servers × many threads, URL space split between them
  • DNS cache: a lookup is 10–200 ms and often synchronous, so other threads stall; keep host → IP, refresh by cron
  • Locality: crawl servers (and caches, queues, storage) near the sites
  • Short timeout: give up on silent hosts, move on
Four robustness measures
  • Consistent hashing spreads hosts over downloaders; add or lose one and only a slice moves
  • Save crawl state and data: a crash resumes, not restarts
  • Exception handling: one bad page never crashes the system
  • Data validation at each step

Throughput ≈ servers × threads ÷ seconds per fetch. At 1 s per fetch you need ~800 fetches in flight for the peak: 8 servers × 100 threads, or 16 × 50. 10 servers × 50 threads at 0.5 s ≈ 1,000 pages/s.

Hashing by host keeps all of one host's URLs on one server, so it serves politeness too. hash % N reshuffles almost every host when N changes; the ring moves only one arc.

Caveats: robots.txt is a sign, not a lock; a blocked page can still appear in results if linked elsewhere. RFC 9309 (2022) says don't trust a cached copy for more than about 24 hours; a 4xx means "all allowed", a 5xx means "assume all blocked". Crawl-delay isn't in the standard (Google ignores it). Real DNS answers carry a TTL; big crawlers run their own async resolver. Pair timeouts with retry and back-off, and respect 429 / Retry-After. The throughput formula ignores politeness and bandwidth caps.

"The downloader checks each site's robots.txt first and caches it. For speed: distribute over many servers and threads, cache DNS because a lookup is 10 to 200 ms and blocks threads, crawl from regions close to the sites, and use short timeouts. For robustness: consistent hashing assigns hosts to downloaders, we checkpoint crawl state, handle exceptions per page and validate data."

9.5 Traps, plug-ins & the wrap-up Quest 9.5 →

Plug-in modules (extensibility)
  • The book's two: PNG Downloader (fetch PNG images) and Web Monitor (copyright and trademark misuse)
  • Both plug in after Content Seen?, beside the URL Extractor: they read every new, unique page
  • The core loop doesn't change: zero lines of core code
  • Beyond the book: a PDF parser sits after download; a spam blocklist is just a URL Filter rule
Spider traps
  • A site that keeps producing new pages: /foo/bar/foo/bar/…, endless "next month" calendars
  • Max URL length (in the URL Filter) stops paths that grow
  • Easy to spot (one host with abnormally many pages), hard to catch automatically
  • So a human reviews the flagged site: exclude it or write a custom URL filter
Wrap-up extras
  • Render JavaScript before parsing (links built by scripts/AJAX)
  • Anti-spam component: drop low-quality pages
  • Replicate + shard the storage
  • Stateless crawl servers: scale out to thousands
  • Availability, consistency, reliability
  • Analytics on the crawl, to tune it
Problem contentWhat it isHandle it withWhere
RedundantSame content again (~29% of pages)Hash / checksumContent Seen?
Spider trapsEndless generated pagesMax URL length + anomaly flag + human review / custom filterURL Filter
Data noiseAds, code snippets, spam linksExclude where possible; anti-spamFilters

Caveats: URL length only stops traps whose URLs grow; calendars, session IDs and filter combos stay short, so real crawlers also cap pages per host and depth, and strip parameters. Rendering costs far more than a plain fetch, so crawlers render selectively, often in a later pass. The book's "server-side rendering" means the crawler runs the scripts; today "dynamic rendering" usually means a site serving bots a pre-rendered copy, which Google calls a workaround. "Noise" depends on the job: code snippets are gold for code search.

"Three kinds of bad content: duplicates, about 29% of pages, caught by hashing; spider traps, where a max URL length handles the simple ones and abnormal hosts go to a human to exclude or filter; and noise like ads and spam, filtered out. New content types are plug-in modules, like a PNG downloader or a web monitor, reading new pages beside the URL extractor. With more time: render JavaScript, add anti-spam, replicate and shard storage, keep servers stateless, add analytics."

Honest caveats strip: near-duplicates need shingling or SimHash, not an exact hash · politeness should be per IP as well as per host · robots.txt is voluntary, and Crawl-delay is non-standard · the book's "server-side rendering" means the crawler renders the page · the two-layer frontier comes from Mercator (1999); modern crawlers add adaptive rate limits and learned priorities · indexing and ranking read from Content Storage and are out of scope.

"A search-indexing crawler: a billion HTML pages a month, new and edited pages, five years kept, duplicates skipped. That's 400 pages a second, 800 at peak, 500 TB a month, 30 PB over five years, and it must be scalable, robust, polite and extensible. Seeds feed a two-layer frontier, front queues for priority and back queues for politeness, on disk with memory buffers. Distributed downloaders obey cached robots.txt, cache DNS, sit near the sites and time out fast, with hosts spread by consistent hashing and state checkpointed. A parser validates, Content Seen? drops duplicate pages, the extractor and any plug-ins read new pages, links are filtered and checked by URL Seen? before looping back. I'd guard against traps with a URL length cap and human review, filter noise, and render JavaScript where it matters."
