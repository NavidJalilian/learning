14.1 Size Up the Tube: scope + napkin maths Quest 14.1 →

Why narrow it
The book opens with YouTube's scale (2 billion monthly users, 5 billion views a day, 73% of US adults, 50 million creators, $15.1B ad revenue in 2019, 37% of mobile traffic, 80 languages). Far too big for 45 minutes, so keep two flows: upload and watch.
Questions that change the design
  • Features? Clients? DAU? Time per user?
  • International? Resolutions + formats?
  • Encryption? Max file size?
  • Can we use existing cloud services? (yes → rent blob storage + CDN)
Non-functional goals
  • Fast uploads
  • Smooth streaming
  • Change video quality
  • Low infrastructure cost
  • High availability, scalability, reliability
  • Mobile apps, web browsers, smart TVs
EstimateFormulaResult
Uploads / day5M DAU × 10%500,000
New storage / day500,000 × 300 MB (uploads, not views)150 TB
CDN cost / day5M × 5 views × 0.3 GB × $0.02 (views, not uploads)$150,000
  • Classic slips: storage from views (×50 too big), CDN from uploads ($3,000, ×50 too small), MB vs GB.
  • Add 5 renditions × 3 replicas and storage is ×15 (~2.25 PB a day). Factors multiply, they don't add.
  • The CDN is the bill that dominates, which is why cost-saving gets its own deep-dive section (14.5).

"Upload and watch only; mobile, web and TV; 5 million DAU. Storage: 10% upload one 300 MB video, so about 150 TB of new originals a day before renditions and replicas. Bandwidth: 25 million views × 0.3 GB × $0.02 ≈ $150,000 a day, so the CDN is the cost to attack."

14.2 Upload Lane, Watch Lane: high-level design Quest 14.2 →

📱 Client
Computer, phone or smart TV.
🌍 CDN
Stores and streams the videos from edge servers near the viewer.
🖥️ API servers
Everything except streaming: feed, upload URL, metadata DB + cache updates, signup.

Upload flow (the book's numbered steps)

StepWhat happens
1Client uploads the file to original storage (blob storage). The bytes never pass through the API servers.
2Transcoding servers fetch the original and start transcoding.
3aIn parallel with 3b: transcoded files go to transcoded storage…
3a.1…and are distributed to the CDN.
3bA "transcoding done" event goes onto the completion queue.
3b.1Completion handler workers keep pulling events off the queue…
3b.1.a/b…and update the metadata DB (a) and metadata cache (b).
4API servers tell the client the video is uploaded and ready to stream.
flow bIn parallel with the upload: metadata (title, size, format…) goes client → load balancer → API servers → metadata cache + DB.
  • Metadata DB: sharded (spread the load) and replicated (availability + reads). Cache: video metadata and user objects in memory.
  • Why the completion queue: decoupling. Transcoders post "done" and move on; the handler absorbs bursts and retries if the DB is slow.
  • Stream, don't download: the player fetches small pieces and plays them as they arrive (300 MB at 20 Mbit/s: 120 s to download, under a second to first frame when streaming).
  • Protocols: MPEG-DASH, Apple HLS, Microsoft Smooth Streaming, Adobe HDS. They differ in supported encodings and players. Today HLS + DASH dominate.
  • Stream from the nearest CDN edge, so latency is low and video traffic never touches your servers.

"The file goes straight to original storage while the metadata goes through the API servers. Transcoders convert it; then, in parallel, the outputs go to transcoded storage and the CDN, and a completion event goes through a queue to handlers that update the metadata DB and cache. Then the API tells the client it's ready, and viewers stream from the nearest edge."

14.3 The Format Forge: why transcode, and the DAG Quest 14.3 →

Four reasons to transcode
  1. Storage: raw video is huge (an hour of 1080p60: ~1.3 TB truly raw, a few hundred GB as a master, a few GB as a streaming encode)
  2. Compatibility: devices and browsers play only some formats
  3. Bandwidth: high resolution for fast links, low for slow
  4. Changing networks: switch quality mid-video
Container vs codec
  • Container = the box: video + audio + metadata. Named by the extension: .mp4, .mov, .avi
  • Codec = the language: how pictures are compressed. H.264, VP9, HEVC (+ AV1 today)
  • A device must open the box and read the codec. Keep H.264-in-MP4 as the safe fallback.
Adaptive bitrate (ABR)
  • Bitrate ladder: same video at several rungs (e.g. 360p 0.7 → 4K 15 Mbit/s)
  • Each rung cut into few-second segments
  • A manifest lists them (HLS .m3u8, DASH .mpd)
  • Player picks the rung for each next segment

The DAG (directed acyclic graph): tasks + "must finish before" arrows, no loops

Original video→Split→VideoAudioMetadata
Video →Inspection→Video encodings ×NThumbnailWatermark
Audio →Audio encoding· all branches + metadata →Assemble→ 360p.mp4 … 4k.mp4
  • Idea borrowed from Facebook's streaming video engine (SVE). Programmers set which tasks run via config, so each creator's pipeline can differ (watermark or not, own thumbnail or generated).
  • Inspection first → a malformed file fails fast, before expensive encoding.
  • Independent branches run on different workers: latency = the critical path (longest dependent chain), cost = total work.

"We transcode for storage, compatibility, bandwidth and changing networks. Each rendition is cut into segments listed in a manifest, so the player adapts per segment. The work is a configurable DAG like Facebook's SVE: split, inspect, then encodings, thumbnail and watermark in parallel with audio encoding, then assemble."

14.4 The Transcoding Factory: the architecture Quest 14.4 →

Preprocessor→DAG scheduler→Resource manager→Task workers→Encoded video
underneath, used by the line:Temporary storage
✂️ Preprocessor
  • Splits the video stream into GOP-aligned chunks (GOP = group of pictures: starts with a full I-frame, plays on its own, a few seconds)
  • Splits on the server for old clients that can't
  • Builds the DAG from config files client programmers write
  • Caches GOPs + metadata in temp storage → a failed encode retries from the saved piece
🗺️ DAG scheduler
Splits the DAG into stages of tasks that don't depend on each other and puts them in the resource manager's task queue. Book example: stage 1 = split into video, audio, metadata; stage 2 = video encoding, thumbnail, audio encoding.
🎛️ Resource manager
  • Task queue: priority queue of tasks
  • Worker queue: priority queue of worker utilisation
  • Running queue: which task runs on which worker
  • + a task scheduler (loop below)
👷 Task workers → 🎞️ Encoded video
Typed workers: encoders, thumbnail makers, watermarkers, mergers. Output e.g. funny_720p.mp4 → transcoded storage → CDN.

Task scheduler loop

  1. Get the highest-priority task from the task queue.
  2. Get the best (least-busy) worker of the right type from the worker queue.
  3. Tell that worker to run the task.
  4. Bind task + worker and put the pair in the running queue.
  5. Remove the pair from the running queue when the task is done. (A worker dies → the running queue shows its task → re-queue it.)
📦 Temporary storage: choose the system by data type, size, access frequency and life span. Metadata (small, read often) → in memory. Video + audio → blob storage. Freed once the video's processing completes.

"The preprocessor splits by GOP, builds the DAG from config and saves the pieces for retries. The DAG scheduler turns the graph into stages in a priority task queue. The resource manager pairs the top task with the least-busy worker and tracks it in a running queue. Workers encode, watermark and merge; temporary data is freed at the end."

Pre-signed URL in 3 steps
  1. Client asks the API servers for permission to upload
  2. API servers return a URL signed for one object, one method, short expiry
  3. Client PUTs the video straight to cloud storage; storage checks signature + expiry
Long tail
A few videos get most views (in the quest's chart the top 10% get ~80%). Caching just the head covers most traffic. Every cost trick depends on popularity, access patterns and size, so analyse historical viewing first.
Two kinds of error
  • Recoverable (a segment fails to transcode): retry a few times, then return an error code
  • Non-recoverable (malformed video format): stop that video's tasks, return an error code

"Speed: chunked, resumable uploads to nearby upload centers and queues between modules. Safety: pre-signed upload URLs, plus DRM or AES and watermarks for playback. Cost: views follow a long tail, so only the head lives on the CDN. Failures: retry what can recover, stop and return an error for what can't, and fail over per component."

Honest caveats (where the book simplifies)

  • Dated stats. The intro figures are from around 2019–2020 third-party roundups. Use them for "how big, roughly", never as today's facts.
  • 150 TB is originals only. Renditions (often 5+) and replicas (often 3) multiply it many times.
  • $0.02/GB is CloudFront's cheapest US tier. The first tier is about $0.085 (4.25× → ~$637,500/day). At 7.5 PB a day nearly all traffic is in the cheap tier; big customers negotiate private rates.
  • The CDN estimate cuts both ways. Every view streaming the whole 300 MB is pessimistic; US-only pricing for an international audience is optimistic.
  • Byte vs GOP chunking. Real uploaders (S3 multipart, YouTube resumable uploads) chunk by bytes; GOP-aware splitting usually happens on the server.
  • Clean GOP cuts need closed GOPs, and extra keyframes cost a little size or quality.
  • AES is not DRM. Plain AES-128 HLS with a fetchable key URL is weak; watermarks deter and trace, they don't block copying.
  • Replica promotion can lose writes if replication was asynchronous; a fresh cache node starts cold.
  • Retries need idempotent tasks + backoff, and queues usually deliver at least once, so handlers must tolerate duplicates.
  • The three-queue resource manager is a teaching design. Real systems often use a general job scheduler or managed batch/queue service.
  • Step 4 "inform the client" is unspecified: push notification or status polling are both fine answers.
  • Live streaming in practice uses ingest protocols like RTMP or SRT and low-latency HLS/DASH; takedowns at scale rely on fingerprinting (Content ID).
