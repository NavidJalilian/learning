7.1 Numbers Nobody Repeats

▶ Replay Quest 7.1
One database
auto_increment gives 1, 2, 3… and never repeats, because one machine owns the one counter.
Why it stops working
One database isn't big enough, and generating IDs across several databases with low delay is hard. Shard the table and each shard counts from 1 on its own: 2 inserts (one per shard) already clash.
Multi-master: count by k
k = number of servers. Each steps by k from its own offset 1…k. k = 2 → A: 1, 3, 5… · B: 2, 4, 6…. MySQL: auto_increment_increment (step) + auto_increment_offset (start).

The book's three drawbacks

DrawbackWhat you saw in the sim
Hard to scale across several data centersEvery server everywhere must agree on k and its own offset
IDs don't go up with time across serversA busy server reaches 5 while the other is still at 2 → newest ID isn't the biggest
Adding or removing a server hurtsNew server C (step 3, offset 3) issued 3, 6, 9: all already taken. Fix = re-plan every server at once, starting above the max ID
  • Scorecard: unique ✓ · numeric ✓ · 64-bit ✓ · 10k+/s ✓ · time-ordered ✗ · easy to grow ✗.
  • Still the right tool: a small, fixed fleet in one DC where nobody sorts by ID (e.g. an active-active pair, odd/even).

"Before designing, I'd confirm: unique, numbers only, 64 bits, ordered by creation time, over 10,000 a second. One database's auto_increment only works because one box owns the counter. Multi-master steps each of k databases by k with its own offset, so they never collide, but IDs aren't time-ordered across servers and changing k means re-planning everyone."

7.2 Dice or the Ticket Booth

▶ Replay Quest 7.2
UUID
  • 128 bits = 32 hex digits in groups 8-4-4-4-12, e.g. 09c93e62-50b4-468d-bf8a-c07e1040bfb2
  • v4: the version digit (first of group 3 is always 4) + variant bits = 6 fixed → 122 random
  • Every server rolls its own: no coordination
Birthday odds
  • P(dup) ≈ 1 − e−n² / (2 × 2122)
  • 50% at n ≈ 2.7 × 1018 → ~86 yrs at 1B/s (book rounds to ~100)
  • At our 10k/s: ~8.6 million years
  • Collisions are not why UUIDs lose. Real dupes come from broken randomness (cloned VMs, weak seeds).
Ticket server (Flickr, 2010)
  • One MySQL box whose only job is auto_increment
  • One-row table, bumped with REPLACE INTO, read with LAST_INSERT_ID()
  • Flickr runs two: odd + even (count by k, k = 2)
REPLACE INTO Tickets64 (stub) VALUES ('a');
SELECT LAST_INSERT_ID();
UUID
+ simple · no coordination, no sync issues · scales with the web tier
− 128 bits, not 64 · not time-ordered · can be non-numeric (usually a 36-char string)
Ticket server
+ numeric · easy · fine for small to medium apps
− single point of failure (SPOF). More servers → sync problems and only rough order. Every ID costs a network round trip (batches of IDs help).

"UUIDs need no coordination and practically never clash, but they're 128 bits and carry no time, so sorting by ID doesn't sort by date. A ticket server gives short ordered numbers but it's a single point of failure and costs a round trip per ID; adding an odd/even twin removes the SPOF but loses strict order. None of the three meets all five, so I'd go Snowflake."

7.3 Anatomy of a Snowflake

▶ Replay Quest 7.3
signtimestampdatacentermachinesequence
SectionBitsJob
Sign1Always 0 → ID stays positive in a signed long. Reserved for later.
Timestamp41Sorted by date. Top bits win every comparison, so a later ms beats any machine or sequence value.
DC + machine5 + 5Unique with no coordination. No two generators share these 10 bits. Fixed at startup; changing them needs careful review.
Sequence12Throughput. Counts IDs within one ms on one machine; back to 0 each ms, so it is 0 for most IDs.

Decode one (the book's Figure 7-7 timestamp)

Masks
ts = id >> 22
dc = (id >> 17) & 31
machine = (id >> 12) & 31
seq = id & 4095
31 = five 1s, 4,095 = twelve 1s
Worked example
ID 1248292468186091525
>> 22 → 297,616,116,568
+ epoch 1,288,834,974,657
= 1,586,451,091,225 ms → 2020-04-09 16:51:31 UTC
dc 3 · machine 17 · seq 5
Traps
  • Forget the epoch → 1979-06-07
  • The epoch itself → 2010-11-04
  • Last reachable moment → 2080-07-10
  • Within one ms, order follows machine number, not real time
  • Pick a custom epoch near launch: every ms between the epoch and launch is lifetime already spent. After ~69 years → new epoch or migrate IDs.
  • Real variants: Instagram 41 time | 13 shard | 10 seq (in PostgreSQL) · Discord 42-bit time from 2015 · Sonyflake 39 bits of 10 ms | 8 seq | 16 machine. Same idea, different budgets.
  • IDs leak info: creation time and machine. Never use them as secret tokens.

"I'd use a Snowflake-style 64-bit ID: 1 sign bit, 41 bits of milliseconds since a custom epoch, 5 bits of datacenter, 5 of machine, 12 of sequence. Time on the left makes IDs sort by time, the generator's name in the middle makes them unique with no coordination, and the counter on the right gives 4,096 per millisecond per machine. 41 bits lasts about 69 years, so I'd set the epoch near launch."

7.4 When Clocks Lie

▶ Replay Quest 7.4
ProblemWhat goes wrongFix
4,097th ID in one msWrapping the sequence to 0 reissues an ID from that same msWait (spin) for the next ms, restart at 0. Cost: a sub-ms stall, never a duplicate
Clock steps backwards (NTP step, leap second)Re-enters used milliseconds → duplicate and smaller IDsRemember the last timestamp; if now < last, refuse or wait (Twitter's code refuses and logs). NTP slew, not step. Alert on jumps. Smear leap seconds.
Skew between machinesA fast clock stamps IDs "from the future"Accept it: IDs are roughly sortable (k-sorted), within the skew. Fine for feeds, not for "who clicked first"
Two nodes share dc + machineSame ms + same seq → identical IDsAssign at startup from config or a coordinator (Twitter used ZooKeeper). Never bake into a VM image
One ID box goes downEvery write that needs an ID failsLibrary in every service, or several instances behind a load balancer, each with its own machine ID

Section length tuning (63 usable bits)

Layout (ts | dc | m | seq)LifetimeGeneratorsIDs per tickGood for
41 | 5 | 5 | 12, 1 ms69.7 yrs1,0244,096 / msThe book's default
42 | 5 | 5 | 11, 1 ms139 yrs1,0242,048 / msLong-lived, low traffic (the book's example)
41 | 3 | 7 | 12, 1 ms69.7 yrs8 DCs × 1284,096 / msMore machines per DC
41 | 2 | 5 | 15, 1 ms69.7 yrs12832,768 / msHuge bursts, small fleet
Sonyflake: 39 time | 16 m | 8 seq, 10 ms~174 yrs65,536256 / 10 msLong life, many machines
  • One more timestamp bit doubles the lifetime. Bits always come from somewhere: fleet size or burst size.
  • NTP keeps clocks within a few ms on a good network; ntpd slews small errors and only steps past 128 ms by default.
  • The book's "multiple cores" worry: cores share one clock; the real risk is several processes reusing the same machine ID.

"Past 4,096 in a millisecond, it waits for the next millisecond instead of wrapping. The real risk is the clock: NTP or a leap second can step it back, so I keep the last timestamp and refuse or wait while the clock is behind, and have NTP slew. Across machines IDs are only roughly ordered, within the clock skew. I can re-split the bits for our needs, machine IDs come from config or a coordinator, and the generator runs inside each service so there's no box to lose."

BOSS · Mint It Live: the 45-minute interview

▶ Replay the boss
1 · Scope (3–10 min)
  • Ask: properties? +1 or by time? digits only? length? scale?
  • Bonus: several data centers? runs for decades?
  • Play back: unique, numeric, 64-bit, roughly time-ordered, 10k+/s
2 · High-level (10–15 min)
  • Name all four options; reject each by the rule it breaks
  • Multi-master → time order · UUID → 128 bits · ticket server → SPOF
  • Pick Snowflake: split the 64 bits
3 · Deep dive (10–25 min)
  • Draw 1 | 41 | 5 | 5 | 12
  • Numbers: ~69 yrs, 4,096/ms, 1,024 generators
  • Decode: >> 22, add the epoch
  • Answer the curveballs below
4 · Wrap (3–5 min)
The book's three points:
  • Clock synchronization (NTP)
  • Section length tuning
  • High availability
Bonus: monitor clock offset, next-ms waits, duplicate alarms.

"I used a Snowflake-style 64-bit ID: 1 sign bit, 41 bits of milliseconds, 5 + 5 bits of datacenter and machine, and 12 bits of sequence, so IDs are roughly time-ordered with no coordination. It lasts about 69 years and each machine mints up to 4,096 IDs per millisecond. With time left I'd cover clock sync, tuning the section lengths, and keeping the generator highly available."

Honest caveats

  • "Ordered by date" really means roughly. Strict only within one machine; across machines, within the clock skew, and inside one ms by machine number.
  • The book skips two cases. It never says what happens past 4,096 IDs in a ms or when the clock goes backwards. Wait-for-next-ms and refuse-while-behind come from Twitter's original code.
  • Rounded numbers. The book's "about 100 years" for UUID clashes at 1B/s is ~86 by the birthday formula; its "about 69 years" is 69.7.
  • UUIDv7 exists now (RFC 9562, 2024): 48-bit ms timestamp + random bits, time-ordered, no machine IDs. Still 128 bits, so it fails this prompt, but it's a strong answer if 128 bits is allowed.
  • JavaScript can't hold these IDs. Numbers are exact only to 253 − 1; Snowflake IDs are ~260. Twitter added id_str; Discord sends snowflakes as strings.
  • IDs leak creation time (and the machine, and rough traffic). Fine for debugging, wrong for secrets.
  • Random UUID keys hurt databases: v4 inserts land all over a B-tree index, splitting pages.
  • "Multi-master" is two config settings, not replication itself, and changing auto_increment_increment live doesn't renumber old rows.
  • High availability gets one line in the book. In practice the simplest answer is an embedded library with machine IDs assigned at deploy time.
