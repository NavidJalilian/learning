10.1 Three roads to the lock screen Quest 10.1 →

Your system is the provider. It never delivers the last mile itself: every road is Provider → third-party delivery service → device.

Contact info gathering
  • At install or signup, the app calls the API servers (behind a load balancer)
  • They store the contact info in the database
  • The app gets a device token from APNs/FCM and sends it up too
Two tables
  • user: user_id, email, country_code, phone_number, created_at
  • device: id, device_token, user_id, last_logged_in_at
  • One user → many devices, so tokens get their own table; a push to a user goes to every token
Keep providers pluggable
  • The book's extensibility point: plug a service in or out easily
  • Hide each one behind one send() interface per channel
  • New market = config change, not a rewrite

Beyond the book: tokens go stale (uninstall, rotation). APNs answers 410 Unregistered (or 400 BadDeviceToken), FCM answers UNREGISTERED: delete the token, don't retry. Store phone numbers as E.164 strings (+447911123456), not integers: a 32-bit int overflows and you lose the + and leading zeros. Real APNs requests also carry headers (apns-topic, apns-push-type, apns-priority) over HTTP/2, with a 4 KB payload limit.

"Our system is the provider. For iOS we send APNs a device token we stored at install plus a JSON payload; Android is the same shape through FCM; SMS and email go through providers like Twilio and SendGrid. Email and phone live in the user table, tokens in a device table because one user has many devices. Each provider sits behind an interface so we can swap it, say for JPush in China, and we delete tokens APNs reports as unregistered."

10.2 Shatter the single server Quest 10.2 →

Version 1: one box
Services (micro-services, cron jobs, distributed systems) call one notification server that holds the API, DB, cache, HTML rendering and sending.
  • Single point of failure: it dies, nothing goes out
  • Hard to scale: DB, cache and processing can't grow separately
  • Performance bottleneck: heavy rendering + waiting on slow providers, all at peak
Three fixes
  1. Move the database and cache out of the server
  2. Add more notification servers with autoscaling (horizontal scaling)
  3. Add message queues to decouple the parts
Servers stay stateless, so any one can take any request.
Why queues
  • Buffer: soak up a 2-million-email campaign while workers drain at the provider's pace
  • Decouple: the server replies at once, workers send later
  • One queue per channel: an SMS provider outage backs up only the SMS queue; push and email keep flowing

The 6-step flow (one iOS push)

  1. A service calls the notification servers' send API.
  2. The server fetches user info, device token and notification settings from the cache, or the DB on a miss.
  3. It puts the event on the matching queue (iOS PN queue).
  4. Workers pull the event off the queue.
  5. Workers send it to the third party (APNs).
  6. APNs delivers it to the device.
Sample send API (email) 
POST /v1/email/send
{ "to": [{"user_id": 123456}],
  "from": {"email": "from_address@example.com"},
  "subject": "Hello, World!",
  "content": [{"type": "text/plain", "value": "Hello, World!"}] }
The book's sample posts this email body to /v/sms/send: treat it as a typo. Version and channel the path.
Why only a user_id
  • The caller says who, not where
  • The server resolves email, phone, tokens and settings in one place
  • No service keeps its own copy of contact details, and none can skip an opt-out
  • API is internal / verified clients only, to stop spam
Which part fixes it?
  • Burst or provider outage → queue
  • Server dies / API tier slow → more servers (autoscaled)
  • DB melting on hot reads → cache
  • Queue growing, provider healthy → more workers

Caveats: the book's figure draws no load balancer; with several stateless servers you need one anyway. A queue on one broker is a new single point of failure: replicate it (Kafka partition replicas, RabbitMQ quorum queues). The book splits by channel only; real systems add priority lanes so a login code never waits behind a marketing blast.

"One server is a single point of failure, can't scale its parts separately, and bottlenecks at peak. So services call an internal, authenticated API on stateless, autoscaled notification servers. They validate, look up user info, tokens and settings in a cache backed by the DB, and drop an event on one queue per channel. Workers pull and call APNs, FCM, SMS or email providers. Average load is only ~185 a second, but it's bursty, and the queues absorb that while isolating one provider's outage."

10.3 Never lose a ping Quest 10.3 →

The book's rule: a notification may be delayed or reordered, but never lost. Mechanism: a notification log (database) + a retry mechanism.

Worker crashes mid-send…Ack before sendAck after send
Log OFFLost: memory held the only copyArrives late: queue redelivers after a timeout
Log ONArrives late: recovery job re-sends "pending" entriesArrives late: both safety nets

The log only saves you if the write reaches disk before the ack, and something re-scans pending entries. Most real systems simply ack after the provider accepts.

Exactly-once is a myth

RunAt-least-once (retry)At-most-once (ack on pull)
A · crash before calling APNs1 · once, late0 · lost
B · APNs delivers, reply lost2 · duplicate1
C · delivered, crash before ack2 · duplicate1

"Never arrived" and "arrived, reply lost" look the same to the worker (the Two Generals problem). Notifications choose at-least-once and then dedupe.

Dedupe by event ID
  • Every event carries an ID; seen before → drop, else send
  • The caller mints the ID once per real event, so its retries reuse it (an idempotency key)
  • Check-then-add races: two workers both pass the check. Claim atomically: SET notif:e5 sending NX EX 60, then mark sent for ~a day
Dedupe still leaks
  • Crash between send and "mark sent" → the claim expires → the retry is a duplicate
  • The seen-set must expire, or it grows forever
  • So duplicates are rare, not impossible

Retry, drop, or dead-letter

FailureKindDo this
Timeout · 5xx · 429 Too Many RequestsTransientRetry: back on the queue, exponential backoff + jitter, respect Retry-After
410 Unregistered · invalid number · hard bouncePermanentDrop + clean up the bad token / number / address
Still failing on attempt 5 of 5Out of retriesDead-letter queue + alert developers (the book: alert if it persists)
  • Our quests use a limit of 5 attempts (first send + up to 4 retries). The book just says "a set number": any small, fixed limit works.
  • Backoff: each wait doubles (1 s, 2 s, 4 s…, capped). Jitter: wait a random time up to that, so 1,000 failures don't all come back in the same instant and knock the recovering provider over again.

Watch the queue

Book's metric: total notifications waiting in the queue. Growing → workers can't keep up → add workers. Rule: workers × per-worker rate ≥ arrival rate (e.g. 300 emails/s ÷ 20 per worker = 15 workers).
Two refinements
  • Alert on the age of the oldest message (consumer lag): it says how late users actually are
  • Check the provider's error rate first: if it's throttling you (429s), more workers only make more failed calls. Back off and raise the quota.

"Delayed or reordered is fine, lost is not. Workers log each notification and only ack after the provider accepts, so a crash means a retry, not a loss. Transient failures retry with exponential backoff and jitter up to a limit, then go to a dead-letter queue with an alert; permanent ones like an unregistered token get cleaned up. Exactly-once is impossible, so we're at-least-once with dedupe on a caller-supplied event ID, claimed atomically. And we alert on queue depth and oldest-message age, checking the provider's error rate before adding workers."

10.4 Respect the inbox Quest 10.4 →

🧩 Templates
  • A pre-written message with parameters, e.g. [ITEM NAME], [DATE], plus a CTA
  • Book's wins: consistent format, fewer errors, time saved
  • Validate every parameter (present + right shape) before enqueueing; hot templates live in the cache
🔕 Notification settings
  • Table: user_id bigint, channel varchar, opt_in boolean
  • Check before any send: the server reads it with the user's info, so opted-out events never reach a queue
⏱️ Rate limiting (per user)
  • Cap how many notifications one user gets
  • Why: send too often and users switch notifications off entirely
  • Reuse Ch. 4: token bucket / sliding window keyed by user_id (+ channel)
  • Exempt critical messages (login alerts, one-time codes)
🔐 Security
  • Push APIs need an appKey + appSecret: only verified clients send
  • Callers sign requests with the secret; rotate secrets, reject revoked ones
  • Auth + rate limiting sit on the notification servers, before anything is queued

Events tracking → analytics service

start→pending→sent→delivered→click→unsubscribe

  • Click rate = clicked ÷ delivered (380 / 9,500 = 4%)
  • Unsubscribe rate = unsubscribed ÷ delivered (25 / 9,500 ≈ 0.26%): small, but watch the trend

Caveats: real settings are per category × channel, and transactional messages (password resets, receipts) usually ignore marketing opt-outs. Law applies: CAN-SPAM needs a working unsubscribe honoured within 10 business days; EU rules generally need consent for marketing. Providers also rate-limit you.

"Five extras. Auth: only verified clients with an appKey and appSecret call the send API. Settings: check the user opted in to that channel before queueing. Rate limiting per user so we don't annoy people into turning us off, with critical alerts exempt. Templates for consistency, with parameters validated. And tracking: pending, sent, delivered or error, click, unsubscribe, into an analytics service, while we monitor queue depth. Auth and rate limits sit on the notification servers so bad traffic dies before it's queued."

Good "next steps" for the wrap-up (only after the five basics): priority queues for transactional messages · multi-provider failover · a dead-letter queue · replicated queues · token hygiene (prune 410 / UNREGISTERED). Skip slogans like "more microservices" or "rewrite it in Rust".

"Scope: push, SMS and email, soft real-time, iOS, Android and desktop, triggered by services or schedules, opt-out respected, about 10M pushes, 1M SMS and 5M emails a day. We collect tokens, phone and email at install and signup. Services call an authenticated, rate-limited API on stateless notification servers that check opt-in, fill a template, look up tokens in cache or DB and enqueue on one queue per channel. Workers log each notification, call APNs, FCM, SMS or email providers, retry with backoff and alert on persistent failure. Nothing is lost though it may be late; exactly-once is impossible, so we dedupe by event ID. We watch queue depth and track sent, delivered, clicked and unsubscribed."

Honest caveats (beyond the book)

  • Phone numbers are strings in E.164 form, not the book's integer column.
  • Ack after send (or write the log before acking); otherwise a crash loses the only copy.
  • Dedupe leaks: check-then-add races need an atomic claim, and a crash between send and "mark sent" still yields a duplicate. Product "exactly-once" (SQS FIFO's 5-minute dedupe window, Kafka transactions) never covers a call out to APNs.
  • "Delivered" and "opened" are soft signals: an APNs success means "accepted", not "seen"; email opens come from tracking pixels that Apple Mail Privacy Protection loads automatically.
  • Real provider auth differs from appKey/appSecret: APNs uses a .p8-signed JWT or a TLS certificate, FCM HTTP v1 uses short-lived OAuth 2 tokens; internal callers often use mutual TLS.
  • Never lost stops at the provider: once APNs or FCM accepts, a long-offline device may only get the latest notification, or none if it expires.
  • Provider names are the book's examples (Nexmo is now Vonage), not endorsements.
