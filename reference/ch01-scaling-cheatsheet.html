1.1 One box wonder: single server → DB split → load balancer Quest 1.1 →

api.mysite.com→ DNS →15.125.23.214→HTTP request→HTML (browser) / JSON (mobile)
  • DNS is usually a paid third-party service, not something you host. It turns the name into an IP.
  • Split the tiers: a web tier (requests) and a data tier (storage) on separate servers, so each can scale on its own.
Relational (SQL) = the default
Tables, rows, joins; 40+ years of tooling. MySQL, Oracle, PostgreSQL.
NoSQL when you need…
  1. super-low latency
  2. unstructured data / no relationships
  3. only to serialize and deserialize (JSON, XML, YAML)
  4. to store a massive amount of data
4 NoSQL families
  • Key-value: DynamoDB
  • Graph: Neo4j
  • Column: Cassandra, HBase
  • Document: CouchDB
Usually no joins.
Scale up (vertical)Scale out (horizontal)
HowBigger box: more CPU, RAMMore boxes in a pool
GoodSimple; fine while traffic is lowNo hard ceiling; survives losing a box
BadHard hardware ceiling; no failover (one box = SPOF)Needs something to spread the traffic → load balancer
⚖️ Load balancer
  • Users connect to its public IP (88.88.88.1)
  • Web servers get private IPs (10.0.0.1, 10.0.0.2): reachable only inside the network, safer
  • Server 1 dies → traffic goes to server 2
  • Traffic grows → add a server to the pool
What's still fragile
  • The database: still one box → Quest 1.2
  • The LB itself: real setups run a redundant pair or a managed cloud LB

"Today DNS hands out one IP and one box does everything. First I move the database to its own server, relational by default. Scaling up has a ceiling and no failover, so next I scale out: a load balancer on a public IP in front of web servers on private IPs. Lose one and traffic shifts; grow and I add one. The database is now the single point of failure."

1.2 Copy the ledger: database replication Quest 1.2 →

The rules
  • Master (primary) takes every write: INSERT, UPDATE, DELETE
  • Slaves (replicas) get a copy and serve reads only
  • Reads far outnumber writes → more replicas than masters
Three wins
  • Performance: reads run in parallel on many replicas
  • Reliability: a server destroyed (typhoon, earthquake) → data survives elsewhere
  • Availability: one DB offline → the site keeps answering from another
What diesWhat happens
The only replicaReads go to the master temporarily; a new replica replaces it
One of several replicasReads move to the other replicas; replace the dead one
The masterPromote a replica to master, add a new replica. Caveat: the promoted one may lag → missing writes patched with data recovery scripts; multi-master / circular replication help but are out of scope
1 DNS → LB's IP→2 connect to LB→3 LB → server 1 or 2→4 reads ← replica·5 writes → master
  • Replication lag also breaks read-your-writes: right after a user posts, send their reads to the master for a short while.
  • Replication scales reads, not writes. Writes outgrowing one master → sharding (1.5).

"One primary takes writes, several replicas serve reads, so the read load spreads and the data lives in more than one place. A replica dies: its reads move elsewhere and we replace it. The primary dies: promote the most up-to-date replica and add a new one, knowing lag can cost the last few writes."

1.3 Hot memory, near edge: cache tier + CDN Quest 1.3 →

web server→ get(key) →cachehit → return · miss ↓query DB→set(key, value, ttl)→return

The book calls this read-through; most engineers call it cache-aside. Memcached / Redis sit in their own tier between web servers and the DB.

Five cache questions
  1. When: read often, changed rarely; RAM is volatile, so never the only copy
  2. Expiry: too short → DB hammered; too long → stale
  3. Consistency: DB + cache writes aren't one transaction; harder across regions
  4. Failures: one cache server = SPOF → several nodes across DCs, overprovision memory
  5. Eviction: LRU (most popular), LFU, FIFO
CDN fetch flow (6 steps)
  1. User asks for image.png via a CDN URL
  2. Edge misses → asks the origin (web server or S3)
  3. Origin returns it, maybe with a TTL header
  4. Edge caches it and serves the user
  5. Another user asks the same edge
  6. Served from the edge while the TTL is valid
Four CDN considerations
  • Cost: third party charges per byte; don't cache rarely-read files
  • Expiry: pick it per content type
  • Fallback: CDN down → clients fetch from the origin
  • Invalidate early: vendor API, or version the URL (image.png?v=2)
  • Versioning in practice: many CDNs drop the query string from the cache key, so teams put a content hash in the file name (app.3f9a1c.js).
  • Thundering herd: a hot key expiring or a cache node dying can stampede the DB; coalesce refills, jitter TTLs.

"A cache tier for hot reads: check the cache, on a miss read the DB and store it with a TTL, LRU eviction, several nodes with spare memory so one failure doesn't flood the DB. A CDN for static files: the nearest edge serves them, fetching from the origin on a miss; I'd plan for cost, a fallback to the origin, and versioned asset URLs."

1.4 Forget me, find me anywhere: stateless tier + data centers Quest 1.4 →

Stateful web tierStateless web tier
Session livesIn one server's memoryIn a shared store (RDBMS, Memcached/Redis, or NoSQL; the book picks NoSQL, easy to scale)
RoutingSame user → same server (sticky sessions)Any server can serve any request
CostLB overhead; adding/removing servers is hard; a dead server logs users outSimpler, more robust; enables autoscaling
🌍 GeoDNS
Answers each user with the nearest DC's IP: x% to US-East, (100 − x)% to US-West. Each DC has its own LB, web servers, cache, DB. A DC fails → 100% to the healthy one, so each DC needs headroom.
Three multi-DC challenges
  1. Traffic redirection: GeoDNS to the nearest DC
  2. Data sync: replicate across DCs (Netflix: asynchronous) or failover lands users where their data isn't
  3. Test & deploy: test from several locations; automated deploys keep every DC on one version
  • DNS failover isn't instant: resolvers cache answers for the record's TTL; keep it short, or use anycast / global LBs.
  • Async = lag: a failover can lose the last few seconds of writes. Writes in both DCs to the same data can conflict.
  • Autoscaling thrash: keep a gap between add/remove thresholds and a cooldown.

"First I make the web tier stateless: sessions move to a shared store, so any server can answer and the tier can autoscale; sticky sessions are only a stopgap. Then a second data center behind GeoDNS: users go to the nearest one, and all traffic fails over to the healthy one. The hard parts are syncing data across DCs, usually asynchronously, and deploying the same version everywhere."

1.5 Queues, gauges & shards Quest 1.5 →

web servers (producers / publishers)→ publish →message queue→ consume →workers (consumers / subscribers)
  • A durable buffer for asynchronous work. Photo example: upload → "apply filters to #812" job → workers crop, sharpen, blur in the background.
  • Decoupled: workers down → jobs wait; producers keep going. Scale workers on queue depth.
📊 Logs, metrics, automation
  • Logging: ship error logs to one central service
  • Metrics, 3 levels: host (CPU, memory, disk I/O) · aggregated (whole DB tier, cache tier) · key business (DAU, retention, revenue)
  • Automation: CI checks every commit; automate build, test, deploy
DB scale-up runs out
  • Goes far: RDS with 24 TB RAM; Stack Overflow 2013, 10M+ monthly uniques, one master
  • But: hardware ceiling · single point of failure · cost
🧩 Sharding
  • Split one DB into shards: same schema, different rows
  • Sharding key picks the shard: user_id % 4
  • Choose a key that spreads data evenly
  • Move some non-relational data to NoSQL
Sharding headacheWhyFix
ReshardingFast growth, or shard exhaustion (uneven data fills some shards first). % 4 → % 5 moves ~80% of rowsUpdate the shard function, move data; consistent hashing moves only ~1/n
Celebrity / hotspot keyOne shard gets the stars' traffic and meltsA shard per celebrity (maybe split further)
JoinsTables on different servers can't be joined by the DBDe-normalize (copy author_name into posts) so one shard answers

"Slow work like image filters goes on a queue: web servers publish jobs and return, workers consume them and scale on queue depth. I add central logs, host/tier/business metrics and CI/CD. When the primary runs out of room, scaling up hits a ceiling, stays a SPOF and gets expensive, so I shard by an evenly spread key like user_id, planning for resharding with consistent hashing, hot-key shards and de-normalized data to avoid cross-shard joins."

Millions and beyond: the eight rules

  1. Keep the web tier stateless
  2. Build redundancy into every tier
  3. Cache data as much as you can
  4. Support multiple data centers
  1. Serve static assets from a CDN
  2. Scale the data tier by sharding
  3. Split tiers into separate services
  4. Monitor everything and automate

"I grow it in response to pain. Database on its own server; a load balancer in front of stateless web servers with sessions in a shared store; a master with read replicas; a cache for hot reads and a CDN for static files; a second data center behind GeoDNS with replicated data; a queue for slow work; logs, metrics and automation throughout; and sharding by user_id when the primary runs out of room. Redundancy at every tier, and no box before the traffic needs it."

Honest caveats (where the book simplifies)

  • The order is flexible. Many teams start with a managed LB and a CDN on day one because they're cheap, and put off a second region for years because it's costly and complex.
  • Scaling up is underrated. One big database goes much further than people expect (Stack Overflow 2013), so sharding is a last resort, not a milestone. The 24 TB and 2013 figures are dated; check current instance sizes.
  • The IPs are illustrative. 15.125.23.214, 88.88.88.1 and 10.0.0.x come from the book's figures; the x% split and DC names are placeholders too.
  • Failover is more than "promote a replica". Detect the failure reliably, fence the old master (avoid split brain), repoint clients. Async replication means a promoted replica can miss acknowledged writes.
  • "Read-through" is usually called cache-aside, and invalidation on write (update DB, delete key) still races; keep TTLs as a safety net.
  • Queues "in memory" is a simplification. Kafka, RabbitMQ (durable) and SQS persist messages and deliver at least once; make workers idempotent.
  • user_id % N is a teaching example. Production uses consistent hashing, range or directory sharding. A write-hot key may also need salting.
  • SQL vs NoSQL is blurrier today. PostgreSQL indexes JSON; Spanner and CockroachDB scale SQL out. Pick by access pattern and consistency, not label.
  • "Split into services" pays off mostly for team independence, not raw scale, and adds network calls and deploys.
  • Our numbers vs the book's. The ~10 : 1 read ratio, user counts at each alarm, and all sim latencies and prices are ours.
