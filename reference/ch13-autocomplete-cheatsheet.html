13.1 Every keystroke counts: scope, numbers, first sketch Quest 13.1 →

Functional (ask first)
  • Match the start of a query only: peak never suggests twin peak
  • Return 5 suggestions
  • Rank by historical query frequency
  • No spell check or autocorrect
  • English, lowercase a–z, no special characters
  • 10 million DAU
Non-functional
  • Fast: within ~100 ms, before the next key
  • Relevant: related to the prefix
  • Sorted: by the popularity model
  • Scalable: tens of thousands of QPS
  • Highly available: up when parts are offline, slow or erroring

Envelope math

QuantityWorkingResult
Requests per searcha request per character, ~20 characters~20
Average QPS10,000,000 × 10 × 20 ÷ 86,400 (≈ 23,150, round up)~24,000
Peak QPS2 × average~48,000
New storage10,000,000 × 10 × 20 bytes = 2 GB; 20% new0.4 GB / day

First sketch: two services + one table

Data gathering service
Collects queries and keeps a running count per query in a frequency table (query, frequency).
Query service
Given a prefix, returns the 5 most frequent queries that start with it.
SELECT * FROM frequency_table
WHERE query LIKE 'tw%'
ORDER BY frequency DESC
LIMIT 5;
  • twitter35
  • twitch29
  • twilight25
  • twin peak21
  • twitch prime18

Fine while the data is small. At scale, every keystroke scans the matching rows and sorts them all, about 48,000 times a second at peak, while ~1,160 finished searches a second write to the same table. An index on query helps find 'tw%' rows but not the sort. Verdict: the database becomes the bottleneck.

"Prefix-only, top 5 by historical frequency, English lowercase, no spell check, 10 million DAU, under 100 ms. A request per keystroke gives about 24,000 QPS, 48,000 at peak, and 0.4 GB of new data a day, so this is a read problem. A frequency table with LIKE 'prefix%' works for a demo but sorts on every keystroke; I'll replace it with a trie."

13.2 Grow the trie: top-k in one hop Quest 13.2 →

Naive top-k (p = prefix length, c = nodes under it)
  1. Find the prefix node: O(p)
  2. Walk its subtree for queries: O(c)
  3. Sort, keep k: O(c log c)
Worst for short prefixes: one letter = huge c. Book example: be, k = 2 → best 35, bet 29.
Two tricks → O(1)
  • Cap the prefix (~50 chars): finding the node is bounded
  • Cache the top k at every node (k = 5–10): no walk, no sort
Node tw simply stores [twitter, twitch, twilight, twin peak, twitch prime].
The bill: space + ripples
  • A query of length L sits in up to L + 1 cached lists (each prefix + root)
  • beer 10 → 30 changes the lists on root, b, be, bee, beer
  • So the book rebuilds in batches (13.3)

"A trie's root is the empty string and every node is a prefix; query nodes carry a frequency. Naive top-k is O(p) + O(c) + O(c log c), awful for one-letter prefixes. I cap the prefix at about 50 and cache the top k on every node, so lookup is O(1), bounded by the cap. The price is memory, since each query is copied into up to L + 1 lists, and updates ripple to every ancestor."

13.3 The weekly harvest: data gathering service Quest 13.3 →

Analytics logs→Aggregators→Aggregated data→Workers→Trie DB→Trie Cache
PartWhat it does
Analytics logsRaw (query, time) rows. Append-only, not indexed: cheap to write, read only in bulk.
AggregatorsRoll raw rows into counts per period. Weekly is enough for most autocomplete; a Twitter-style product needs short intervals.
Aggregated data(query, time = week start, frequency), e.g. tree, 2019-10-01, 12,000.
WorkersAsync jobs on a schedule: build the trie (with top-k per node) from the aggregated data.
Trie DBDurable copy. Document store: serialize a weekly snapshot (e.g. MongoDB). Key-value store: each prefix is a key, its node data (top-k list) the value.
Trie CacheDistributed in-memory copy for reads; takes a weekly snapshot of the Trie DB.
Why not update on every search?
  • Billions of searches a day → constant writes that slow the reads
  • The top suggestions barely change once the trie is built
Update: swap, don't patch
  • Book's choice: build a new trie each week, swap it in
  • Patch a node in place: slow, because every ancestor's cached list may change (beer 10 → 30 = 5 rewrites); OK only for a small trie
  • Swap needs room for two tries during the switch

"Searches are appended to analytics logs, aggregators roll them into weekly (query, week, frequency) rows, and workers rebuild the trie from those into the Trie DB, either as a document snapshot or as prefix → top-k rows in a key-value store. The Trie Cache loads the weekly snapshot and serves reads. I don't write live: the write volume would slow reads and the top 5 barely moves. Updates are a weekly build-and-swap, since patching ripples up through every ancestor."

13.4 Faster than a keystroke: query service Quest 13.4 →

Browser→Load balancer→API servers→Filter layer→Trie Cachemiss →Trie DB→ replenish cache

A cache hit is one lookup: the node already holds its top 5. The Trie DB is read only on a miss (a cache server ran out of memory or restarted), and the answer is written back into the cache.

TrickHowCost / caveat
AJAXRequest in the background; only the dropdown updates, no page reloadStill one request per keystroke
Browser cachingCache-Control: private, max-age=3600: only this user's browser stores it, fresh for 1 hourA removed suggestion can linger up to an hour; the Google header is a dated snapshot
Data samplingLog 1 in every N requests; multiply counts by N (N = 10 → 10M of 100M searches a day logged)Top rankings survive; the rare long tail gets noisy or vanishes
Filter layerSits in front of the Trie Cache; drops hateful, violent, explicit or dangerous suggestions by rule, right awayPair it with an async delete from the DB so the next weekly build is clean

"The browser sends an AJAX request per keystroke to a load balancer and an API server, which reads the prefix's top 5 from the Trie Cache through a filter layer. On a miss we read the Trie DB and replenish the cache. Responses carry Cache-Control: private, max-age=3600, so repeats within the hour never reach us; we log 1 in N searches to keep logging cheap; and harmful suggestions are filtered at once and deleted from the DB asynchronously."

13.5 Split the alphabet: scaling + follow-ups Quest 13.5 →

ServersBook's split
2a–m · n–z
3a–i · j–r · s–z
26one per first letter: the ceiling for first-level sharding
> 26shard on the 2nd or 3rd letter: aa–ag · ah–an · ao–au · av–az
Uneven letters → shard map manager
Far more words start with c or s than x. Use historical data to draw boundaries and keep them in a lookup database: e.g. s alone on one shard, u–z together on another. Every read and write asks the map first (cache and replicate it).
🌍 Other languages
Store Unicode characters in trie nodes; children in a map, not a fixed array of 26. UTF-8 is 1–4 bytes per character, so 20 bytes per query holds only for plain English.
🗺️ Country-specific results
A trie per country, stored on CDNs near users for response time. Cost: storage × countries.
📈 Trending, real-time
Weekly workers aren't due yet, and a full rebuild is too slow. Ideas: shard to shrink the working set, weight recent searches more, treat data as a stream (Kafka, Spark Streaming, Storm, Hadoop MapReduce).

"I'd shard by first letter, up to 26 servers, then by second or third letter. Letters are lopsided, so a shard map manager draws boundaries from historical traffic, like 's' alone versus 'u' through 'z'. For other languages I'd store Unicode in the nodes; for countries, a trie per country on CDNs; for trending, shrink rebuilds by sharding, weight recent queries, and move to a streaming pipeline."

"Scope: prefix-only, top 5 by historical frequency, English lowercase, 10 million DAU, under 100 ms; about 24,000 QPS, 48,000 at peak, 0.4 GB of new data a day. The SQL table sorts on every keystroke, so I use a trie with a capped prefix and the top k cached at every node. Writes are offline: logs, aggregators, workers rebuild the trie weekly into the Trie DB, and the Trie Cache keeps a snapshot. Reads: AJAX plus a one-hour browser cache, load balancer, API servers, filter layer, Trie Cache, falling back to the Trie DB on a miss. I sample logs, shard by prefix with a shard map manager, and would add Unicode, per-country tries on CDNs and a streaming path for trends."

Honest caveats (where the book simplifies)

  • "O(1)" means bounded. Finding the node is O(p); it counts as constant only because p is capped at ~50. Say "bounded by the max prefix length" if pushed.
  • Debouncing lowers real QPS. One request per keystroke is a pessimistic upper bound; real clients wait for a short pause in typing. And 23,150 rounds to "~24,000": say you rounded.
  • Weekly is an example interval. Big search engines refresh far more often and run a separate fresh/trending path that they blend with the batch trie.
  • Staleness adds up. Weekly rebuild + a one-hour browser cache = suggestions up to a week (plus an hour) old. A removed suggestion can linger in a browser for up to max-age.
  • The Google header is a dated snapshot. private, max-age=3600 is what the book observed; quote the technique, not the value.
  • Sampling loses the long tail. Fine for top 5 by popularity; wrong for anything needing exact counts.
  • 26 children isn't enough. The book's own queries contain spaces (twin peak); real tries keep children in a map. A cached trie is really a prefix → top-k table.
  • Cold caches. When a new weekly snapshot lands, warm the cache before switching traffic (general practice, not from the book).
  • Ranking is more than counts. Personalization, freshness and location are strong wrap-up mentions; don't build them unasked.
