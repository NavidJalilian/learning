8.1 Scope, napkin math & API Quest 8.1 →

Requirements (ask, don't assume)
  • Example: long URL → tinyurl.com/y7keocwj; a click redirects to the original
  • 100 million new URLs a day
  • Code as short as possible, using 0-9 a-z A-Z (62 chars)
  • No delete, no update (keeps it simple)
Use cases
  • Shorten: long URL in → short URL out
  • Redirect: short URL in → browser sent to the long URL
Non-functional
  • High availability, scalability, fault tolerance
Two endpoints (REST)
  • POST api/v1/data/shorten body {longUrl} → returns the short URL. POST because it creates.
  • GET api/v1/{shortUrl} → HTTP redirect to the long URL. In production it sits at the domain root.

301 vs 302: the redirect choice

CodeBrowserOur loadAnalyticsPick when
301 Moved PermanentlyCaches it; repeat clicks skip usLowerOnly the first click per browserLoad matters, stats don't
302 FoundAsks us every timeHigherEvery click (rate, source, country)Click analytics, destination may change

Both carry the long URL in the Location response header; the browser follows it on its own.

Caveats: "301 = no analytics" is the book's simplification. Bitly and others send 301 and still count clicks, since browsers don't cache a 301 forever and every new visitor's first click reaches the shortener. 307/308 are the method-preserving twins of 302/301; mention them only if asked. 36.5 TB is a floor: add codes, IDs, indexes and ×3 replication. 10 : 1 is an assumption; real shorteners are far more read-heavy.

"Before drawing anything: 100M new URLs a day is about 1,160 writes a second, and at 10 : 1 about 11,600 reads. Over 10 years that's 365 billion rows, about 36.5 TB. Two endpoints: POST to shorten, GET on the code to redirect. 302 if we want every click for analytics, 301 if we'd rather browsers cache it and spare our servers."

8.2 Data model, code length & hashing Quest 8.2 →

365 billion rows won't fit in one server's in-memory hash table (a 256 GB box fills in under a month), so the mapping lives in a relational table:

id (PK)shortURLlongURL
2009215674938zn9edcuhttps://en.wikipedia.org/wiki/Systems_design

Redirects look rows up by shortURL, so it needs an index. createdAt, userId, clickCount are wrap-up extras, not core.

How many characters? Smallest n with 62n ≥ 365 billion

n62nvs 365B
5916,132,832 (~916M)too few
656,800,235,584 (~56.8B)too few (~16%)
73,521,614,606,208 (~3.52T)enough, ~9.6× headroom
8218,340,105,584,896 (~218T)needed at 10× traffic

Drop upper case (36 chars): 367 ≈ 78.4B is too few, so you'd need 8. A bigger alphabet buys a shorter code.

Approach A: hash + collision resolution

Hash lengths (of …/wiki/Systems_design)
  • CRC32: 8 hex · 5cb54054
  • MD5: 32 hex · 5a62509a84df…
  • SHA-1: 40 hex · 0eeae7916c06…
All longer than 7, so keep the first 7.
Collision loop
  1. Hash the long URL, keep 7 chars
  2. Code already in the DB?
  3. Yes → append a predefined string to the input, hash again
  4. No → save the row (original long URL)
Cost: one DB lookup per try; avg tries ≈ 1 / (1 − fraction full).
Bloom filter in front of the DB
  • Bit array + k hash functions
  • Any bit 0 → definitely not taken → skip the DB
  • All bits 1 → maybe → ask the DB
  • False positives yes, false negatives never
  • Can't delete items; fine, links are never deleted

Caveats: the "first 7 hex characters" shortcut gives only 167 ≈ 268 million codes, about 2.7 days of traffic. Take ~42 bits of the hash and write them in base 62 instead. At year ten ~10% of 627 is used, so about 1 insert in 10 collides on its first try. A Bloom filter at 1% false positives needs ~9.6 bits per item: ~440 GB for 365B codes. Two writers can both see "free": a unique index on shortURL settles the race.

"62 to the 6th is about 56.8 billion, short of 365 billion; 62 to the 7th is about 3.5 trillion, so 7 characters. Hashing the long URL and keeping 7 characters collides, so on a clash I append a fixed string and rehash. Each check is a DB lookup, so a Bloom filter in front answers 'definitely not taken' from memory."

8.3 Base 62 conversion Quest 8.3 →

Give each new URL a unique ID, then write that number in base 62. Place values: 1, 62, 3,844 (62²), 238,328 (62³)…

0–9 → 0–9a–z → 10–35A–Z → 36–61
Encode 11157 (divide by 62, keep remainders)
  • 11157 ÷ 62 = 179 r 59 → X
  • 179 ÷ 62 = 2 r 55 → T
  • 2 ÷ 62 = 0 r 2 → 2
Read last to first: 2TX. Check: 2·62² + 55·62 + 59 = 11157.
Decode = multiply each char's value by its place value and add.
  • 10 → 62 · zz → 2,205
  • Book's flow: ID 2009215674938 → zn9edcu
  • One-to-one: unique ID ⇒ unique code ⇒ no collisions

Hash vs base 62

Hash + collision resolutionBase 62 conversion
LengthFixed (7)Grows with the ID
ID generatorNot neededNeeded (Ch. 7)
CollisionsPossible → check + retryImpossible (unique IDs)
Next code guessable?NoYes, if IDs go up by 1 → scramble

The book picks base 62 for its deep dive. With a counter at 100M/day: 5 chars cover the first ~916M links, the 7th char appears around day 568 (62⁶), and the 8th only after ~96 years (62⁷).

Caveats: a 64-bit Snowflake ID (Ch. 7) encodes to 11 chars, not 7; keep IDs counter-sized (ticket server, or pre-allocated ID ranges per server). Sequential codes can be walked: scramble the ID with a keyed reversible function (or use random IDs) and rate-limit lookups. A toy multiply-and-add scramble isn't encryption. Researchers in 2016 scanned shortener code spaces and found private cloud documents and revealing map links. Unique IDs don't dedupe long URLs on their own; the flow's lookup step does.

"I'd base-62 encode a unique ID: 11157 becomes 2TX. IDs are unique, so there are no collisions and no retry loop. I give up fixed length and depend on an ID generator, and counting IDs make the next code guessable, so I'd scramble the ID before encoding and rate-limit the redirect path."

8.4 The two flows & scaling Quest 8.4 →

Shortening flow (6 steps)
  1. Long URL comes in
  2. Is the long URL already in the DB?
  3. Yes → return its existing short URL
  4. No → get a new ID from the unique ID generator
  5. ID → base 62 → short URL
  6. Save row (id, shortURL, longURL), return it
Step 2 makes shortening idempotent: same long URL, same code.
Redirect flow (5 steps)
  1. User clicks the short URL
  2. Load balancer → a web server
  3. Cache hit (shortURL → longURL)? Use it
  4. Miss → read the DB (fill the cache). Not in DB either → 404, an invalid short URL
  5. Return the long URL as a 301/302 redirect
Cache because reads are 10× writes and a few hot links get most clicks.
Wrap-up talking points
  • Rate limiter (Ch. 4): stop floods of shorten requests, by IP or other rules
  • Web tier: stateless, so add/remove servers freely
  • Database: replication (failover, read scale) + sharding
  • Analytics: log every click (when, where, referrer)
  • Availability, consistency, reliability (Ch. 1)

Caveats: step 2 is a lookup by long URL on every shorten, so it needs an index, usually on a fixed-size hash of the long URL (a unique constraint on it also closes the two-writers race). Shard by short URL and redirects hit one shard, but the step-2 index must be sharded on the long-URL hash or the check asks every shard. Async replicas can briefly 404 a brand-new link: read your own writes from the primary or write the new mapping into the cache. Cache sizing isn't in the book; ~20% of ~1B daily reads is a few tens of GB. Links never change, so cached entries never go stale.

"To shorten, I check whether the long URL exists; if not, I take a new ID, base-62 encode it and store the row. A click goes LB → stateless web server → cache → DB, with a 404 for unknown codes, then a 301 or 302. To scale: rate limiter, more web servers, DB replicas and sharding by code, and a click-analytics pipeline."
