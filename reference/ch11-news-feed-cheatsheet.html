11.1 Two rivers: scope, APIs, both flows Quest 11.1 →

A news feed is the constantly updating list of posts on your home page (Facebook feed, Instagram feed, Twitter timeline: same problem). Under the scroll are two separate flows.

✍️ Feed publishing (write)
DNS→LB→Web servers→
  • Post service → post DB + post cache (the permanent copy)
  • Fanout service → pushes the post ID into friends' lists in the news feed cache
  • Notification service → tells friends, sends push notifications
All three hang straight off the web servers, side by side. The fanout service is not behind the post service.
📰 Newsfeed building (read)
LB→Web servers→News feed service→News feed cache
  • The cache holds each user's list of post IDs, not full posts
  • Reading is one lookup: the expensive work happened at publish time
  • Turning IDs into posts = hydration (Quest 11.4)
Why each scope answer matters
  • 5,000-friend cap → bounds the copies per post
  • Images + video → media served from a CDN
  • Newest first → no ranking service in v1
  • 10M DAU → sizes the caches and fanout workers
  • Mobile + web → one HTTP API for both

Caveats: real feeds are ranked; the book assumes newest first to keep the design clear, and the fanout + cache skeleton survives ranking (it adds a scoring step). POST isn't safe to retry blindly: real APIs add an idempotency key. The notification service is a black box here; World 10 covers it.

"Two endpoints, both authenticated: POST /v1/me/feed to publish, GET /v1/me/feed to read, with 'me' taken from the token. Publishing: load balancer, web servers, then the post service stores the post, the fanout service pushes its ID into each friend's list in a news feed cache, and the notification service pings friends. Reading: the news feed service returns my precomputed list of IDs. Reads are cheap because the work happened at write time."

11.2 Push, pull, or both Quest 11.2 →

ModelProsCons
Push
fanout on write		Feed is precomputed: opening the app is one fast lookup. Friends see the post in real time.Celebrity problem: one post by an account with millions of followers = millions of writes and minutes of fanout lag. Wasted work on inactive users who never read.
Pull
fanout on read		No wasted work on inactive users. A post is written once, so celebrities are no problem.Slow reads: every feed load gathers and merges many lists, and gets slower the more accounts you follow.
The hybrid (book's answer)
  • Push for the vast majority of users: fast reads
  • Accounts above a follower threshold skip fanout
  • Their followers pull those posts at read time and merge them into the precomputed list, newest first
  • Our toy dial (Quest 11.2): any threshold from ~10k to ~1M followers keeps both the write burst and the read merge small
Plus: consistent hashing
  • The book also suggests it to spread requests and data evenly over cache nodes and ease hotspots
  • Honest limit: a ring spreads many keys, but can't split one very hot key; real systems replicate hot items or cache them locally
Which model?
  • Friends-only, capped at 5,000 → push is bounded and fine
  • Most users small, a few with 50M followers → hybrid
  • Pure pull and feeds take seconds → precompute: hybrid
  • Returning user / lost cache → build it with a pull, then cache

Caveats: the book calls the celebrity case a "hotkey problem"; strictly it's write amplification plus fanout lag. With a strict 5,000-friend cap, push is bounded; it really bites with unlimited followers (Twitter, Instagram, public pages). Twitter described a hybrid like this in 2012 (Redis timelines, big accounts merged at read time). Feeding Frenzy (SIGMOD 2010) chooses push or pull per producer–consumer pair.

"Push by default, because reads vastly outnumber writes and a precomputed feed makes reading one lookup. But push breaks for celebrities: a 50-million-follower page would mean 50 million writes per post, and it wastes work on inactive users. So it's a hybrid: accounts above a follower threshold aren't fanned out, and their posts are pulled at read time and merged in. Consistent hashing spreads the cache load, though it can't split one hot key."

11.3 The fanout factory: publishing deep dive Quest 11.3 →

🚪 Web servers = the bouncers
  • Authentication: only a valid auth_token may publish
  • Rate limiting: a few posts per user per time window stops spam (World 4)
  • Both run before the expensive fanout
⚙️ The five-step fanout workflow
  1. Graph DB: fetch the poster's friend IDs
  2. User cache: load friends' info and filter by settings (muted, audience)
  3. Message queue: enqueue the post ID + filtered friend list
  4. Fanout workers: take jobs off the queue
  5. News feed cache: write <post_id, user_id> into each friend's list
📬 Why a queue in the middle
  • The poster gets "Posted!" fast; workers write in the background
  • Absorbs rush-hour spikes; add workers to drain a backlog
  • A crashed worker's un-acked job is retried
  • Price: friends see it a little later (eventual consistency)
🗂️ IDs only, and a cap
  • Store IDs, not post/user objects: one post lands in hundreds of lists
  • Each list holds a configurable max (say 500); few people scroll further, so misses stay rare
  • 16 B × 500 × 10M ≈ 80 GB vs ≈ 5 TB with full 1 KB posts (illustrative)
  • Scroll past the cap → fall back to the database

Caveats: the list is already keyed by the viewer, so the entry's user_id is best read as the author (needed to hydrate); real systems use a capped Redis list or a time-scored sorted set. Facebook's "graph DB" is TAO, a graph-shaped cache over sharded MySQL. Fanout-time filters go stale (unfriend, audience change, delete), so reads re-check. Queues are at-least-once: make feed writes idempotent (a set keyed by post_id).

"The web server checks the token and rate-limits, then hands the post to the post service, the notification service and the fanout service. Fanout reads friend IDs from the graph DB, filters them with settings from the user cache, and puts the job on a queue so the poster gets a fast reply. Workers write post ID and author ID into each friend's capped list in the news feed cache, IDs only. Big accounts skip this and are pulled at read time."

11.4 Hydrate the feed: retrieval + caches Quest 11.4 →

The six retrieval steps
  1. Phone sends GET /v1/me/feed
  2. Load balancer → a web server
  3. Web server → news feed service
  4. Service reads the user's (post ID, author ID) list from the news feed cache (+ merges in pulled posts from big accounts: hybrid)
  5. Hydrate: multi-get users from the user cache and posts from the post cache; DB on a miss
  6. Fully hydrated feed returns as JSON
💧 Hydration
  • Turn bare IDs into full objects: name, avatar URL, text, media URLs
  • Batch each lookup (multi-get) and run them in parallel
  • Drop posts that were deleted or are no longer visible (unfriend, block)
  • Hydrate only one page (say 20), not the whole list
🌐 Media by CDN
  • The JSON carries image/video URLs only
  • The phone downloads bytes from the nearest CDN edge
  • Big, read-heavy, rarely changed files never touch the web servers

The five cache layers (book)

LayerHoldsExample
📰 News FeedIDs of the posts in each user's feed"last 500 post IDs for Ana"
📝 ContentEvery post's data; popular posts in a hot cachetext + media URLs of p981; a viral post
🕸️ Social GraphFollower and following lists"accounts Bo follows"
❤️ ActionWhether a user liked, replied to or otherwise acted on a post"did Bo like p981?"
🔢 CountersCounts of likes, replies, followers, following…"likes on p981", "Bo's follower count"

Why split: each layer has its own shape, size and change rate, so it can be sized, scaled and evicted on its own. The user cache in the retrieval figure is separate from the five layers. Caveats: like counters at huge scale are often approximate or updated asynchronously (one hot key again). Facebook's real feed (Multifeed) doesn't keep a per-user list: it gathers and ranks recent actions at read time; the book's design is closer to Twitter's timeline cache.

"GET hits a web server, which calls the news feed service. It reads the user's list of post and author IDs from the news feed cache, merges in posts pulled from the few big accounts they follow, then hydrates: one multi-get to the user cache and one to the post cache, DB on a miss, dropping anything deleted or no longer visible, adding like counts and 'you liked this'. It returns JSON with CDN URLs for the media. The cache is five layers: news feed, content with a hot tier, social graph, action, counters."

Honest caveats (beyond the book)

  • Our numbers are illustrative. The book does no estimation here; only 5,000 friends and 10M DAU are its own. The 300 friends, 35k writes/s, 50M followers, 500-entry cap, 80 GB and 5 TB are our assumptions.
  • Real feeds are ranked: candidate generation, then ML scoring (Twitter open-sourced its pipeline), plus ads, de-duplication and cursor paging.
  • Facebook's Multifeed pulls at read time from sharded in-memory leaf servers and ranks; Twitter's timeline service is closer to the book's push + hybrid design.
  • TAO is not a graph database: it's a graph-shaped caching layer over sharded MySQL. "Graph DB" in the book means "a store that's good at friend edges".
  • At-least-once queues need idempotent writes; exactly-once end to end is rarely worth it.
  • Push and pull aren't either/or: rebuilding a lost or long-idle feed is a pull. Push is the fast path; pull is the fallback.
  • "Master–slave" is the book's term; most docs now say leader–follower or primary–replica.
