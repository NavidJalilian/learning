4.1 Why you need one, and where it stands Quest 4.1 →

A rate limiter caps how many requests a client (user, IP address, device, API key) may send in a time window. Over the limit → the request is blocked with 429. A rule = who is counted + how many + per what window. Book examples: 2 posts / second per user · 10 accounts / day per IP · 5 reward claims / week per device.

⛔ Stop resource starvation
A DoS flood (on purpose or by accident) shuts real users out. Almost every big API has limits: Twitter 300 tweets / 3 h, Google Docs 300 reads per user / 60 s.
💸 Cut cost
Fewer excess requests → fewer servers, more room for high-priority APIs. Matters most for paid third-party calls (credit checks, payments, health records).
🔥 Prevent overload
Filter out bots and misbehaving (buggy) clients before they push servers too hard.

Requirements: accurately limit excessive requests · low latency (don't slow HTTP responses) · as little memory as possible · distributed (one count shared by many servers) · exception handling (clear message when throttled) · high fault tolerance (a dead cache server must not take the system down).

Where it stands

SlotVerdictWhy
A · In the clientUnreliableRequests are easy to forge or the app is patched; you may not control the client. A patched app sent 30 / s, all 30 processed.
B · MiddlewareBook's pickSits between clients and API servers; over-limit requests get 429 before reaching any server.

In microservices the middleware is usually the API gateway: a managed front door that also does SSL termination, authentication, IP whitelisting and static content (e.g. AWS API Gateway throttling).

Build or buy: the book's 4 guidelines
  1. Check your tech stack (language efficient enough? cache service?)
  2. Need a specific algorithm? Building gives full control; a third-party gateway may limit the choice
  3. Already run an API gateway (auth, whitelisting)? Add the limiter there
  4. Short on engineers? Buy a commercial gateway
Which OSI layer?
  • The book's limiter works at layer 7 (HTTP): it sees users and endpoints
  • You can also limit by IP at layer 3 with iptables: cheaper per packet, blind to users
  • A 2 Tbps UDP botnet is neither: that needs network-level DDoS protection upstream

"A rate limiter caps requests per client per window, like 2 a second per user, and answers 429 over the limit. It prevents starvation from DoS, cuts cost, and stops bots overloading us. Clients can be forged, so I'd enforce it server-side as middleware, or in the API gateway if we already run one. Build for full control of the algorithm; buy if we're short on people."

Caveats: platform limits (Twitter, Google Docs) are snapshots and change often. Counting by IP lumps together everyone behind one NAT (an office, a mobile carrier); for logged-in traffic count by user ID or API key. Client-side limits are fine as politeness, never as the only guard.

4.2 Token bucket vs leaking bucket Quest 4.2 →

🪙 Token bucket (Amazon, Stripe)
  • Bucket holds up to capacity tokens; a refiller adds tokens at the refill rate; extra tokens overflow and are lost
  • Each request takes 1 token, or is dropped if the bucket is empty
  • Book figure: size 4, refill 4 / minute. A burst of 5 on a full bucket → 4 through, 1 dropped
  • Size = biggest burst · refill rate = long-run average
  • + easy, memory-efficient (2 numbers per bucket), allows short bursts
  • − two parameters that are hard to tune
💧 Leaking bucket (Shopify)
  • A FIFO queue of the requests themselves; full queue → new request dropped
  • Requests leave at a fixed outflow rate
  • Parameters: bucket (queue) size + outflow rate
  • + memory-efficient (fixed queue), stable outflow for fragile downstreams
  • − a burst fills the queue with old requests, so recent ones get limited; also two knobs to tune

Production limiters don't run a timer per bucket. They store tokens left + last refill time and refill lazily on each request:

tokens = min(capacity, tokens + Δt × rate)
if tokens ≥ 1: take one, allow · else: drop

Drill from the quest: capacity 10, refill 2 / s, starts empty, a request every 0.25 s for 3 s → 6 allowed, 6 dropped. Long-run throughput is the refill rate, not the size.

How many buckets? One per rule, per key

Hard vs soft limits (from the wrap-up): hard = requests can never exceed the threshold (contract caps); soft = may exceed it briefly. Bursty user traffic → token bucket; fragile downstream that needs a steady rate → leaking bucket.

"A token bucket holds up to N tokens refilled at a fixed rate; each request spends one or is dropped. Size sets the biggest burst, refill rate the average; it's two numbers per bucket, which is why Amazon and Stripe use it. A leaking bucket is a FIFO queue drained at a fixed rate: smooth output, as at Shopify, but a burst fills it with stale requests. Both have two knobs that are hard to tune."

Caveats: there are two "leaky buckets". The book's is the queue (delays requests). The meter version rejects instead, and is equivalent to a token bucket (GCRA); Shopify's API is meter-style and answers 429 at once. "Amazon uses token bucket" means API Gateway throttling (rate + burst), not every Amazon system.

4.3 Window algorithms Quest 4.3 →

Fixed window counter
  • Timeline cut into windows on the round second / minute; one counter each
  • Counter hits the limit → drop until the next window (book's first picture: 3 per 1-second window)
  • Edge exploit, limit 5 / min: 5 between 2:00:30–2:01:00 + 5 between 2:01:00–2:01:30 → 10 in one rolling minute
  • + tiny memory, easy, quota resets on a boundary (daily plans)
  • − edge bursts can double the quota
Sliding window counter (Cloudflare)
  • Two fixed-window counters per key: this minute + last minute
  • Rolling ≈ current + previous × overlap
  • Book: limit 7 / min, 5 last minute, 3 so far, 30% into the minute → 3 + 5 × 0.7 = 6.5 → round down to 6 < 7 → allow; one more hits the limit
  • + smooths edge spikes, two counters per key
  • − an estimate: assumes last window's requests were evenly spread

Sliding window log (limit 2 / min, Redis sorted set)

Per request: ① drop timestamps older than now − 60 s (ZREMRANGEBYSCORE) ② add the new timestamp (ZADD) ③ accept if log size ≤ limit (ZCARD), else reject.

ArrivesRemovedLog afterSizeVerdict
1:00:01—[1:00:01]1accept
1:00:30—[1:00:01, 1:00:30]2accept
1:00:50—[… 1:00:30, 1:00:50]3reject, but stays logged
1:01:401:00:01, 1:00:30[1:00:50, 1:01:40]2accept

Exact in every rolling window, but memory-hungry: 500 / hour × 1M users × 8 B ≈ 4 GB of bare timestamps (Redis overhead makes it more), and rejects are logged too.

Blind spot of the counter: keep 30% and bunch last minute's 5 requests in its final second: the real count is 5 + 3 = 8 > 7, yet the estimate says allow. In practice it's close: Cloudflare measured 0.003% of 400 million requests wrongly allowed or limited.

"Fixed window is one counter per round minute, cheap, but 5 at the end of one minute and 5 at the start of the next gives 10 in a rolling minute. A sliding log stores every timestamp in a sorted set: exact, but memory per request, rejects included. A sliding window counter estimates current plus previous times the overlap, 3 + 5 × 0.7 = 6.5: two counters per key and Cloudflare saw it wrong on only 0.003% of requests. I'd ship that or a token bucket, and use the log only when it must be exact."

Caveats: rounding is a choice (the book rounds 6.5 down; Cloudflare compares the unrounded rate). 0.003% is one company's traffic mix. Some sliding-log implementations log only accepted requests, saving memory but not penalizing hammering.

4.4 Counters, rules & 429s Quest 4.4 →

Counters live in Redis
  • Not the database: disk is too slow for a check on every request
  • In-memory cache: fast + time-based expiry
  • INCR key: +1 (missing key = 0, so the first INCR returns 1)
  • EXPIRE key 60: Redis deletes the key after 60 s
  • Book flow: read counter → limit reached? reject : forward, increment
⚠ INCR + EXPIRE must be atomic
  • Crash after INCR, before EXPIRE → key has TTL −1, never expires
  • User sits at 5 / 5 and gets 429 for days
  • Fix: one Lua script, or MULTI/EXEC (set TTL when INCR returns 1, inside it)

Rules: Lyft-style YAML, stored on disk

5 marketing messages per day 
domain: messaging
descriptors:
  - key: message_type
    value: marketing
    rate_limit:
      unit: day
      requests_per_unit: 5
5 logins per minute 
domain: auth
descriptors:
  - key: auth_type
    value: login
    rate_limit:
      unit: minute
      requests_per_unit: 5

Lyft's service now lives at envoyproxy/ratelimit, same domain / descriptors / rate_limit layout.

Telling the client: 429 + headers

Header (book's names)Meaning
X-Ratelimit-LimitCalls allowed per time window
X-Ratelimit-RemainingAllowed calls left in this window
X-Ratelimit-Retry-AfterSeconds to wait before calling again without being throttled (sent with the 429)

Worked example (5 per 60-s window from t = 0; requests at 0, 5, 10, 15, 20, 25 s): Remaining 4 → 3 → 2 → 1 → 0, then #6 gets 429 with Retry-After 35. Over-limit requests are dropped, or queued for later (book: orders limited during overload).

Client best practices (book)
  • Cache responses to avoid repeat calls
  • Know the limit; don't send bursts
  • Catch errors so the app recovers gracefully
  • Add enough back-off to retries (+ jitter; honour Retry-After)
Impatient vs polite client (429 at t = 25 s)
  • Retry every 0.5 s: in at 60 s, after 69 wasted calls
  • Wait 35 s + jitter: in at ~62 s, 0 wasted
  • Nobody beats the window

"Rules sit in config files on disk; workers pull them into a cache. A request hits the limiter middleware, which loads its rule from the cache and its counter from Redis, using INCR and EXPIRE in one atomic script. Under the limit it goes to the API servers; over it, the client gets 429 with X-Ratelimit-Limit, -Remaining and -Retry-After, and the request is dropped or queued."

Caveats: X-Ratelimit-* is a habit, not a standard. GitHub sends x-ratelimit-reset as a clock time, not seconds. The standard "wait" header is plain Retry-After; the IETF is drafting RateLimit / RateLimit-Policy. Queue only work that can safely run later, and tell the client it was accepted.

4.5 Many servers, one count Quest 4.5 →

🏁 Race condition
  • Read → check → write as separate steps
  • Counter = 3: requests A and B both read 3, both write 4; it should be 5. Both got in
  • Fixes: Lua script (Redis runs nothing else meanwhile) or Redis sorted set
  • Locks are correct but slow the system down a lot (extra trips + queuing)
🔀 Synchronization
  • Web tier is stateless: a client's calls hit different limiters
  • Local counters, 2 limiters, limit 5 → all 10 get in
  • Sticky sessions: neither scalable nor flexible (one box hot; dies → count lost)
  • Book's fix: centralized store (Redis) shared by all limiters
🌏 Performance
  • Multi-data-center: far users see high latency
  • Route to the nearest edge server (Cloudflare: 194 in 2020)
  • Sync counters with eventual consistency
  • Sydney → Virginia Redis ≈ 196 ms per check; local edge ≈ 5 ms
  • Price: 100 / min global, 100 via Sydney + 100 via Frankfurt before a sync → 200 get in

Monitoring: is the algorithm effective? are the rules effective?

Dashboard saysDo
Normal day, ~30% of valid requests rejected, tickets piling upRules too strict → relax them

Lots of 429s, all to one scraper key, nobody complainingNothing: the limiter is working

When Redis dies

ModeWhat happensGood for
Fail open + alertTraffic flows unlimited; product stays up, protection goneOrdinary endpoints (search, checkout)
Fail closedReject everything; a cache outage becomes a product outageAbuse-prone endpoints (login), or fall back to a strict local limit

"Three things break at scale. A race on read-check-write: make it atomic with a Lua script or a sorted set, since locks are too slow. Synchronization: not sticky sessions, which neither scale nor flex, but one central Redis. Latency: check at edge servers and sync counters eventually, accepting a brief overshoot. Then monitor: too many valid drops means relax the rules, flash-sale bursts mean token bucket. If Redis dies, fail open with an alert, closed for login."

Caveats: fail open vs closed isn't in the book; it follows from "high fault tolerance" (Stripe's limiters fail open). One Redis is a bottleneck and single point of failure: shard and replicate. A plain fixed-window INCR is already atomic; the race appears when you read, decide in code, then write. Cloudflare now lists 300+ cities.

If they ask for numbers (the chapter has no estimation; these inputs are our assumptions): 10M daily users × 2 counters (sliding counter) = 20M keys × ~50–100 B ≈ 1–2 GB of RAM. 10M × 100 calls / day ≈ 1B / day ≈ 12k req/s; at 2× peak and 1–2 Redis ops per call ≈ 25–50k ops/s: a small Redis cluster.

"Server-side limiter with flexible rules, as middleware or in the gateway. Token bucket if bursts are fine, sliding window counter for smooth limits. Counters in Redis with INCR and EXPIRE inside a Lua script; rules in config files that workers cache. Over the limit: 429 with the rate-limit headers, then drop or queue. One central Redis for a shared count, edge servers with eventual sync for far users, monitoring to tune rules, and fail open with an alert if Redis dies."

Honest caveats (where real systems differ from the book)

  • Header names aren't standard. X-Ratelimit-* is a convention; GitHub's x-ratelimit-reset is a clock time. Standard: 429 (RFC 6585) and Retry-After (RFC 9110); the IETF RateLimit headers are still a draft.
  • Leaky bucket: queue vs meter. The book's is a queue that delays; the meter version rejects and equals a token bucket (GCRA). Shopify is meter-style.
  • INCR / EXPIRE atomicity. Two commands can be split by a crash → a key with no TTL locks a user out. Use a Lua script or MULTI/EXEC.
  • Global limits are approximate. Edge counters synced eventually can briefly overshoot (200 through a 100 limit); exact global caps cost a cross-region trip per call. In practice that makes them soft limits.
  • Fail open is a choice, not the book's text. It meets the fault-tolerance requirement; fail closed (or a strict local fallback) for security limits like login.
  • An HTTP limiter isn't DDoS protection. Volumetric floods fill the links first; they need network-level protection upstream.
  • Example numbers age. Twitter / Google Docs limits and Cloudflare's 194 edge sites (2020) are snapshots.
