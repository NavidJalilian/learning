15.1 Scope, napkin math, APIs, one server → many Quest 15.1 →

In scope
  • Add files (drag and drop), download files
  • Sync across devices; see revisions
  • Share with friends, family, coworkers
  • Notify on edit, delete or share
  • Web + mobile, any file type, ≤ 10 GB, encrypted at rest
Out of scope
  • Google Docs-style live co-editing (needs operational transform or CRDTs: a different interview)
  • Anything the interviewer never asked for (a photo editor…)
Non-functional, in priority order
  1. Reliability: data loss is unacceptable
  2. Fast sync · low bandwidth · scalability · high availability

"I'd cover upload, download, sync, revisions, sharing and notifications on web and mobile, files up to 10 GB, encrypted at rest; live co-editing is out. Reliability comes first. 50M users × 10 GB is 500 PB allocated; 10M DAU × 2 uploads is about 240 uploads a second, 480 at peak. Three APIs: simple or resumable upload, download, list revisions, all authenticated over HTTPS."

Metadata cacheHot metadata in memory for fast reads

Offline backup queueHolds changes for offline clients until they reconnect

Block-server pipeline

✂️ split ≤ 4 MB→🗜️ compress→🔒 encrypt→☁️ upload to S3
  • Each block gets a hash (fingerprint of its bytes); hash + order go in the metadata DB. A file = its blocks joined in order.
  • Compress before encrypt: encrypted bytes look random and barely compress. Pick the algorithm by type: gzip/bzip2 for text; photos and video are already compressed.
  • Delta sync: re-hash on change and upload only blocks whose hash changed. Example: 40 MB file = ten 4 MB blocks; edit 2 → send 8 MB (20%).

Caveats: "unique hash" in practice means a cryptographic hash (Dropbox: SHA-256 per 4 MB block). Fixed blocks break on inserts: add one byte at the front and every boundary shifts, so every hash changes. rsync uses a rolling checksum; many tools use content-defined chunking (cut where the content matches a pattern). Delta sync only saves upload bandwidth if the client knows what changed: real Dropbox clients chunk and hash locally. 4 MB is a dial: bigger = fewer metadata rows, coarser deltas.

"Metadata calls go through a load balancer to API servers; file content goes to block servers, which split it into blocks of up to 4 MB, compress then encrypt each, and store them in S3. Hashes and block order live in the metadata DB, so on a change we upload only blocks whose hash changed. That's delta sync: less bandwidth, faster sync."

15.3 Metadata: consistency, schema, conflicts Quest 15.3 →

Strong consistency by default
No two clients may see different versions of a file at once. Caches are eventually consistent by default, so:
  1. Cache replicas stay consistent with the master
  2. Invalidate (delete) the cache entry on every DB write
Why relational
ACID comes built in: atomic, consistent, isolated, durable writes. Most NoSQL stores don't give it by default, so you'd code consistency into the sync logic yourself. Shard it (e.g. by user) to scale.
Sync conflict rule
  • The first version processed wins and becomes the new version
  • The later one gets a conflict: the user sees their local copy + the server's latest
  • They merge, or let one override the other. Nothing is lost silently.

Open revision 3: namespace → file (by path) → file_version (number 3) → blocks ORDER BY block_order → fetch from S3 and join.

Caveats: the schema has no sharing/permissions table even though sharing is in scope: add an ACL table if asked. Invalidate-on-write still has a small race (a reader refills the cache with the old row right after the delete); real systems add versioned entries or leases. "First processed wins" is not merging. At huge scale "relational because ACID" becomes sharded MySQL with layers on top (Dropbox's Edgestore) or Spanner.

"Metadata must be strongly consistent, so I'd use a relational DB for native ACID, shard it by user, and invalidate the cache on every write. Tables: user, device, namespace, file, file_version and block; versions are read-only and each maps to ordered blocks, so any revision can be rebuilt. On concurrent edits the first one processed wins and the other user sees both copies to merge."

15.4 Upload, download & notifications Quest 15.4 →

Upload · lane A: metadata
  1. Client 1 sends the new file's metadata to the API servers
  2. Saved in the metadata DB, status pending
  3. API servers tell the notification service
  4. Notification service tells client 2: "uploading…"
Upload · lane B: content (in parallel)
  1. Client 1 sends the content to block servers
  2. Split, compress, encrypt, store in cloud storage
  3. Cloud storage fires the upload-completion callback to the API servers
  4. Status → uploaded in the metadata DB
  5. API servers tell the notification service
  6. Notification service tells client 2: ready
Download (9 hops)
  1. Notification service → client 2: "something changed"
  2. Client 2 asks API servers for metadata
  3. API servers read the metadata DB
  4. DB returns it to the API servers
  5. Client 2 gets the metadata (the block list)
  6. Client 2 asks block servers for blocks
  7. Block servers fetch them from cloud storage
  8. Cloud storage returns them
  9. Client 2 downloads only new blocks and rebuilds the file

Editing a file runs the same upload flow. Offline client? The change waits in the offline backup queue and syncs when it reconnects.

Long polling vs WebSocket

Long pollingWebSocket
HowClient sends a request; server holds it until news or timeout; client reopens at onceOne persistent connection, both sides send any time
FitsOne-way (server → client), infrequent, no bursts: Drive (Dropbox uses it)Real-time two-way traffic: chat

Caveats: the ping carries no data, only "something changed"; correctness comes from re-reading metadata, so a missed ping delays sync but corrupts nothing. Real clients keep a change cursor ("everything since X?") rather than a literal per-device queue; Dropbox's long poll answers just "changes: true/false". S3 can emit object-created events, but "upload done" means every block of this version is stored, which the server must track. Today WebSocket or SSE is also a fine answer if you give a reason.

"The laptop sends metadata and content in parallel. Metadata lands as pending and the other devices hear a file is coming; when S3's completion callback arrives, the status flips to uploaded and they're pinged again. The phone holds a long poll, because the traffic is one-way and infrequent; on a ping it pulls the metadata, then only the blocks it lacks. Offline devices catch up from the offline backup queue."

15.5 Save storage, survive failures Quest 15.5 →

1 · De-duplicate blocks
Same hash = same block. Store it once per account; files point at it.
2 · Back up intelligently
Cap the number of versions (oldest dropped first) and keep the valuable ones: dense recent history, sparse old. 1,000 versions of a 10-second autosave = only ~2.8 hours back.
3 · Cold storage
Data untouched for months/years → e.g. S3 Glacier. Deep Archive ≈ $0.00099 vs Standard ≈ $0.023 per GB-month (~23× cheaper), but restores take hours.

"What happens when X dies?"

FailureRecovery
Load balancerLBs watch each other with heartbeats; the standby becomes active
Block serverOther block servers pick up its unfinished or pending jobs
Cloud storage (a region)Buckets are replicated across regions; fetch from another
API serverStateless: the LB routes its traffic to the others
Metadata cacheReplicated: read another node, bring up a replacement
Metadata DB masterPromote a replica ("slave") to master, add a new replica
Metadata DB replicaRead from another replica, replace the dead one
Notification server~1M long polls drop; clients reconnect to other servers. Slow: a server can hold many connections but can't accept them all at once
Offline backup queueQueues are replicated; consumers may re-subscribe to the backup queue

Caveats: cross-user dedup saves more but leaks "someone already has this file", and per-user encryption keys make identical files differ, so you'd hash before encrypting. Glacier has a 180-day minimum (Deep Archive) and per-retrieval fees; prices change. Promoting an asynchronously replicated replica can lose the last writes; use semi-sync or a consensus store. Jittered exponential backoff (not in the book) stops a million phones hammering the survivors; it can't beat their accept rate (1M ÷ 30k/s ≥ 33 s in the quest's toy model).

"Three savers: dedup blocks by hash per account, cap versions but keep the valuable recent ones, and move cold data to Glacier, which is far cheaper but takes hours to restore. For reliability every tier has a spare: S3 across regions, a promoted replica for the metadata master, stateless API servers behind a standby LB, replicated caches and queues; a dead notification server means a million slow reconnects, so clients back off with jitter."

Wrap-up trade-offs

Client uploads straight to S3?
  • + Faster: the file travels once, not twice; no block-server fleet
  • − Chunking, compression, encryption rebuilt for every platform (iOS, Android, web): error-prone, costly
  • − Clients can be hacked, so encryption logic there isn't ideal
  • The book keeps block servers.
Presence service
Move online/offline status out of the notification servers into its own service, so other features can reuse it. The book's closing idea.

Also worth a sentence: ACL table for sharing, per-user rate limits, multi-region (hard with a strongly consistent DB).

"Scope: upload, download, sync, revisions, sharing and notifications for 10M daily users, files up to 10 GB, ~240 uploads a second, 500 PB allocated, reliability first. Content goes to block servers that cut 4 MB blocks, compress, encrypt and store them in cross-region S3, with cold storage for old data; metadata goes through a load balancer and stateless API servers to a cached, sharded relational DB. Only changed blocks sync. Uploads are pending until S3's callback; a long-polling notification service pings other devices, and offline ones catch up from a queue. First save wins on conflicts. Dedup, version caps and cold storage cut cost. I'd revisit direct-to-S3 uploads and a presence service."

Honest caveats (where the book simplifies)

  • Quota ≠ usage. 500 PB is promised space; real growth from the book's numbers is ~10 TB/day before replicas and versions.
  • Fixed blocks vs content-defined chunking. One inserted byte shifts every fixed 4 MB block; rsync's rolling checksum and content-defined chunking fix that. The book doesn't cover it.
  • Real Dropbox chunks on the client. It hashes 4 MB blocks locally and uploads only blocks the server lacks, closer to the book's "direct" alternative.
  • Dedup vs encryption and privacy. Cross-user dedup leaks who has which file; per-user keys defeat dedup unless you hash before encrypting.
  • The offline queue is really a change cursor in most sync systems: "give me everything since change X".
  • The schema has no ACLs, though sharing is in scope. Add a permissions table and say the API servers check it.
  • Interview-sized numbers. Real Google Drive serves far more than 50M users.
