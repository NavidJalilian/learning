Quest 4.1 · Design a Rate Limiter

Bouncer at the Door

Every busy API has a bouncer: something that counts how often each client knocks and turns away the ones who knock too fast. Find out why it's there, what to ask before you build one, and where it has to stand.

🎯

Your win today: you can explain in one breath what a rate limiter does, give three reasons to have one, ask the scoping questions, and defend where you'd put it: middleware or the API gateway, not the client.

1

Why bounce anyone?

Three reasons every big API has a limiter

A rate limiter controls how fast a client (a user, an app, another service) may send traffic. On the web that means: at most this many requests in this much time. Requests over the limit are blocked.[1] The book's example rules:

2 / secondA user can write at most 2 posts per second.
10 / day / IPAt most 10 accounts created per day from one IP address.
5 / week / deviceRewards can be claimed at most 5 times a week per device.

Each rule has three parts: who is counted (user, IP address, device), how many, and per what time window. The book gives three reasons to bother:[1]

  • Stop resource starvation. A Denial of Service (DoS) attack floods a service with requests so that real users can't get in. It can be on purpose or by accident. The limiter drops the excess. The book notes that almost every big API has limits, such as Twitter's 300 tweets per 3 hours and Google Docs' default of 300 read requests per user per 60 seconds.
  • Cut cost. Fewer excess requests means fewer servers, and more capacity left for high-priority APIs. It matters most when you pay per call to a third-party API, for example to check credit, make a payment or fetch health records.
  • Prevent overload. Filter out excess requests from bots, or from users (and their buggy apps) behaving badly, so the servers aren't pushed too hard.

Starvation and overload overlap. In this quest, starvation means other users get shut out by a flood. Overload means the servers themselves are strained by bots or misbehaving clients.

    Where does the bouncer stand?

    Client, middleware or server: predict, then watch

    There are three places to put the limiter:[1]

    • A · In the client: the app or browser counts its own requests.
    • B · Middleware: a separate piece that sits between clients and the API servers and turns away excess requests before they reach the servers.
    • C · Inside the API servers: each server checks the limit in its own code.

    When a request is turned away, the answer is HTTP status 429 Too Many Requests. It's the standard code for "you sent too many, slow down".[3]

    Limiter in:

    Rule: 2 requests per second per client.
    Middleware in real life: the API gateway. In cloud setups built from many small services (microservices), the limiter usually lives in an API gateway: a managed front door that also handles SSL termination (decrypting HTTPS), authentication (checking who you are), IP whitelisting (only letting listed addresses in) and serving static files.[1] AWS API Gateway, for example, has throttling built in.[4] Slot C works too, but rejected requests still reach your servers and use a little of their time.

    Which floor of the building?

    Network traffic is often described with the 7-layer OSI model, from cables (layer 1) up to apps (layer 7).[5] A limiter can work at more than one layer. Tap the layer where the book's limiter works. It reads HTTP requests and counts them per user.

    4

    Build it or buy it?

    The book's four guidelines, applied

    Should you write your own limiter as middleware, or use an API gateway? The book says there's no single right answer. It depends on your tech stack, your engineering resources (people and time), your priorities and your goals. It gives four guidelines:[1]

    • ①Check your tech stack. Look at your language and cache service. Is the language efficient enough to do the limiting on the server side?
    • ②Pick the algorithm the business needs. Build it yourself and you control the algorithm fully. A third-party gateway may limit your choice.
    • ③Already have a gateway? Use it. If you run microservices with an API gateway doing auth and IP whitelisting, add the limiter there.
    • ④Short on people? Buy. Building your own takes time. Without enough engineers, a commercial API gateway is the better option.

    Four companies ask for your advice. Pick what they should do and the guideline that backs it, then lock it in. The right call with the wrong reason earns half.

    🎓 Level-up note (for later)

    • The example limits are snapshots. Twitter's 300 tweets per 3 hours and Google Docs' 300 reads per user per minute were real when the book was written. Platform limits change often, so treat them as examples, not current facts.
    • An HTTP limiter doesn't stop a big DDoS. A distributed DoS (DDoS) uses thousands of machines. By the time a request has been read as HTTP, the bandwidth is already used up. Real systems put network-level DDoS protection in front, often at the CDN or network edge.
    • Counting by IP is blunt. Many users can share one public IP address. Offices and mobile carriers do this with NAT (network address translation). Attackers can also switch IPs. When requests are logged in, count by user ID or API key.
    • Client-side limiting still has a place. As politeness it saves wasted calls (the book's wrap-up suggests clients cache results and back off), but never as your only protection.
    • Fail open or fail closed? If the limiter's cache dies, letting traffic through ("fail open") keeps the product up but removes protection. Blocking everything ("fail closed") does the reverse. Quest 4.5, Many Doors, One Count, comes back to this.
