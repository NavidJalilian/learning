1

Same block, stored once

De-duplication, watch the counter

Here's the problem the book raises. To keep version history (every past copy of a file) and to stay safe if a data center burns down, Drive stores many versions of each file in several data centers. Do that for every save of every file and storage fills up fast.[1]

The book gives three ways to save space. Technique 1 is de-duplication ("dedup"): never store the same block twice. Recall from Quest 15.2 that files are cut into blocks of up to 4 MB. Each block gets a hash: a short fingerprint computed from its bytes. The same bytes always give the same hash, and different bytes give a different one. So the rule is simple. If two blocks have the same hash, they're the same block. Store it once, and let both files point at it. The book does this per account: one user's blocks are compared with that user's other blocks.

Honest caveat: why only per account? Dedup across all users would save more. But it leaks information. If an upload finishes instantly, the uploader learns that someone else already has that exact file. That's why many providers limit cross-user dedup. Encryption also gets in the way: if each user's blocks are encrypted with a different key, identical files turn into different bytes. So you have to hash before encrypting, which has its own privacy trade-offs.
2

Keep what matters

Version limits and cold storage, tune the sliders

Technique 2: back up intelligently. The book suggests two moves.[1]

  • Cap the number of versions. Keep at most N versions of a file. When the cap is reached, the oldest version is thrown out to make room for the new one.
  • Keep only valuable versions. Some files are saved constantly. The book's example is a document saved over a thousand times in a short time. Most of those copies are worthless. Keep more of the recent versions and fewer of the old ones, and test to find the right numbers.

Technique 3: move cold data to cold storage. Cold data is data nobody has touched for months or years. Cold storage is a cheaper storage class built for data you almost never read, like Amazon S3 Glacier.[2] Rough list prices in us-east-1: S3 Standard is about $0.023 per GB per month, and Glacier Deep Archive about $0.00099. That's roughly 23× cheaper.[3] The catch: getting a file back from Deep Archive takes hours, not milliseconds.

Pull the plug

Failure handling, chaos board

Interviewers love one follow-up: "What happens when this box dies?" The book answers it for every component in the design.[1] A few words first. A heartbeat is a tiny "I'm alive" message one machine sends another every few seconds. A stateless server keeps no user data between requests, so any copy can answer any request. A replica is a copy of a database or cache that's kept in sync. The book calls the main database the master and its copies slaves.

🌩️ The reconnect storm

Notification server 1 held about 1,000,000 long-poll connections. That's the figure from Dropbox's 2012 talk.[5] Now every one of those phones has to reconnect to the two survivors, and together they can accept about 30,000 new connections a second (a made-up but plausible number).   • ✓Run it with everyone retrying every second
  • ✓Run it with jitter + exponential backoff: each phone waits a random time, and the wait roughly doubles after every failed try
Honest caveat: the fix isn't in the book. The book just says reconnecting is slow. The standard fix, randomised ("jittered") exponential backoff, is well known from AWS's write-up.[6] It can't beat the servers' accept rate, so reconnecting stays slow. What it does is stop a million phones from hammering the survivors with doomed retries. In this toy model, overloaded servers waste CPU turning people away and accept fewer connections. Real servers do the same, and can even fall over.

🎓 Level-up note (for later)

Promoting a replica can lose writes. If the master copied changes to its replicas asynchronously (without waiting for them), the last few writes may never have reached the replica you promote. For metadata that must be strongly consistent, use synchronous or semi-synchronous replication, or a store built on a consensus protocol like Raft, which only confirms a write once a majority has it.

Fixed-size blocks and edits. With fixed 4 MB blocks, inserting one byte near the start of a file shifts every block after it, so they all hash differently and dedup misses. Some systems use content-defined chunking instead: block edges are picked from the content itself, so they move with the data.

Hash collisions. Two different blocks with the same strong hash (like SHA-256) is possible in theory but so unlikely that real systems treat it as never happening.
