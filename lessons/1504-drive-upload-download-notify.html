Two lanes at once

The upload flow, tap-in-order

In Quest 15.2 you met the cast of the high-level design. Quick refresher:[1]

🧱 Block servers split a file into blocks and push them to cloud storage.
☁️ Cloud storage holds the blocks (Amazon S3 in the book).
🖥️ API servers do almost everything except moving bytes: sign-in, profiles, file metadata.
🗄️ Metadata DB stores metadata: data about files (name, size, versions, which blocks).
🔔 Notification service tells clients when something changed.
📥 Offline backup queue holds changes for a device that's offline.

When client 1 (Bob's laptop) saves a new file, it fires two requests at the same time.[1] Lane A records what the file is (its metadata). Lane B moves what's in it (the content). Tap each step into its lane, in order. Watch the file's status on the metadata DB and client 2's screen.

      Catch up

      The download flow, trace it

      A download starts when a file is added or edited somewhere else. How does your phone find out? The book gives two cases:[1]

      • Phone online: the notification service tells it "something changed, come and get it". The phone then pulls the latest data itself.
      • Phone offline: the change is saved in the offline backup queue. When the phone comes back, it pulls the latest changes.

      Hold the line

      Long polling vs WebSocket, predict-then-watch

      The notification service has to push news to clients. The server can't just phone a laptop out of the blue, so the client keeps a line open. The book weighs two ways to do that:[1]

      ⏳ Long polling

      The client sends a normal HTTP request. The server holds it open without answering until it has news or a time limit passes. Then the client sends a new one straight away. Dropbox uses this.[1]

      🔌 WebSocket

      One connection that stays open, and both sides can send messages at any time. It's built for two-way, real-time traffic.[3]

      You are client 2. Press Open long poll. The bar is your request, held open by the notification service. When the server answers, your poll is over: the client fetches the news and must reopen right away. Be quick: any change that lands while no poll is open can't reach you.

      What you just did by hand, a real client does in a loop: after every answer or timeout it reopens at once.[1] A "missed" change isn't lost. The server still has it, and the next poll gets it straight away. It just arrives late. Correctness comes from re-reading the metadata, not from the ping itself. The 60 s timeout is just this sim's choice; the book doesn't give a number.

      Pick the channel. For each product, would you use long polling or WebSocket?

      The book's two reasons for long polling in Drive:[1] (1) the traffic is one-way: the server tells the client about file changes, and the client never pushes anything back on that line. (2) Drive's notifications are infrequent, with no bursts of data. WebSocket shines for real-time, two-way traffic like chat.

      🎓 Level-up note (for later)

      • The "offline backup queue" is fuzzy. Real sync clients usually keep a cursor: a marker for the last change they saw. When they reconnect, they ask "everything since this cursor?" No per-device queue is needed. Dropbox's public API works this way: the long poll only answers "changes: true or false", and the client then lists the changes since its cursor.[5]
      • "Upload complete" is your job to track. S3 can send an event when an object is created.[4] But a file is many blocks, so "done" really means "every block of this version is stored". The server has to count that itself.
      • Long polling vs WebSocket is a close call today. Many products push to clients over WebSocket or server-sent events. Either answer is fine in an interview if you give the reason.
      • The ping only says "something changed". Correctness comes from re-reading the metadata. So a lost notification delays sync but doesn't corrupt data.
