Quest 4.5 · Design a Rate Limiter

Many Doors, One Count

One limiter on one box is easy. Now run fifty of them, in three regions, sharing one Redis that might fall over. This is where interviewers start digging.

🎯

Your win today: you can show the read-check-write race (two requests both see 3), fix it with a Lua script or a sorted set, explain why sticky sessions lose to a central Redis, talk through edge servers and eventual consistency, and say what you’d monitor and what happens when Redis dies.

1

The race

Two requests, one counter, wrong answer

On one server with one thread, a rate limiter is simple. The book points out that real systems run many servers, each with many threads (tasks running at the same moment). That brings two new problems: race conditions and synchronization.[1] This stage is about the first.

Here is the limiter’s logic, written as three separate steps, the way the book lays it out:

  1. Read the counter from Redis.
  2. Check: would counter + 1 go over the limit? If yes, reject with 429.
  3. If not, Write counter + 1 back to Redis and let the request in.

A race condition is a bug where the result depends on the exact timing of two tasks running at once. Below, the counter is at 3 and the limit is 4. So exactly one of requests A and B should get in. You control the timing.

That’s the book’s exact bug. Both requests read 3, both decided “3 + 1 = 4, fine”, and both wrote 4. The second write wiped out the first. Two requests got in, but the counter only went up by one. With a true count it should read 5.[1] Under real load this happens thousands of times a second, so a client can blow far past its limit.

The obvious fix is a lock: a flag that says “I’m using this counter, everyone else wait.” The book’s view is that locks slow the system down a lot. It names two common alternatives instead:[1]

  • A Lua script. Redis can run a small script written in Lua (a tiny programming language). While a script runs, Redis runs no other command. So read, check and write happen as one atomic step: nothing can sneak in between.[3]
  • A Redis sorted set. A sorted set is a list of items kept in order by a number called a score. Use the request timestamps as scores and send the commands as one transaction.
Show me both fixes in code 
-- Lua: read, check and write as ONE atomic step
-- KEYS[1] = counter key, ARGV[1] = limit, ARGV[2] = window in seconds
local n = tonumber(redis.call('GET', KEYS[1]) or '0')
if n + 1 > tonumber(ARGV[1]) then return 0 end  -- reject: 429
n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end
return 1                                         -- allow
# Sorted set (sliding window log), sent as one MULTI ... EXEC transaction
ZREMRANGEBYSCORE key 0 (now - window)   # drop old timestamps
ZADD key now now                        # add this request
ZCARD key                               # how many in the window?
EXPIRE key window
# then: allow only if the count is within the limit

The sorted-set recipe is the one ClassDojo published.[2] The book only names the idea. One catch: the transaction runs all four commands together, but your code decides allow or reject afterwards. So a rejected request has already been added to the set. The Lua version checks before it writes.

2

Sticky or shared?

The synchronization problem

Millions of users means one rate limiter server isn’t enough, so you run several behind a load balancer (LB: the box that spreads requests across servers). The web tier is stateless: any server can handle any request, so one client’s calls can land on different limiters.[1]

If each limiter keeps its own counts, limiter 1 knows nothing about what the client did through limiter 2. Getting them to agree is the synchronization problem. Try the three setups. One client sends 10 requests. The limit is 5 per minute.

Let in this minute: 0 / limit 5
  • ✓Local: each limiter counts on its own
  • ✓Sticky: pin the client to limiter 1, then kill limiter 1
  • ✓Central Redis: both limiters share one counter
Why the book rejects sticky sessions. A sticky session means the load balancer always sends the same client to the same limiter. It works until it doesn’t. The book calls it neither scalable nor flexible.[1] You just saw both: one heavy client pins all its load on one box (the heat bar), and when that box dies, the client’s count dies with it.
The book’s choice: a central store. All limiters read and write the same counters in Redis. Routing no longer matters, and a dead limiter loses nothing, because the count never lived on it. Combine this with stage 1: the shared counter must be updated atomically.
3

Go to the edge

Multi-data-center speed vs exactness

A central Redis is correct, but it lives in one place. The book’s first performance tip: a multi-data-center setup matters, because users far from the data center see high latency. Cloud providers run many edge servers (small data centers close to users). The book notes Cloudflare had 194 of them in 2020. Traffic goes to the closest one.[1][5]

Its second tip: keep the edges’ counters in sync with eventual consistency. Each edge updates its own copy right away and shares changes with the others a little later. Copies may disagree for a moment, but they catch up. (You met this idea in World 6, in Majority Rules.)

4

Watch the gauges

Monitoring, and what happens when Redis dies

Shipping the limiter isn’t the end. The book says to collect analytics afterwards and check two things: is the algorithm effective, and are the rules effective?[1] You’re on call. Read each dashboard (green = let in, red = rejected with 429) and pick the fix.

When Redis itself goes down

The book’s requirements include high fault tolerance: if part of the limiter fails, for example a cache server goes offline, the whole system must not go down with it.[1] So decide in advance what each endpoint does without its counters:

  • Fail open: let every request through, unlimited, and alert a human. The product keeps working, but nothing protects it.
  • Fail closed: reject every request. Nothing gets abused, but you’ve turned a cache outage into a product outage.

Honest caveat. Fail open vs fail closed isn’t in the book’s deep dive. It follows from the “high fault tolerance” requirement, and interviewers ask it all the time. Stripe’s write-up on its limiters says they should fail open, so a limiter bug never blocks good traffic.[4] A common middle path: fall back to a rough per-server limit in memory until Redis returns.

🎓 Level-up note (for later)

  • One Redis is one point of failure. A single instance is also a bottleneck. Real systems shard counters across a Redis cluster (split keys by user or API key) and add replicas.
  • Not every counter races. For a plain fixed-window counter, INCR alone is atomic (Quest 4.4): increment first, then compare the number it returns. The race appears when you read, decide in your code, and write in separate commands.
  • Global limits are approximate. With regional counters synced eventually, a global limit can briefly overshoot. An exact global cap costs a cross-region round trip on every call. Cloudflare’s write-up counts per location, which works because a client usually keeps hitting the same nearby one.[6]
  • The 194 is dated. That was Cloudflare in 2020. It now lists well over 300 cities. The point stands: limit close to the user.
