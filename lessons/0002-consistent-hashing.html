Quest 6.2 · Design a Key-Value Store

Slice the Keyspace

Your data no longer fits on one server. Cut it into slices, hand them out — then add and kill servers and see how many keys have to move.

🎯

Your win today: when an interviewer asks "how do you decide which server stores which key?", you can explain the hash ring, say why hash % N breaks when servers come and go, and explain how virtual nodes keep the load even.

1

The modulo trap

The obvious way to split data, and why it breaks

In Quest 6.1 one server ran out of room. So you cut the data into slices called partitions (also called shards) and give each server some of them. The book says a good split has to do two things:[1]

  • Spread data evenly, so no server ends up with far more than its share.
  • Move as little data as possible when servers are added or removed. Every key that moves has to be copied over the network. In a cache, a moved key is a miss: the data isn't where clients look for it.

The obvious first try is server = hash(key) % N. A hash function turns any key into a big number that looks random. % N takes the remainder after dividing by N (the number of servers), which is always between 0 and N−1. Below are 100 keys spread over 4 servers. Tap one to see its math.

This is the rehashing problem. A key stays put only if hash % 4 happens to equal hash % 5, which is true for about 1 key in 5. So roughly 80% of keys move. The book's example is a cache that loses one server: most clients now look on the wrong server, and you get "a storm of cache misses" that all fall through to the database.[2] Notice the legend, though. Modulo spreads keys evenly, so it passes test 1 and fails test 2.
2

Bend it into a ring

Consistent hashing, hands-on

Consistent hashing (Karger et al., 1997)[3] fixes this with one picture. Take every number the hash function can output (for SHA-1 that's 0 to 2160−1) and bend that line into a circle, so the end meets the start. That circle is the hash ring.[2]

Hash each server (its name or IP address) to place it on the ring. Hash each key to place it on the same ring. The rule: start at the key, walk clockwise, and the first server you reach stores it.[1]

Tap a key to walk it. Press + to add a server. Tap a server to kill it. The number in the middle counts how many keys moved.

Virtual nodes

Even out the slices, and handle bigger servers

The basic ring has two problems, according to the book:[2] uneven slices (servers land at random spots, so one can own a huge arc and another a sliver) and uneven keys (even with equal arcs, keys can bunch up in one stretch). You also saw a third one in round 3: when s1 died, s2 took all of its load.

The fix is virtual nodes. Each real server is hashed onto the ring many times (s0#0, s0#1, s0#2…), so it owns many small slices scattered around the ring instead of one big arc. Dynamo calls these positions tokens.[4]

Drag the slider. Each bar is a server's share of the ring, and the black line marks its fair share.

Spread: — how far a typical server is from its fair share (standard deviation)
1 virtual node each is just the basic ring. Look how uneven it is.
  • ✓Get the spread under 12%
  • ✓Give the upgraded server its fair share
Matches the book. The book reports a spread of about 10% of the mean with 100 virtual nodes and about 5% with 200.[2] Your sim gives a similar result. It isn't free: every position has to be stored and shared between servers, so more virtual nodes means more metadata (bookkeeping data about which slice belongs to whom). That's a dial you tune.
🖥️ New hardware. s4 was upgraded and now has 2× the memory and disk of the others, so its fair-share line just moved. The book calls this heterogeneity: give each server a number of virtual nodes in proportion to its capacity.[1]

Honest caveat: hot keys. The book's wrap-up says consistent hashing helps with the "hotspot key" problem.[2] That's true for ranges of keys. But one very hot key (say, a celebrity's profile) still hashes to exactly one spot and one server, however many virtual nodes you add. That needs other tools, such as caching or extra copies.

🎓 Level-up note (for later)

Real systems tuned this further. Dynamo later moved away from random positions. It now splits the ring into equal-sized fixed slices and hands whole slices to servers, which balanced load better and made backups simpler (§6.2, "Strategy 3").[4] Cassandra cut its default from 256 virtual nodes per server to 16 in version 4.0, using a smarter way to pick positions. More virtual nodes isn't always better.[5]
