Drop it in the queue

Producers, consumers, decoupling

Some work is slow. In the book's example, users upload photos and pick filters: crop, sharpen, blur. Each one takes seconds of CPU.[1] If the web server does that work while the user waits, the user's request waits too.

A message queue sits between two parts of a system and holds work for later. The book describes it as a durable component (it keeps messages until someone handles them), stored in memory, that supports asynchronous communication: the sender drops a message and moves on, without waiting for the work to finish.[1][5]

  • Producers (also called publishers) create messages and put them on the queue. Here: web servers posting "filter photo #812".
  • Consumers (also called subscribers) connect to the queue, take messages, and do the work. Here: photo-processing workers.

Gauges on the dashboard

Logging, metrics, automation

A small site can get by on luck. Once it serves a big business, the book says, good tooling stops being optional.[1] It names three kinds:

  • Logging. Error logs tell you what went wrong. You can read them on each server, but it's far easier to ship them all to one central log service where you search them in one place.
  • Metrics are numbers you track over time, at three levels:
    • Host level: one machine's health. CPU, memory, disk I/O (how busy its disk is reading and writing).
    • Aggregated level: a whole tier at once, such as the performance of the entire database tier or cache tier.
    • Key business metrics: what the company cares about. Daily active users, retention (how many come back), revenue.
  • Automation. When the system gets big, let machines do the checking. Continuous integration (CI) runs automated checks on every code check-in, so problems show up early. Automating build, test and deploy makes developers faster too.[6]

Bigger box or more boxes?

Scaling the database: up vs sharding

The database is filling up. You have two ways out, the same two you met for web servers in Quest 1.1.

Scale up (vertical): buy a bigger machine with more CPU, RAM and disk. It goes further than you'd think. The book notes that Amazon RDS offered database servers with 24 TB of RAM, and that Stack Overflow in 2013 served over 10 million monthly unique visitors with just one master database.[1][2] But it has three drawbacks:

  • Hardware has a ceiling. With enough users, even the biggest box isn't enough.
  • Single point of failure. Everything rides on one machine. If it dies, so does your app.
  • Cost. The most powerful servers cost far more per unit of power.

Scale out (horizontal), called sharding: split one large database into smaller, easier-to-manage parts called shards.[4] Every shard has the same schema (the same tables and columns), but each holds different rows, with no overlap. To decide where a row goes, you pick a sharding key (also called a partition key): one or more columns whose value picks the shard. The book's example puts users on 4 shards with shard = user_id % 4. (% means "remainder after dividing", so the answer is always 0–3.)

Shard trouble

Resharding, celebrities, joins

Sharding works, but the book warns it brings new problems.[1] Here are the three it names. Work through all three panels, in any order.

  • ✓A. Resharding: add a 5th shard, two ways
  • ✓B. Celebrities: cool down a hotspot shard
  • ✓C. Joins: answer a query that spans two shards
Panel A

Resharding

You need to reshard (change how rows map to shards, and move data to match) in two cases. Either a shard can't hold more because you grew fast, or some shards fill up faster than others because the data isn't spread evenly. The book calls that second one shard exhaustion. Here, 100 users sit on 4 shards by user_id % 4. Shard 4 is waiting to join.

shard = user_id % 4
Why it's so different. With % N, a user stays put only if id % 4 equals id % 5, which happens for 1 id in 5. Consistent hashing places shards and keys on a ring, so a new shard only takes a slice from its neighbours: about 1/5 of the users here. The book points to it as the common fix for resharding (it gets its own chapter). Try it hands-on in Quest 6.2, Slice the Keyspace.
Panel B

The celebrity problem

Also called the hotspot key problem: one shard gets far more traffic than the others and buckles. In a social app, three of the biggest stars all happen to live on shard 2. Tap each one to make them go viral. The black line is what one shard can handle (8,000 queries per second, or QPS).

Panel C

Joins across shards

A join combines rows from two tables, like posts plus the names of their authors. On one database that's a single query. Once the tables live on different servers, the database can't do it for you.

🎓 Level-up note (for later)

  • "Stored in memory" is a simplification. Real brokers such as Kafka, RabbitMQ (with durable queues) and Amazon SQS write messages to disk or to replicated storage so they survive a crash. Most deliver at least once, so a job can arrive twice. Make consumers idempotent: running the same job twice must be harmless.
  • user_id % N is a teaching example. Production systems usually use consistent hashing, range-based sharding (by key ranges) or directory-based sharding (a lookup table), so adding a shard doesn't move most of the data.
  • Sharding is often a last resort. Many teams first try read replicas (Quest 1.2), caching (Quest 1.3), archiving cold data and a bigger box. Sharding makes transactions, joins and schema changes much harder.
  • The numbers are dated. The 24 TB RDS figure and the 2013 Stack Overflow figure come from the book. Check current instance sizes before you quote them; AWS lists its largest memory machines on its High Memory instances page.[3]
  • A shard per celebrity fixes reads, not every hotspot. A key that takes huge numbers of writes may also need key salting (adding a small random suffix so one key's writes spread over several shards) or splitting the key across shards.
