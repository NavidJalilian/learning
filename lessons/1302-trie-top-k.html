Grow the Trie

Every keystroke needs five suggestions in under 100 ms. Grow the tree that makes prefix search cheap, time its slow top-k lookup, then use two cheats to answer in a single hop.

🎯

Your win today: you can draw a trie, explain why the naive top-k lookup costs O(p) + O(c) + O(c log c), show how capping the prefix length and caching the top-k queries at every node make it O(1), and say what that speed costs in memory.

1

Plant a trie

A tree where every path spells a prefix

In Quest 13.1 a plain SQL table of (query, frequency) couldn't keep up: every keystroke meant a LIKE 'prefix%' scan plus a sort. The book swaps it for a data structure built for prefixes, the trie.[1] The name comes from retrieval. Most people say "try" so it doesn't sound like "tree".[2]

  • The root stands for the empty string "".
  • Every other node holds one character. Read the characters from the root down to a node and you get a prefix (the start of a word). So each node is a prefix.
  • Words that start the same way share nodes. tree, try and true all pass through t → tr.
  • A node where a full search query ends also stores its frequency: how many times people searched it.

2

Top-k the slow way

Three steps, three costs

The user types a prefix. We want the k most-searched queries that start with it. The book uses three letters to count the work:[1]

  • p = length of the prefix (be → p = 2).
  • n = total number of nodes in the trie.
  • c = how many nodes sit under the prefix node. The book calls these its children, meaning everything below it, not just the next level.

The naive algorithm: ① walk down to the prefix node, O(p). ② visit its whole subtree and collect every node that holds a frequency, O(c). ③ sort what you found and keep the top k, O(c log c). Run it on the book's example: k = 2, the user types be.

Why short prefixes hurt. Step ① is cheap: a one-letter prefix is one hop. The damage is in steps ② and ③. A short prefix sits near the root, so its subtree is a big slice of the whole trie, and you walk all of it and sort it on every keystroke. The timings are rough, for feel only: about 50 ns per node visit (each hop is a jump in memory) and about 5 ns per comparison while sorting.
3

Two cheats that buy O(1)

Cap the prefix, cache the answers

The book makes two changes:[1]

  • Cap the prefix length. People almost never type very long queries, so treat p as a small fixed number, such as 50. Walking down at most 50 hops is a constant, so step ① becomes O(1).
  • Cache the top queries at every node. Each node keeps its own ready-made list of the top k queries below it. Users only need 5 to 10 suggestions, so k stays small. Node be stores [best 35, bet 29, bee 20, be 15, beer 10]. No subtree walk, no sort: steps ② and ③ disappear.

🎓 Level-up note (for later)

Once every node carries its top-k list, the trie is really a lookup table from prefix → answers. Many production systems skip the in-memory tree and store exactly that table. Prefixy, for example, keeps a sorted set per prefix in Redis.[3] The book gets there too, when it stores the trie in a key-value database (Quest 13.3).

The book ranks by historical frequency only, on purpose. Real autocomplete also weighs freshness (what's trending now), location and personalization. The book only touches on trending queries at the end of the chapter (Quest 13.5).
