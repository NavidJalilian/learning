Plant a trie

A tree where every path spells a prefix

A trie (say "try") is a tree built for storing strings compactly. The name comes from retrieval.[1][2] Three rules:

  • The root stands for the empty string. Nothing typed yet.
  • Each node adds one character. The path from the root down to a node spells a prefix (the start of a query). Below, each node shows the prefix it spells, with its own new letter in colour.
  • Words that start the same way share nodes. tree, try and true all go through t → tr.

For ranking, the node where a whole query ends also stores how often people searched it: its frequency (the yellow badge). The six words and counts are the book's example.[1]

Top-k the slow way

Three steps, three costs

Autocomplete needs the top k queries for a prefix: the k most frequent ones that start with it. First, three letters the book uses:[1]

  • p = length of the prefix (be → p = 2)
  • n = total number of nodes in the trie
  • c = number of nodes below the prefix node (its whole subtree)

The naive lookup takes three steps. ① Find the prefix node: walk down one letter at a time, O(p). ② Collect: visit every node in its subtree and keep the ones that are real queries, O(c). ③ Sort them by frequency and take the top k, O(c log c). O(…) is "big-O": how the work grows as the input grows.

Your move: type be and run the three steps in order. Here k = 2, as in the book's example.

    Two cheats that buy O(1)

    Cap the prefix, cache the answers

    The book makes the lookup fast with two tricks.[1]

    • ✂️ Limit the prefix length. People rarely type long queries, so cap p at a small number such as 50. Walking at most 50 steps is a fixed, small amount of work, so finding the node counts as O(1) (constant time: it doesn't grow with the data).
    • 📋 Cache the top queries at every node. Store the top k right on each node. 5 to 10 suggestions are plenty, so k stays small; the book keeps 5. Node be holds [best 35, bet 29, bee 20, be 15, beer 10]. No walking the subtree, no sorting.

      Pay for speed

      Count the copies

      Caching the top 5 at every node means one query gets copied into the list of every node above it where it makes the top 5. That's the memory bill. There's a second bill: when a query's count changes, every list holding it may have to change too.

      🎓 Level-up note (for later)

      • The trie becomes a table. Once every node stores its top k, the useful data is really a map: prefix → top-k list. Many production systems skip the in-memory tree and store exactly that. Prefixy, for example, keeps one sorted set per prefix in Redis.[3] The book gets there too, in the next quest, when it stores the trie in a key-value store.
      • "O(1)" means "bounded". Lookup is O(p) with p capped at 50. Say it that way if pushed.
      • Ranking is more than counts. The book ranks by historical frequency only. Real systems also weigh freshness, location and personal history.
      • Smaller tries. Long single-child chains (like w → wi → wis → wish) can be merged into one node. That's a radix tree, and it saves a lot of nodes.[2]
