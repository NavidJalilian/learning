1

The sticky problem

Stateful servers

In Quest 1.1 you put a load balancer in front of several web servers so traffic could be shared out. There's a catch the book raises next: what the servers remember.[1]

State is data about a client that has to survive from one request to the next, like "this browser is logged in as User A". A stateful server keeps that data in its own memory. A stateless server keeps none.

Below, each user's session (their login record) lives on one server. The load balancer uses round-robin: it hands requests to Server 1, 2, 3, 1, 2, 3… in turn, without caring who sent them. Send a few requests.

  • ✓Send requests until one lands on a server that doesn't know the user
  • ✓Switch the load balancer to sticky sessions and send again
Sticky sessions (also called session affinity) means the load balancer always sends a given user to the same server, usually by setting a cookie on the first response.[2] Most load balancers can do it. The book's verdict: it works, but it adds overhead, it makes adding or removing servers harder, and it makes server failures hard to handle. Test those three claims below.
2

Move the memory out

Stateless web tier + autoscaling

The book's fix: take the state out of the web servers and put it in a shared data store that every server can reach. That store could be a relational database, Memcached or Redis (in-memory key-value caches), or a NoSQL database. The book picks NoSQL because it's easy to scale.[1]

Now any server can handle any request: it just looks the session up in the store. The book calls the result simpler, more robust and more scalable. Flip the switch, then rerun the three stress tests.

Now let the fleet size itself

Once servers hold no state, you can add or remove them at any moment. Autoscaling means doing exactly that, automatically, based on traffic. You set the rules. The demo runs one day in fast-forward: a quiet night, a morning peak and an evening spike. Each server handles 100 requests per second, and a new one takes about 10 minutes to boot.

Goal: 0 overloaded minutes, at most 190 server-hours (running 14 servers all day would cost 336), and at most 2 flaps. The starting rules are bad on purpose.
That's thrashing. When the add and remove lines sit close together, adding one server drops average CPU below the remove line, so a server is removed, CPU jumps back up, and the cycle repeats. Real autoscalers prevent this with a gap between the thresholds and a cooldown: after a change, wait a few minutes before making the opposite one.
3

Two continents

Data centers and GeoDNS

Your app goes national, then international. One data center (DC: a building full of your servers) is far from many users and is a single point of failure. So the book adds a second one. Each DC gets its own load balancer, web servers, cache and database.[1]

How does a user's phone know which DC to talk to? DNS turns a name like app.example.com into an IP address. GeoDNS is a DNS service that gives a different answer depending on where the user is. Each user gets the address of the closest DC. The book calls this being geo-routed, and it writes the traffic split as x% to US-East and (100 − x)% to US-West.

Tap a city to see its DNS answer. Drag the clock: people wake up and go to bed at different times on each coast, so x moves all day.

Honest caveat: DNS failover isn't instant. Phones and internet providers cache DNS answers for a set time (the record's TTL, "time to live"). Until that runs out, some users keep trying the dead DC. Teams keep the TTL short (seconds to a minute), or use anycast addresses and global load balancers, which can reroute faster.
4

The hard parts

Redirection, data sync, test and deploy

Two DCs sound great until something goes wrong. The book names three problems you have to solve:[1]

  • Traffic redirection: you need a reliable way to send each user to the right DC. GeoDNS does this by sending users to the nearest one.
  • Data synchronization: each region may use its own local database and cache. After a failover, users can land in a DC that doesn't have their data. The usual fix is to replicate (copy) data across DCs. The book points to Netflix, which copies data between regions asynchronously, meaning in the background a moment after each write.[3]
  • Test and deployment: test the app from several locations, and use automated deployment tools so every DC runs the same version.

🎓 Level-up note (for later)

  • A third stateless option. Signed tokens such as JWTs carry the session inside the client's request, so no store lookup is needed. The catch: you can't easily revoke one before it expires.
  • Sticky isn't always wrong. Long-lived connections like WebSockets stay on one server by nature. The chat design in World 12 keeps stateful connection servers on purpose.
  • DNS failover is slow-ish. Cached answers live for their TTL, so some users keep hitting a dead DC for a while. Anycast and global load balancers fail over faster.
  • Writes in two regions conflict. If both DCs accept writes to the same data (active-active), two writes can collide. Many teams keep one region as the database writer (active-passive) or give each user a home region.
  • The numbers are made up. The book's x% / (100 − x)% split and its DC names are illustrative, and so are this quest's autoscaling numbers.
