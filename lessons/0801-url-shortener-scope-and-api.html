Quest 8.1 · Design a URL Shortener

Specs for a Shrink Ray

The interviewer says "Design TinyURL." Don't start drawing yet. First find out what you're building and how big it is, then sketch the two calls everyone will make.

Ask before you draw

Step 1 · scope the prompt

A URL shortener turns a long web address into a tiny one. Paste a long link in, get something like tinyurl.com/y7keocwj back. Anyone who clicks the tiny link lands on the original page.[1]

The book's prompt is deliberately vague: "design a URL shortener like TinyURL." Step 1 of the interview framework is to ask questions until it isn't vague any more. Below are 9 questions you could ask. Tap the 5 you'd ask first. The interviewer answers the good ones, and each answer goes on your requirements note.

Careful: a question about tools (languages, databases, platforms) is not a requirement. Asking one now costs a heart.

Interviewer"Design a URL shortener like TinyURL. Go."

📌 Requirements 0 / 5

    Nothing yet. Ask something!
    What you now know. Two use cases (things users do): shortening (long URL in, short URL out) and redirecting (short URL in, browser sent on to the long URL). Plus three non-functional needs, meaning qualities rather than features: high availability (it stays up), scalability (it grows by adding machines) and fault tolerance (it keeps working when a part breaks).[1] Every one of these answers will matter in a later quest.

    Back-of-the-envelope, then play with the knobs

    Drag the knobs until storage passes 100 TB. Which knob moved it fastest?

    No wrong answer. Just notice.

    💡 What you just saw. Storage = URLs/day × 365 × years × bytes. Each of those three knobs multiplies storage directly, so the one with the widest range (URLs/day, 100× from end to end) moves it fastest. And the read : write knob didn't touch storage at all. Reads don't create rows; they drive QPS (queries per second) and caching, not disk.
    Honest caveat. 36.5 TB counts only the long URLs. Real storage also holds the short codes, IDs, timestamps and indexes, and is usually copied about 3 times for safety. So expect a real number several times bigger. Also, 10:1 is the book's assumption. Popular shorteners are far more read-heavy, which makes caching even more valuable.
    3

    Two doors in

    Step 2 · the API endpoints

    An API endpoint is one address the outside world can call. The book uses a REST style: each call is an HTTP method (the verb: GET reads, POST creates, PUT replaces, DELETE removes) sent to a path (the noun), sometimes with a body (data attached to the request).[2] Our two use cases need exactly two endpoints.

    Build each request from the chips and press Send. The mock server answers like a real one. Error codes are free here: read them, they explain themselves.

    The two endpoints, as the book writes them.[1]
    POST api/v1/data/shorten with body {longUrl: longURLString} → returns the short URL.
    GET api/v1/shortUrl → returns the long URL inside an HTTP redirect.
    In practice the redirect lives at the root (tinyurl.com/y7keocwj, no /api/v1/) so the short URL stays short. Many APIs also answer a create with 201 Created instead of 200 OK.
    4

    301 or 302?

    Predict, then watch the browser

    When a short link is clicked, the shortener doesn't send back a page. It sends a redirect: a status code plus a Location header (a named line in the response) holding the long URL. The browser reads it and goes there by itself. Two codes are in play:[1]

    • 301 Moved Permanently: "this address has moved for good." Browsers cache it (remember it locally).[3]
    • 302 Found: "it's over there for now." Nothing is remembered; ask again next time.[4]

    Pick a code, predict, then click the same short link three times and watch who gets asked.

    Shortener saw: 0Clicks logged: 0Link clicks: 0
    Predict first, then click.

    The interview line: "301 if we want to cut server load, since the browser goes straight to the long URL next time. 302 if we want analytics, such as click rate and where clicks come from, since every click passes through us."[1]
    Honest caveat. The book's "301 = no analytics" is a useful simplification, not a law. Popular shorteners such as Bitly answer with 301 and still count clicks, because each browser's first click is logged and browsers don't keep a 301 forever. There are also 307 and 308: like 302 and 301, except the browser must repeat the same HTTP method.[5] For GET-only redirects, 301 vs 302 is the whole story; bring up 307/308 only if asked.

    The obvious version

    Step 2 · shortening with a hash table

    The simplest design the book starts from: keep a hash table (a lookup table from key to value, like a dictionary) of <shortURL, longURL> pairs. A hash function fx(longURL) = hashValue turns each long URL into a short value, and the short URL is www.tinyurl.com/{hashValue}.[1]

    The function has two jobs: each long URL must map to one hashValue, and each hashValue must map back to its long URL. Try both below. (This toy function is a stand-in. Choosing a real one is the next quest.)

    🎓 Level-up note (for later)

    • Real shorteners mostly send 301 and still have analytics: each browser's first click is logged, and a cached 301 doesn't live forever. Treat "301 = no stats" as the book's simplification.
    • 307/308 are the method-preserving twins of 302/301. Mention them only if the interviewer asks.
    • 36.5 TB is a floor. Add short codes, IDs, timestamps, indexes and ×3 replication, and the real number is several times bigger.
    • 10:1 is an assumption. Real shorteners are far more read-heavy, which strengthens the case for a cache (Quest 8.4).
    • The book writes the redirect as GET api/v1/shortUrl. In production it sits at the root of the domain so the link stays short.
