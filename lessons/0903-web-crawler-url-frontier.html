Quest 9.3 · Design a Web Crawler

Taming the Frontier

The URL frontier is the crawler's to-do list. Make it a plain queue and you'll hammer small websites and crawl junk before gold. Today you rebuild it in two layers: one for priority, one for politeness.

🎯

Your win today: you can explain why plain BFS is impolite and priority-blind, draw the two-layer URL frontier (front queues for priority, back queues for politeness with a host-to-queue mapping), name two recrawl strategies, and justify keeping the frontier on disk with memory buffers.

1

Deep or wide?

DFS vs BFS on the web graph

The web is a directed graph: each page is a node, and each link is a one-way edge from one page to another. Crawling means walking that graph. There are two classic ways to walk it:[1]

  • DFS (depth-first search): follow the first link, then that page's first link, and keep going down. It uses a stack: last in, first out.
  • BFS (breadth-first search): fetch every page one link away, then every page two links away, and so on. It uses a FIFO queue: first in, first out, so URLs are fetched in the order they were found.

BFS fixes depth, but floods one host and ignores importance. Look at the end of the BFS timeline: 8 wiki pages back to back. Most links on a page point to the same site (on Wikipedia, nearly all of them), so a site's URLs pile up together in a FIFO queue. That's problem 1: impolite bursts at one host. Problem 2: every URL just waits its turn. Apple's home page and wiki page #4,000 get the same treatment, so there's no priority.[1] The rest of this quest fixes both.
2

Don't knock too fast

Politeness · back queues

Politeness means not sending a site lots of requests in a short time. A crawler that does this can look like a denial-of-service attack (flooding a server until it can't serve real users), and sometimes it really is one. The book's rule: download one page at a time per host, and wait a little between two downloads from the same host.[1] (A host is the site part of a URL, like apple.com.)

Why this works. The queue router uses the mapping table (host → queue) to put each URL into the FIFO queue for its host, so each back queue holds one host only. The queue selector gives each worker thread one queue, and the worker downloads that queue's URLs one by one, pausing in between. One host, one queue, one worker, so two workers can never hit the same host at once.[1] The crawl still moves because the other hosts are being fetched in parallel. A real crawler has millions of hosts, so there's always one that's ready.
3

Important pages first

Priority · front queues

Not all pages are equal. A random forum post that mentions Apple is worth far less than Apple's home page, even though both contain the word "Apple". So crawl the useful pages first. The book judges usefulness with signals such as PageRank[5] (a score based on how many important pages link to this one), website traffic, and how often the page changes.[1]

A component called the Prioritizer scores each URL and puts it in a front queue: f1 for high priority, f2 for medium, f3 for low (the book draws f1…fn, one queue per level). You're the prioritizer now.

Next, a queue selector decides which front queue to take the next URL from. The book's selector picks a queue at random, but weighted toward higher priority. Set the weights, pick 100 URLs, and watch where they come from. Then try strict priority (always take from the highest non-empty queue).

The front queues never run dry on the real web: new high-priority URLs keep arriving.

Stack the two layers

Front queues + back queues = the URL frontier

The full frontier design stacks both ideas. URLs flow from top to bottom. The front queues module decides what comes out next (priority). The back queues module decides when a host may be hit (politeness).[1]

Beyond the book: there are more hosts than queues. The book's figure shows one back queue per host, but the web has hundreds of millions of hosts. The Mercator crawler keeps a fixed number of back queues (it suggested about three times the number of worker threads). When a back queue empties, it's handed to a new host pulled from the front queues. A heap (a structure that always gives you the smallest item) tracks the earliest time each host may be contacted again.[2][3]
5

Keep it fresh, keep it stored

Recrawl strategy + where the frontier lives

Freshness. Pages are added, edited and deleted all the time, so a crawler must recrawl pages it has already downloaded. Recrawling everything is slow and expensive. The book gives two strategies:[1]

  1. Use each page's update history: pages that changed often in the past get revisited more often.
  2. Prioritize: recrawl important pages first, and more frequently.

The book's answer: hybrid. Most URLs live on disk, where space is cheap and survives a crash. Small in-memory buffers sit in front for enqueue and dequeue, and the buffer is written to disk periodically in big batches. All in memory is neither durable nor scalable. All on disk is too slow and becomes the bottleneck.[1]

🎓 Level-up note (for later)

  • Politeness is really per server, not per host name. Thousands of small sites can share one IP address at a hosting provider, so careful crawlers limit by IP as well. Mercator also scaled the pause to the host: it waited several times as long as the last download took, instead of a fixed delay.[3]
  • "One page at a time per host" is conservative. Big sites can take much more. Google adjusts its crawl rate for each site based on how quickly and cleanly the server responds.[6]
  • PageRank is just the book's example. Modern search engines use many signals and keep the details private. Treat the prioritizer as "some scoring function", not a known algorithm.
  • Freshness has a twist. Cho and Garcia-Molina found that recrawling pages strictly in proportion to how often they change can backfire: a page that changes constantly is stale again almost as soon as you fetch it. You may have seen this in Lab A, where piling recrawls onto the hourly score page barely helped. "Recrawl what changes often" is a good first answer, not the last word.[4]
