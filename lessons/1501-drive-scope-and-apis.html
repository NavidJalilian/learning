What are we building?

Step 1 · ask before you draw

"Design Google Drive" is too big to answer as asked. So step 1 of the interview framework is to ask questions until the problem is small enough to design in 45 minutes. Here is roughly how the book's candidate does it, in our words:[1]

Now sort what you heard. A functional requirement is something the product does (a feature). A non-functional requirement is a quality it must have: how reliable, fast or big it is. Out of scope means "we agreed not to design this today." Tap a bin for each card that drops.

12 cards left
Mini-step

The book lists five non-functional requirements. For a storage product, which one is non-negotiable?

  • Reliability: data loss is unacceptable. A lost file is the one sin users never forgive.
  • Fast sync: if a change takes ages to show up on your other devices, people give up on the product.
  • Low bandwidth: send as few bytes as possible. It matters a lot on mobile data plans.
  • Scalability: the design must cope with a very large amount of traffic.
  • High availability: people keep working even when some servers are slow, offline or cut off by network errors.

Run the numbers

Back-of-the-envelope, calculate-and-check

Next comes a back-of-the-envelope estimate: rough math, done in your head, to see how big the system must be. These are the book's assumptions:[1]

50M signed-up users10M DAU10 GB free each2 uploads / user / day500 KB avg fileread : write = 1 : 1

Handy conversions: 1 PB = 1,000 TB = 1,000,000 GB. One day = 24 × 3,600 = 86,400 seconds. QPS means queries (requests) per second.

Promised is not the same as used. 500 PB is the quota: what we'd need if every user filled their 10 GB. The bonus card shows that the book's own numbers add only about 10 TB of new data per day, and most free users never fill their quota. That 10 TB figure is our derivation, not the book's. In an interview, saying this out loud shows you know what the number means.
Senior habit: round out loud and move on. 231 becomes "about 240", and nobody minds. An estimate exists to pick an architecture (one server or many? disks or object storage?), not to be exact. The 2× peak factor is a rule of thumb, not a measured number.

Three doors in

The APIs: upload, download, revisions

An API (application programming interface) is the set of requests the apps can send to our servers. The book needs only three.[1] Open each door.

# tap a door to see its request
🔐 Every call: user must be logged in🔒 HTTPS only (TLS/SSL encrypts data in transit)

Upload comes in two kinds. A simple upload sends the whole file in one request. Fine for small files. A resumable upload is for big files on shaky networks: if the connection drops, you carry on from where it stopped. Try both on a 2 GB video. The Wi-Fi will drop at about 70%.

  1. 1Start. Send POST …/files/upload?uploadType=resumable. The server answers with a session URL for this upload.
  2. 2Upload the data in chunks to that URL and keep track of how far you got.
  3. 3Disturbed? Ask the server how much it has (it replies 308 with a Range), then resume from the next byte.

Outgrow the box

From one server to S3, predict-then-watch

The book starts small, on purpose: one server.[1] It runs an Apache web server (handles uploads and downloads), a MySQL database for metadata (data about the data: users, logins, file names, sizes), and 1 TB of disk for the files themselves. Files live under a drive/ folder with one namespace (sub-folder) per user. A file's ID is its namespace plus its path, like drive/alice/trips/video.mp4.

Then the users arrive. Three rounds: predict first, then watch.

One server. Plenty of room. For now.
What's a region? A region is a geographic area where a cloud provider runs its own data centers (say, Northern Virginia or Frankfurt). S3 can copy objects to another bucket in the same region or in a different region.[4] Netflix and Airbnb are the book's examples of companies that keep files in S3.[1] AWS pitches S3 as object storage built for scale, availability, security and performance.[3]

🎓 Level-up note (for later)

  • 500 PB is a promise, not a disk bill. Using the book's own numbers, 20M uploads × 500 KB is only about 10 TB of new data per day (our derivation). Capacity planning works from actual use plus growth. Quota matters for pricing and limits.
  • 231 vs ~240. The exact answer is 231. The book rounds up, and the 2× peak is a rule of thumb. Real traffic has daily cycles, so measure your peak once you can.
  • Resumable details are Google's, not the book's. Session URL, 256 KB chunk multiples, 308 + Range.[2] S3 does the same job with multipart upload: split the file into parts, upload them (even in parallel), retry only the failed parts, then "complete" the upload.[5]
  • Interview-sized numbers. Real Google Drive serves far more than 50M users. The book's numbers are sized so the math fits on a napkin.
