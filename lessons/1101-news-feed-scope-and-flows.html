Quest 11.1 · Design a News Feed System

Two Rivers

A news feed looks like one endless scroll. Underneath it are two separate flows: one carries new posts out to friends, the other carries a ready-made feed back to you. Scope it, give it two API calls, and build both flows.

What's in a feed?

Scope it in under a minute

Newest first, or best first?

Why the book picks the simple order

There are two ways to order a feed. Reverse chronological means sorting by post time, newest on top. Ranked means sorting by a score. The book's example of a ranking signal: posts from close friends count for more than posts from distant ones.[1] Facebook's help pages list similar signals, such as who posted and how you've interacted with them.[2]

Extra data that ranking needs, and newest-first doesn't:

Why the book picks newest first. Ranking needs extra data (how close each pair of friends is, like and comment counts) and a scoring step every time someone loads a feed. To keep the core design clear, the book assumes reverse chronological order. Ranking is a good extension to mention in the wrap-up. A ranking formula in depth is a rabbit hole (remember EdgeRank in Quest 3.4).
Honest caveat. Real feeds are ranked. The good news: the fanout and caching skeleton you'll build in this world works for both orders. Ranking adds a scoring step on top. It doesn't replace the design.

Two doors in the wall

The publish API and the retrieval API

The book keeps the API to two HTTP endpoints, one per flow.[1] Both carry an auth_token, a string the client got at login that proves who is calling. Some background:

  • POST creates something new. GET only reads. A GET must have no side effects, which is why browsers, caches and retry logic feel free to repeat it.[3]
  • me in a path means "whoever is calling". The server works it out from the token. The client never types a user ID.

4

River one: publishing

Where a new post goes

Here's the book's publishing flow, in our words.[1] The client sends POST /v1/me/feed. DNS turns the domain name into an IP address. A load balancer spreads requests across many web servers. The web servers send the request on to three internal services:

  • Post service: saves the post in the post database and the post cache.
  • Fanout service: pushes the new post into each friend's news feed. Feeds live in a news feed cache so reading them is fast. Fanout means copying one item out to many recipients.
  • Notification service: tells friends there's something new and sends push notifications.

A cache is a fast in-memory store (such as Redis or Memcached) that sits in front of a slower database.

River two: feed building

How you read your feed

The book's feed-building flow is shorter.[1] The client sends GET /v1/me/feed. The load balancer passes it to a web server. The web server calls the news feed service, which fetches the user's feed from the news feed cache.

The cache holds the IDs of the posts in each feed, not the full posts. IDs are enough to know which posts to show. Turning them into full posts with names, photos and videos is the reading deep dive in Quest 11.4.

🎓 Level-up note (for later)

Friends vs followers. The 5,000-friend limit matches Facebook's real cap on friends, and it keeps fanout bounded. But pages and public figures can have far more followers than that, with no cap. That's where pushing every post into every feed gets painful, and it's the whole story of Quest 11.2.

Name the missing pieces. The book's v1 leaves out paging on the read API, ranking, and the inside of the notification service. Saying "I'm leaving these out on purpose, here's where they'd go" reads as senior, not as a gap.

Is GET really safe here? Reading a feed changes nothing on the server, so retries are harmless. Publishing isn't: a retried POST can create the same post twice. Real APIs guard against that with an idempotency key the client sends with the POST. That's beyond the book, but a good follow-up answer.
