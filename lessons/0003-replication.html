Quest 6.3 · Design a Key-Value Store

Copies Everywhere

One copy of your data is one bad day away from gone. Learn how a key-value store picks the servers that hold each key's copies — and how it stops them all dying together.

🎯

Your win today: when an interviewer asks "which servers store a key's copies?", you can explain the clockwise walk, why it skips repeat machines, and why the copies live in different data centers — in three sentences.

1

Why keep copies?

N replicas, written asynchronously

Remember n1, n2, n3 from the CAP quest? Those were three copies of one bank balance. Each copy is a replica, and keeping them is replication. The book's rule: every key is copied to N servers, where N is a setting you choose — that quest simply had N = 3.[1][2] Copies buy two things: reliability (a dead disk doesn't lose the data) and availability (another copy can answer while one server is down).

The book adds one word that matters: data is replicated asynchronously.[1] In plain words: the server that takes your write — the coordinator — can answer "OK" before every copy has arrived. The other copies are still travelling, so for a short window the replicas disagree.[3]

Honest caveat — "asynchronous" is a simplification. In Dynamo, the coordinator doesn't answer after zero copies, and it doesn't wait for all N either: it sends the write to N replicas and says OK once W of them (itself included) have confirmed.[2] The rest land in the background. How many must confirm is exactly the dial you'll learn to set in Quest 6.4 · Majority Rules.

Walk the ring

Picking the N servers for a key

Quick recap from 6.2: the store hashes each key to a spot on a circle — the hash ring — and the first server you meet walking clockwise owns the key.

Replication just keeps walking. To place N copies: start at the key's spot, walk clockwise, and take the first N servers you meet. In the book's figure, with N = 3, key0 is copied to s1, s2, s3.[1] Dynamo calls that list the key's preference list.[2]

The twin trap

Virtual nodes — predict, then watch

Real rings use virtual nodes: each physical machine sits on the ring at several spots, so the keys spread more evenly (that was 6.2). Below, 4 machines each own 3 spots. Same colour and same name = same machine.

That creates a trap for the simple walk. Each round, predict first — then watch it happen.

4 machines × 3 virtual nodes = 12 spots on the ring.
Honest caveat — real preference lists are longer than N. Dynamo builds the list by skipping ring positions so it holds only distinct physical machines — exactly what you just did — and it also keeps more than N machines on it, so that when one is down it can use the next healthy one.[2] Cassandra does the same skip: replicas are always distinct physical nodes.[4] What happens when a chosen server is down is Quest 6.6 · When Nodes Die.

Lights out

Spreading copies across data centers

Servers in the same data center (DC — one building full of machines) share power, network and weather. So they tend to fail together: power outages, network issues, natural disasters.[1]

The book's fix: place replicas in distinct data centers, linked by high-speed networks.[1] Dynamo builds every preference list so its machines span several DCs, so a whole-DC failure doesn't take the data down.[2] Below, 9 machines live in 3 DCs — colour now shows the DC. N = 3.

Honest caveat — real systems count per data center. The "skip a DC that already has a copy" walk here is a teaching version. Cassandra's NetworkTopologyStrategy asks you for a replica count per data center (for example 3 in East and 3 in West), then inside each DC walks the ring clockwise and tries to put each copy on a different rack (a cabinet of servers that shares power and a network switch).[4] And distance has a price: a copy in a far-away DC takes longer to reach than one next door.

🎓 Level-up note (for later)

This lesson is leaderless replication (any of the N replicas can take a write), the Dynamo family. Most SQL databases instead use leader–follower replication: one primary takes every write and streams it to followers, either synchronously or asynchronously. DDIA chapter 5 compares the two styles[3] — worth knowing when an interviewer asks "why not just use Postgres replicas?"
