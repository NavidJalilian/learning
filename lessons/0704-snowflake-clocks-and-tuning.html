The 4,097th ID

What happens when the sequence runs out?

Quick recap from Quest 7.3. A Snowflake ID is 64 bits: 1 sign bit, 41 bits of timestamp (milliseconds), 5 datacenter bits, 5 machine bits and 12 sequence bits.[1] The sequence number is a counter. It starts at 0 each millisecond and goes up by one for every ID that machine hands out in that millisecond.

12 bits hold the values 0 to 4,095. That's 4,096 IDs per millisecond per machine. The book stops there. But what does the code do when request number 4,097 shows up and the clock still reads the same millisecond?

Where this comes from. The book only gives the 4,096 limit. The wait-for-the-next-millisecond rule is what Twitter's original Snowflake code does: when the sequence would wrap inside the same millisecond, it spins until the clock moves on, then restarts at 0.[4] The cost is a stall of under a millisecond in an extreme burst. The gain is that it never hands out a duplicate.
2

Time runs backwards

NTP corrections and duplicate IDs

Snowflake trusts the clock. The book admits the weak spot in its wrap-up: it assumed every ID server has the same clock, and that isn't true once you have many machines.[1] Every computer's clock drifts (runs a little fast or slow). The usual fix is NTP, the Network Time Protocol: each machine regularly asks time servers for the correct time and corrects its own clock.[2]

Here's the catch. If a clock is running ahead, the correction can step it straight back. Your generator then re-enters milliseconds it has already used. Try it: each press mints one ID, and 1 ms passes between presses.

The real defences. (1) Remember the last timestamp. If the clock now reads earlier than that, refuse or wait until it catches up. Twitter's code throws an error that says the clock moved backwards and it refuses to make IDs for that many milliseconds.[4] (2) Tell NTP to slew: speed the clock up or slow it down a little until it's right, instead of jumping it. (3) Alert on big jumps, so a human finds out.
This really happens. At the leap second on 1 January 2017, Cloudflare's DNS code saw time go backwards. A duration came out negative and some servers crashed.[5] A leap second is an extra second added to official time now and then to keep clocks in step with the Earth's spin. It's the same bug class as a backwards NTP step.

Roughly in order

Clock skew between machines

Even with NTP, two machines' clocks never agree exactly. The gap between them is called clock skew, usually a few milliseconds. Since the timestamp is the first part of the ID, a machine whose clock is ahead stamps its IDs "from the future".

Roughly sortable. When Twitter announced Snowflake, it called the IDs "roughly sortable".[3] The project's README uses the term k-sorted: every ID sits close to its true position, but not always exactly there.[4] So "sorted by time" really means sorted to within the clock skew. Inside a single millisecond the machine bits decide the order, not real time. That's fine for a newest-first feed. It's not fine for "who clicked first", which needs a single sequencer (one place that numbers every event) or a logical clock.
4

Tune the bits

Section length tuning

The 41 | 5 | 5 | 12 split isn't sacred. The book's wrap-up says you can re-tune it. Its example: a long-lived, low-traffic system can take bits away from the sequence and give them to the timestamp.[1]

Think of the 63 usable bits as a budget shared by three needs. Lifetime comes from the timestamp bits. Fleet size comes from the datacenter and machine bits. Burst size comes from the sequence bits. One extra timestamp bit doubles the lifetime: 41 bits ≈ 69.7 years, 42 bits ≈ 139 years. Sony's Sonyflake counts time in 10 ms units instead, so 39 bits last about 174 years.[6]

The other two sections are set at startup. The book says datacenter and machine IDs are chosen when the system starts and normally stay fixed. Changing them needs careful review, because a slip can give two machines the same ID.[1] In practice they come from config or from a coordination service. Twitter's original Snowflake registered its workers in ZooKeeper, a service that hands out shared settings and locks.[4]

🎓 Level-up note (for later)

The book never says what happens past 4,096 IDs in a millisecond, or when a clock goes backwards. What you practised here comes from Twitter's original code: wait for the next millisecond, and refuse while the clock is behind.[4]

NTP keeps clocks within a few milliseconds of each other on a good network, not exactly together. Most NTP daemons slew small errors and only step large ones (ntpd's default step threshold is 128 ms).[2] Many big fleets also "smear" a leap second over several hours, so the clock never jumps. Systems that need tight time bounds use special hardware: Google's TrueTime uses GPS and atomic clocks. That's far more than this interview question needs.

About "multiple cores" in the book: on one machine, all cores normally read the same system clock. The real risk is several processes or threads on one machine using the same machine ID. Give each process its own worker ID, or share one generator behind a lock.
