Quest 6.5 · Design a Key-Value Store

Who Wrote Last?

Two replicas, two different values, one key. Meet the tiny list of counters that tells you which write came first — or proves nobody can tell.

🎯

Your win today: when an interviewer asks "two replicas accepted different writes to the same key — now what?", you can explain how a vector clock detects the conflict, who fixes it, and what that costs compared with plain last-write-wins.

Two truths at once

How replicas end up disagreeing
Remember Quest 6.1's sandbox? When you wrote to both sides of a split and healed it, the log said ⚔ CONFLICT: both sides were written during the split… and quietly kept the most recent write. The other write was thrown away. Today you pay that off: how a real store notices the conflict instead of guessing.

Copying data to several servers (replication) keeps the store available, but the copies can drift apart.[1] Here is the book's example: replicas n1 and n2 both hold name = "john". Two clients change it at the same moment, through different replicas.

2

Build a clock

Versioning and the vector-clock rule

The fix starts with versioning: every change creates a new, unchangeable version of the data instead of editing it in place.[1] Then each version gets a label that records its history — a vector clock.

A vector clock is just a list of [server, counter] pairs stuck to the data: D([S1, v1], [S2, v2], …). The rule when a write to D is handled by server Si:

  • If [Si, vi] is already in the clock → add 1 to vi.
  • If it isn't → add a new pair [Si, 1].

That's the whole rule. Send some writes through different servers and watch the clock 👇

Ancestor or conflict?

Compare two clocks at speed

Line two clocks up server by server. A missing pair counts as 0.[1]

  • X is an ancestor of Y (no conflict) if every counter in Y is ≥ the matching counter in X. Y already contains X's changes, so X can be thrown away. Book example: D([s0,1],[s1,1]) is an ancestor of D([s0,1],[s1,2]).
  • X and Y are siblings — a conflict — if X is ahead on some server and Y is ahead on another. Book example: D([s0,1],[s1,2]) vs D([s0,2],[s1,1]).

Six rounds, 12 seconds each. Answer in under 6 seconds for a +5 speed bonus. Running out of time costs no heart — just the XP.

When clocks get too long

The book's second downside: every new server that handles a write adds a pair, so the clock can grow. The fix is a size cap: past a threshold, drop the oldest pair. Dynamo keeps a timestamp on each pair to know which is oldest, and its example cap is 10.[2] Here a hot key has already been written through 10 servers during a messy outage.

📦 newest version Y10 / 10 pairs
🐢 An old copy still sits on a slow replica: X = D([S1,1]) — a true ancestor of Y.
Honest caveat — this is rarer than it sounds. The Dynamo paper admits truncation "can lead to inefficiencies in reconciliation" because ancestry can no longer be worked out accurately — and then says the problem had not come up in production, so Amazon never investigated it deeply.[2] Writes are normally handled by the same few servers, so clocks stay short.
5

Merge day

You are the client — reconcile the siblings

When two versions conflict, the store can't pick for you: it keeps both siblings and hands them to the next client that reads the key. That client — your application code — merges them and writes the result back.[2] Amazon's shopping cart does exactly this, with one hard rule: an "add to cart" must never be lost.

A read returns these two siblings of one shopper's cart:

Sibling A · 📱 phone

D([Sx,2],[Sy,1]) · 10:02:07
  • 📕 book
  • 🎧 headphones

Sibling B · 💻 laptop

D([Sx,2],[Sz,1]) · 10:02:05
  • 📕 book
  • 🖊️ pen
  • ☕ mug
Build the merged cart. Tap items to put them in (or take them out).
What really happened. Before the split the cart was D([Sx,2]) = 📕 book, 🖊️ pen. On the phone, the shopper added 🎧 headphones and removed 🖊️ pen → sibling A. On the laptop, they added ☕ mug → sibling B.

The merged version is D5([Sx,3],[Sy,1],[Sz,1]) — exactly Stage 3's D5. Notice the 🖊️ pen is back, even though the shopper deleted it. The client only sees two finished carts, not the steps that made them, so "A dropped the pen" looks identical to "B added a pen". Dynamo's paper admits it plainly: an add to cart is never lost, but deleted items can resurface.[2]

Last-write-wins (LWW) skips clocks and merging: every write carries a timestamp, and the newest timestamp simply wins. Cassandra works this way.[3] Sibling A (10:02:07) beats sibling B (10:02:05), so the cart becomes 📕 book, 🎧 headphones. The ☕ mug just vanished — no error, no sibling, nobody told. Simpler, but a real add-to-cart was silently dropped.

Honest caveat — "newest" depends on whose clock. LWW trusts timestamps from different machines, and machine clocks drift. A server whose clock runs a few seconds fast can make an older write "win".[5] Vector clocks avoid wall-clock time entirely: they only track who has seen what.

Vector clocks never lose a write — but they aren't free. The book lists two downsides; LWW is the simpler alternative.[1]

🎓 Level-up note (for later)

In practice conflicts are rare: over 24 hours, 99.94% of Amazon shopping-cart reads saw exactly one version, and most divergence came from many writers hitting one key at once (often automated clients), not from failures.[2] Later systems refined the idea: Riak 2.0 switched to dotted version vectors, which tag each sibling with the exact write that made it, to stop siblings piling up ("sibling explosion").[4] Even Dynamo let some services opt into last-write-wins — its session-info service did.[2]
