Beware the Spider Traps

Your spider runs. Now the web fights back: endless fake pages, copies of copies, and pages that are mostly junk. Plug new powers into the crawler without breaking it, dodge the traps, and close the interview with a strong wrap-up.

1

Snap-on modules

Extensibility · plug in, don't rewrite

Almost every system grows. Today the crawler fetches HTML. Next quarter someone wants images, or PDFs, or alerts. The book's answer is extensibility: design the crawler so a new content type is a new module (a self-contained piece of code) that you plug in. The core loop stays as it is.[1]

The book gives two examples. A PNG Downloader fetches PNG images. A Web Monitor watches the web for copyright and trademark infringement (someone using your content or your brand name without permission). 2

Into the spider trap

Infinite loops that look like pages

A spider trap is a web page or site that sends a crawler into an endless loop.[1][2] Every "page" is real enough to download, and every one links to yet another. The book's example is an endlessly deep folder path: /foo/bar/ links to /foo/bar/foo/bar/, which links one level deeper, forever. Some traps are made on purpose, to catch bots. Others are accidents, like a calendar with a "next month" link that never runs out.

Why a human? The book's point: traps are easy to spot (one site with an unusually large number of pages) but hard to catch automatically, because a huge real site looks the same from the outside. There's no one-size-fits-all fix. So a person checks the flagged site and either excludes it or writes a custom URL filter for it.[1] Real crawlers add more automatic guards too: a cap on pages per host, a cap on link depth, and tidying URL parameters. They still keep humans for the edge cases.
3

Trash, twins and noise

Three kinds of problematic content

The book sorts bad content into three kinds:[1]

  • Redundant content (duplicates). Nearly 30% of web pages are duplicates. A hash or checksum (a short fingerprint computed from the page's content) spots them: same fingerprint, same content. That's the Content Seen? box from Quest 9.2.
  • Spider traps. Endless loops of generated pages, from the last stage.
  • Data noise. Content with little or no value, such as ads, code snippets and spam URLs. It doesn't help the crawl, so exclude it where you can.

4

The page that builds itself

Wrap-up · rendering JavaScript and other extras

Many modern sites send the browser an almost empty page plus a script. The script builds the content, links included, after the page loads. Some pages also fetch more content in the background (that's AJAX: the page asks the server for data without reloading). A crawler that only downloads and parses the raw HTML never sees those links.[1]

The fix in the book's wrap-up is server-side rendering (also called dynamic rendering): run the page's scripts first, then parse the result. Try both on the same shop page.

Honest caveat. Running a browser for every page costs far more CPU and time than a plain fetch, so real crawlers render selectively, often in a later second pass. Google, for example, queues pages for rendering after crawling them.[4] Also, "dynamic rendering" today usually means something different: a website serving bots a pre-rendered copy. Google calls that a workaround it no longer recommends.[3] In the interview, say what you mean: "the crawler runs the page's JavaScript before parsing."

🎓 Level-up note (for later)

  • URL length only stops traps whose URLs grow. Calendars, session IDs and filter combinations like ?color=red&size=9&sort=price make endless URLs of normal length. Real crawlers also cap pages per host and link depth, and normalise or strip parameters.
  • An exact hash only catches exact copies. A printer-friendly page with a different header has a different hash. Real crawlers use near-duplicate fingerprints such as shingling or SimHash.[5]
  • "Noise" depends on the job. Code snippets are noise for a general web index and exactly what a code-search engine wants. That's why scoping comes first.
  • Rendering is expensive, so crawlers render selectively, and the book's "server-side rendering" means the crawler runs the scripts itself (see the caveat in stage 4).
