    Same URL twice

    Predict, then submit

    Step 2 of the flow looks small: "is this long URL already in the DB?" It decides what happens when two people shorten the same page. With the check, the same input always gives the same output. Engineers call that idempotent: doing it twice has the same effect as doing it once.

    The hidden cost of step 2. The check is a lookup by long URL, on every single shorten request. Without an index (a sorted lookup structure, like a book's index) on that column, the DB would scan the whole table each time. At billions of rows that's hopeless. Long URLs can run to thousands of characters, and many databases limit how long an indexed value can be. So a common trick is to store a fixed-size hash of the long URL in its own column and index that.
    Honest caveat. Some real products want a fresh link per user or per campaign, so each one gets its own click stats. Then you'd check "this long URL for this user", not the long URL alone. The book's version dedupes globally.
    3

    Bounce with a cache

    The redirect flow under load

    Now the other direction. Someone clicks https://tinyurl.com/zn9edcu. The book's redirect flow has five steps:[1]

    1. The user clicks the short link.
    2. A load balancer (a traffic cop that spreads requests across servers) sends it to one web server.
    3. If the short URL is in the cache (a fast in-memory copy), the server gets the long URL straight from there.
    4. If not, it reads the long URL from the DB. If the DB doesn't have it either, the user probably typed an invalid short URL.
    5. The long URL goes back to the user as an HTTP redirect, and the browser jumps there.

    Why a cache? Reads beat writes 10 to 1. In the book's estimate that's 11,600 reads/s against 1,160 writes/s.[1] Clicks are also lopsided: a few viral links get most of them. Pretend our single DB handles about 3,000 reads/s comfortably (a toy number). Drive the traffic and find out.

    Which redirect? Step 5 is either a 301 (permanent: the browser remembers it and later clicks skip your servers) or a 302 (temporary: every click comes back to you). A 301 cuts load. A 302 lets you count clicks. That was the choice in Quest 8.1.[5]
    Honest caveat: how big a cache? The book doesn't size it. A common rule of thumb is to cache the hot 20% of a day's reads. At about 1 billion clicks a day, that's a few tens of GB of mappings, which fits in a small Redis or Memcached cluster. Links are never edited or deleted in this design, so a cached entry can never go stale. Add "edit my link" and cache invalidation comes back.

    Honest caveat: sharding vs. step 2. Shard by short URL (or ID) and every redirect is a lookup on exactly one shard. But the shortening check, "is this long URL already stored?", doesn't know the short URL yet. So it needs its own index keyed by long URL (or its hash), sharded on that key.     🎓 Level-up note (for later)

    • The step-2 race. Two people shorten the same new URL in the same millisecond. Both checks say "not found" and both insert, so you get two rows. A unique constraint on the long-URL hash makes the second insert fail, and that request then reads back the winner's short URL.
    • Replica lag. If the DB copies to replicas asynchronously (in the background, after confirming the write), a link you just created can briefly 404 when the click is read from a replica that hasn't caught up. Fixes: read your own new writes from the primary, or write the new mapping into the cache at create time.
    • Cold cache after a failure. A replaced cache node starts empty, and every click on it falls through to the DB until it warms up. You saw this in the warm-up seconds of stage 3. Replicated caches and DB headroom soften it.
    • Long-URL index under sharding. See the stage 4 caveat: redirect lookups shard by short URL, dedupe lookups need a second index sharded by long-URL hash.
