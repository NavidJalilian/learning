Why send a spider?

Four jobs a crawler does

A web crawler (people also say robot, bot or spider) is a program that finds new and changed content on the web: pages, images, videos, PDF files. It starts from a handful of pages, reads the links on them, follows those links to more pages, and keeps going.[1][2]

The book lists four reasons to run one. Each card below describes a real-world job. Drag it into the right basket, or just tap a basket. Every correct card moves the spider one knot along its thread.

The book's real examples. Indexing is the most common use: Googlebot is the crawler behind Google Search. Archiving: national libraries such as the US Library of Congress, and the EU's web archive, save sites before they change or vanish. Mining: finance firms download shareholder-meeting transcripts and annual reports to learn about companies. Monitoring: Digimarc runs crawlers that hunt for pirated copies of works and reports on them.[1]
How hard is it to build? That depends on scale. A class project crawler is an afternoon's work. A crawler for the whole web keeps a dedicated team busy.

The three-step loop

Watch the frontier grow

The web is a graph: each page is a node (a dot) and each link is an edge (an arrow from one page to another). Crawling means walking that graph, which is called graph traversal. The book's basic algorithm is a three-step loop:[1]

  1. Download the pages for a set of URLs.
  2. Extract the URLs (links) found inside those pages.
  3. Add the new URLs to the list still to be downloaded. Go back to step 1.

The URLs you start with are called seed URLs. Here the only seed is page A. Drive the loop yourself with the three buttons. The glowing button is the next step.

Ask before you crawl

Step 1 · scope the prompt

The interviewer says only: "Design a web crawler." That sounds simple, but a crawler for a school project and one for a search engine are completely different machines. Step 1 of the interview framework is to ask until you know which one you're building.

    Four traits of a good spider

    Scalable · robust · polite · extensible

    Besides the features the interviewer asked for, the book names four qualities a good crawler needs:[1]

    • Scalable: the web has billions of pages, so one machine fetching one page at a time is hopeless. The work must run in parallel (many fetches at once, on many machines).
    • Robust: the web is full of traps. Broken HTML, servers that never answer, crashes, malicious links. The crawler must survive all of them.
    • Polite: don't send a single website too many requests in a short time. A crawler that floods a small site can knock it offline.
    • Extensible: adding a new content type (say, images) should need small changes, not a rewrite.

    Notice the odd one out. Scalable, robust and extensible are about our system: can it grow, can it survive, can it change. Politeness is about other people's systems. The site you crawl never agreed to carry your load, and the web has a convention for this: a site lists what bots may fetch in a file called robots.txt.[5] Quest 9.3 builds politeness into the queue design, and 9.4 reads robots.txt.

    Napkin math

    Back-of-the-envelope, then twist the knobs

    A back-of-the-envelope estimate is a rough calculation you do out loud in a minute or two. It tells you how big the system is, so you know which problems are real. QPS means queries per second; for a crawler, that's pages downloaded per second. The book works from these assumptions:[1]

    📌 1 billion pages / month📌 HTML only📌 keep 5 yearsavg page = 500 KBpeak = 2 × average

    Work out the four numbers. Anything within about ±10% counts, so round freely. Pick a unit (K = thousand, M = million; 1 TB = 1,000 GB, 1 PB = 1,000 TB) or type the full number. Hints are free.

    Interview tip. A 30-day month is 30 × 24 × 3,600 ≈ 2.6 million seconds. One billion ÷ 2.6 million is about 386, and the book rounds that to 400. Rounding up is fine. Say each assumption out loud as you go: the interviewer grades the reasoning, not the decimals.

    Mini-challenge · bonus

    A real HTML page is often closer to 100 KB than 500 KB. Keep 1 billion pages and 5 years, and drag the page size to 100 KB. What happens to the 5-year total?

    💡 30 PB became 6 PB. Storage is pages × size × months, so it moves in a straight line with each one: a fifth of the size gives a fifth of the storage. Page count and years work the same way. That's why you say the size assumption out loud: change it and the storage answer changes by the same factor.
    Side note: how many machines? The book stops at QPS and storage, but a natural follow-up is "how many download servers?". If you assume one server fetches about 50 pages a second (a made-up round number, not from the book), peak needs 800 ÷ 50 = 16 servers, before you add spares for failures. Watch the last tile change as you turn the knobs.
    Honest caveats. "Peak = 2 × average" is a rule of thumb. A crawler sets its own pace, so its peak is mostly a choice; the harder problem is uneven load on individual sites (politeness again). And 500 KB is generous for HTML alone, which compresses well, so 30 PB is an upper bound before compression and duplicate removal.

    🎓 Level-up note (for later)

    • 386, not 400. 1 billion ÷ 2.59 million seconds is about 386 pages/s. The book rounds up to 400, and interviewers expect that.
    • Peak is a choice. A user-facing service can't control its traffic spikes; a crawler can. "2 × average" is a rule of thumb. The real risk is too many requests to one host, not total load.
    • 500 KB is generous. Many HTML documents are tens of KB and compress well, so 30 PB is an upper bound before compression and de-duplication.
    • Real crawls are bigger. One billion pages a month is an interview-sized target, not Google's. The open Common Crawl project alone publishes a few billion pages per crawl, and you can download and inspect them.[4]
