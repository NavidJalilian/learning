Faster Than a Keystroke

In 13.1 you counted ~48,000 requests a second at peak and a 100 ms budget. In 13.2 and 13.3 you grew a trie and stored it. Now follow one keystroke from the browser to the dropdown, and learn the tricks that keep it fast and safe.

🎯

Your win today: you can trace one keystroke through load balancer → API servers → Trie Cache (→ Trie DB on a miss), name the three speed tricks (AJAX, browser caching with Cache-Control: private, max-age=3600, data sampling) and their costs, and explain how a filter layer hides harmful suggestions right away while the database is cleaned in the background.

Follow one keystroke

The read path, hit and miss

The book's improved query service has four steps.[1]

  1. The query goes to a load balancer: a box that spreads incoming traffic across many servers.
  2. The load balancer sends it to one of the API servers.
  3. The API server reads the trie from the Trie Cache (a copy of the trie kept in memory, spread over several cache servers) and builds the suggestions.
  4. If the data isn't in the cache (a cache miss), it is loaded from the Trie DB (the trie's permanent storage, from Quest 13.3) and written back into the cache. The next request for that prefix is fast again.

Misses happen when a cache server runs out of memory or goes offline. Your job: predict the path before each run. Tap the boxes in the order the request visits them (a box can be visited twice), then press Run.

    Three speed tricks

    AJAX and the browser cache

    For autocomplete, speed comes first. The book adds three optimizations.[1] Data sampling gets its own stage next. Here are the first two.

    Trick 1: AJAX. AJAX is a way for a web page to send and receive data in the background, without reloading the whole page.[5] Type a letter and compare.

    Trick 2: browser caching. Suggestions for a prefix rarely change within a short time. So the browser keeps each answer and reuses it. The book shows that Google answered autocomplete requests with this response header:[1]

    • private: only this user's own browser may store the answer. Shared caches (an office proxy, a CDN) must not.[2]
    • max-age=3600: the stored answer stays fresh for 3,600 seconds = 1 hour. After that the browser asks the server again.

      Log 1 in N
      Data sampling, and what it loses
      
    
      
      
      Trick 3: data sampling. Every search is also written to a log, so the weekly trie build (Quest 13.3) can count it. At this scale, logging every search costs a lot of processing power and storage. The book's fix: log only 1 out of every N requests.[1] To estimate a real count, multiply the logged count by N.

      Honest caveat. Sampling keeps the ranking of popular queries and distorts rare ones. That's fine for "top 5 by popularity". It's wrong for anything that needs exact counts, like billing or a long-tail report. At very large N, two popular queries with close counts can also swap places.
      
    
      
  
      

  
  
      
    
      4
      The filter layer
      Deleting what must never appear
      
    
      
      
      Some suggestions must go: hateful, violent, sexually explicit or dangerous ones. The book puts a filter layer in front of the Trie Cache, between the API servers and the cache. It drops unwanted suggestions before they reach the user. Because it's a separate layer, you can swap in different filter rules.[1]

        Notice the dropdown can show fewer than 5. The cache stores each prefix's top 5. If the filter drops 2, the user sees 3 until the trie is rebuilt. Keeping a few spare entries per node would let you backfill. That's an extra idea, not from the book.
        

      
        The filter only hides the entries. The book also physically removes them from the database asynchronously (in the background, not on the request path). That way the next weekly build uses a clean data set.[1] Why do both? Play one week of each plan. A harmful suggestion is reported on Monday.

And a removed suggestion can still sit in a browser cache for up to an hour (stage 2).

        🎓 Level-up note (for later)
        
      
          
        
        • The Google header. private, max-age=3600 is what the book observed at the time. Real services tune it and may change it. Talk about the technique, not the exact value.
          • 
        
        • Sampling bias. 1-in-N keeps popular rankings and blurs the long tail. Rare queries can vanish from the sample or show up with a count of N. Fine for top-5-by-popularity, wrong for exact counts.
          • 
        
        • Moderation. The book's filter layer is a blocklist. Production systems add classifiers, human reviewers, appeal paths and per-region rules.
          • 
        
        • Stale copies. Browser caching means a removed suggestion can linger in a user's browser for up to max-age. It's a small consistency cost. Name it if the interviewer asks about takedowns.
          • 
        
        • Cold caches. When a fresh weekly snapshot replaces the cache, every prefix starts as a miss. A common fix is to load (warm) the new cache before switching traffic to it. That's general practice, not from the book.
