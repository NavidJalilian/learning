Quest 13.4 · Design a Search Autocomplete System

Faster Than a Keystroke

The trie is built and the weekly pipeline keeps it fresh. Now the hot path: every key a user presses has to come back as five suggestions before the next key lands. Follow one request, then make it faster, cheaper and safer.

🎯

Your win today: you can trace one keystroke through load balancer → API servers → Trie Cache (→ Trie DB on a miss), name the three speed tricks (AJAX, browser caching with Cache-Control: private, max-age=3600, and data sampling) and what each one costs, and explain how a filter layer hides harmful suggestions right away while the database is cleaned in the background.

1

Follow one keystroke

The read path, hit and miss

The query service is the part that answers "what are the top 5 for this prefix?" The book's improved version has four steps:[1]

  1. The request goes to a load balancer, a box whose only job is to spread traffic across many servers.
  2. The load balancer sends it on to one of the API servers.
  3. The API server reads the prefix's top 5 from the Trie Cache, a copy of the trie kept in memory so reads are fast.
  4. If the cache doesn't have that data (a cache miss), the API server reads it from the Trie DB on disk and writes it back into the cache. The next request for that prefix is a hit again.

Misses happen when a cache server runs out of memory or goes offline. Below, type a prefix. Before each run, tap the boxes in the order you think the request visits them. Then send it.

Why the gap is so big. Reading memory takes well under a microsecond. A disk-backed database read takes milliseconds, plus a network hop. The numbers here are toy values, but the shape is real: a miss can be ten times slower than a hit. That's why the miss writes the answer back. One slow request pays so that every later one is fast.
2

Speed tricks

AJAX and the browser cache

For autocomplete, speed is the top priority. The book adds three optimizations on top of the read path.[1] This stage covers the first two, and stage 3 covers the third.

  • AJAX request. AJAX stands for "Asynchronous JavaScript and XML". The page sends the request in the background and updates only the dropdown. The rest of the page is never reloaded.
  • Browser caching. The top 5 for "din" won't change in the next few minutes. So the browser keeps each answer and reuses it. The book's example is a header Google sent at the time: Cache-Control: private, max-age=3600.

Log 1 in N

Data sampling, and what it loses

The third trick is on the logging side. Every search gets written to the analytics log so the weekly job can count popularity. Logging every single search takes a lot of processing power and storage. With data sampling, the system logs only 1 out of every N requests.[1]

That's fine for a "top 5 by popularity" product. It would be wrong for billing, fraud checks, or anything else that needs exact counts.
4

The filter layer

Deleting what must never appear

Some suggestions must never be shown: hateful, violent, sexually explicit or dangerous ones. The book's fix has two parts:[1]

  • A filter layer sits in front of the Trie Cache, between it and the API servers. It drops unwanted suggestions on the way out. Because it runs on rules, you can swap in different rules without rebuilding anything.
  • The unwanted entries are also physically deleted from the database, asynchronously (in the background, not while the user waits). That way the next weekly build of the trie starts from clean data.

    🎓 Level-up note (for later)

    • The header is an example. private, max-age=3600 is a snapshot from when the book was written. Name the technique in an interview, not the vendor.
    • Sampling skews the tail. It keeps popular rankings and distorts rare queries. That's right for top 5 by popularity and wrong for anything that needs exact counts.
    • Moderation is bigger than a filter. Google's published autocomplete policies describe automated systems plus enforcement teams and user reports on top of rules.[3]
    • Caching vs takedowns. With browser caching, a removed suggestion can linger in a user's browser for up to max-age. A shorter max-age shrinks that window but sends more requests to the server. Say this trade-off out loud.
