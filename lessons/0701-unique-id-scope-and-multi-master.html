Quest 7.1 · Design a Unique ID Generator

Numbers Nobody Repeats

Every tweet, order and user needs a name nobody else has. On one database that's free. Spread the data over many servers and the easy answer starts handing out duplicates.

🎯

1

One counter, many servers

Why the easy answer stops working

A unique ID is the number that names one row: one user, one tweet, one order. It's usually the table's primary key (the column the database uses to find and tell rows apart).

On a single database you get this for free. Mark the column auto_increment and the database hands out 1, 2, 3… It can never repeat, because one machine owns the one counter.

The chapter opens by saying this stops working in a distributed system. One database server isn't big enough, and generating IDs across several databases with very little delay is hard.[1] So you split the users table into two shards (a shard is one slice of a table, living on its own database server). Each shard keeps its own auto_increment.

        Count by k

        Multi-master replication, hands-on

        The book's first idea keeps auto_increment but changes how it counts. With k database servers, each one steps by k instead of 1, and each one starts at a different offset. With k = 2, server A issues 1, 3, 5, 7… and server B issues 2, 4, 6, 8…. Their numbers can never meet.[1]

        The book calls this multi-master replication: several writable databases (all "masters", or primaries), each issuing its own IDs. MySQL has a setting for each knob: auto_increment_increment is the step, auto_increment_offset is the start.[2]

        Tap a server to ask it for the next ID. Every ID lands on the timeline in the order it was made.

        The book's three drawbacks of multi-master:[1]
        1. It's hard to scale across several data centers. Every server everywhere has to agree on k and its offset.
        2. IDs don't go up with time across servers. You saw 2 arrive after 5.
        3. It doesn't scale well when a server is added or removed. Changing k means re-planning everyone.

        🎓 Level-up note (for later)

        • "Ordered by date" is really "roughly ordered". The book asks for IDs sorted by time. No real system can promise exact time order across machines, because their clocks never agree perfectly. What you can actually get is roughly time-ordered IDs. Quest 7.4 digs into this.
        • The name is a bit misleading. The trick here is two config settings, not replication itself. It's named after the setup where it's usually used: several writable primaries copying data to each other, which must not hand out the same key. Flickr used the same two settings on its pair of ticket servers: one issues only odd numbers, the other only even.[3]
        • Live reconfiguration is messier than the sim. Changing auto_increment_increment on a running MySQL server doesn't renumber old rows. The next value is the smallest number in the new series that's bigger than the current maximum in the column.[2] The sim simplifies this, and the "re-plan" step shows the safe pattern: change every server together and start above the highest ID already issued.
