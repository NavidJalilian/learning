Boss: the curveball barrage

Step 3 · "what happens when…?"

Now the interviewer starts poking holes. Eight curveballs. For each one, pick the kind of fix a senior engineer reaches for. Every card then names the exact mechanism, so read the "why".

Honest caveats from the barrage. (1) Twitter's original Snowflake refused to mint IDs while its clock was behind the last timestamp it had used. It logged an error and rejected requests until time caught up[9]. Waiting a few milliseconds instead is a common variant. (2) NTP can either step a clock (jump it) or slew it (run it slightly fast or slow until it's right). Slewing never moves time backwards, which is why ID generators prefer it[5]. (3) JavaScript numbers are exact only up to 253 − 1[8]. That's why APIs that hand out Snowflake IDs also send them as strings.

🎓 Level-up note

The book's answer is from 2010. If an interviewer allows 128 bits, UUIDv7 is a strong modern answer. It puts a 48-bit millisecond timestamp in front of random bits, so it is time-ordered and needs no machine IDs[6]. Other real options: Sonyflake (a Snowflake variant with 10 ms ticks and a longer lifetime), and database sequences that hand out ranges of IDs to each server. On high availability, the book gives one line. In practice the simplest design is a generator library embedded in every service: no network hop, nothing to go down, with machine IDs assigned at deploy time.
