Six hops to Bob

The 1-on-1 chat flow

In Quest 12.2 you met the parts. Now watch them work together. The book traces one message from Alice (user A) to Bob (user B) in six steps, with a fork at step 5: one branch if Bob is online, one if he isn't.[1]

One new term. The message sync queue is a queue that sits between the chat server and the rest of the system. The chat server drops the message on it and moves on; the queue gets it stored and on its way to Bob. That way the chat server isn't stuck waiting.

Honest caveat: how does chat server 1 find Bob? The book's step 5a just says the message goes to the server Bob is connected to. It doesn't say how anyone knows which server that is. Real systems keep a lookup table of user → server (often in Redis), or have each chat server subscribe to a per-user topic, so a message for Bob lands wherever Bob happens to be.
2

Many devices, one account

cur_max_message_id

Alice has a phone and a laptop. Each one opens its own WebSocket to a chat server (maybe different servers). So how does the laptop catch up after a night asleep?

The book's answer: each device keeps one number, cur_max_message_id, the highest message ID it already has. A message is new for that device when two things are true:[1]

  • it was sent to the logged-in user (Alice), and
  • its ID in the KV store is greater than that device's cur_max_message_id.

Because every device has its own cursor (a bookmark of "where I'm up to"), sync is simple. A device that wakes up asks for everything above its bookmark. Try it: close the laptop, let messages arrive, then predict what it fetches.

Honest caveat: one cursor needs one sequence. A single cur_max_message_id only works if every message to Alice gets an ID from one rising sequence. In Quest 12.3 the book lets IDs be unique only within one chat (a local sequence). Then "ID > 105" means nothing across chats, and a device needs one cursor per conversation, or the server keeps a per-user inbox sequence. The book glosses over this mismatch. It's a great thing to spot out loud.
3

Small-group fan-out

One inbox per recipient

Alice posts in a group with Bob and Carol. The book's design copies the message into each member's message sync queue: one copy for Bob, one for Carol. Think of each member's sync queue as their personal inbox.[1] Copying one event out to many destinations is called fan-out.

The book gives two reasons this suits small groups. Sync stays simple, because each client only ever checks its own inbox. And when the group is small, one copy per member is cheap. WeChat does something similar and caps groups at 500 members. Drag the slider to see where "cheap" stops being true.

Numbers to anchor on. The book's own requirements cap group chats at 100 members, and WeChat's cap is 500. At those sizes a copy per member is a few hundred writes at most. The book stops at "a copy per member is not acceptable for big groups". The usual fix, which goes past the book, is to store the message once per channel and have members read the channel (fan-out on read). Discord, for example, stores messages per channel.[2] Group caps change over time and by product. WhatsApp has raised its limit more than once. The principle is what matters: copying per member only stays cheap while groups are small.
4

When delivery fails

Retry, queue, and don't double-post

Networks drop things. The book's wrap-up names the two standard ways to resend a message: retry and queueing.[1] Retrying brings a new risk: the same message can arrive twice. That's called at-least-once delivery.

The rest of this stage goes past the book. In an interview, say so ("beyond the basic design…"). Three rules make retries safe:

  • Ack only after storing. An ack (acknowledgement) is the server's "got it". Send it only once the message is safely in storage.
  • The client stamps every message with its own ID (a client_msg_id) before the first try, and reuses it on every retry.
  • The server dedupes on that ID. If it has already stored that ID, it skips the write. That makes the send idempotent: doing it twice has the same effect as doing it once.

Honest caveat: "exactly once" is a myth. Over a real network you can't guarantee a message is delivered exactly once. What chat apps really do is at-least-once delivery plus deduplication. To the user that looks exactly like exactly-once.

🎓 Level-up note (for later)

  • When does Alice see "sent"? The book's figure doesn't say whether step 3 (queue) or step 4 (store) must finish first. Real systems ack the sender only after the message is durably stored (or durably queued), then deliver.
  • Routing to Bob's server needs a user → server lookup (often Redis) or a per-user pub/sub topic. The book leaves it out.
  • Cursors need one sequence. With per-chat IDs, a device keeps a cursor per conversation, or the server gives each user's inbox its own rising sequence.
  • Huge groups flip to fan-out on read: one stored copy per channel, and each member keeps a "last read" pointer into the channel. That's the same cursor idea as stage 2, applied per channel.
