Majority Rules

Three numbers — N, W and R — decide whether your reads are fast, your writes are fast, or your data is never stale. Turn the dials, race the clock, and find the overlap.

🎯

Your win today: when an interviewer asks "how do your replicas stay consistent?", you can explain N, W and R in plain words, say why W + R > N guarantees a fresh read, name what it costs (waiting), and pick a setting for a given product.

1

Meet the coordinator

N replicas, and what W really means

In Quest 6.3 every key got copied to several servers. Copies only help if they agree, so the book uses quorum consensus — a voting rule that says how many copies must answer before a request counts.[1] It has three numbers:

  • N — how many replicas (copies) each key has. Usually 3.
  • W — the write quorum: a write counts as successful once W replicas confirm ("ack") it.
  • R — the read quorum: a read waits for answers from at least R replicas.

The client never talks to the replicas directly. It talks to a coordinator — the node that receives the request and forwards it to the replicas, like a proxy.[2] Change W and send a few writes. Watch where the data goes, and when the client hears "OK".

Race the clock

Speed vs. freshness

Every replica sits at a different distance from the coordinator, so its answer takes a different time (shown under each node in milliseconds). The coordinator can only reply once it has heard from enough replicas — so a request is as slow as the slowest replica it has to wait for.[2]

That is the trade-off: W = 1 or R = 1 is fast (wait for anyone). Bigger W or R gives better consistency, but you wait longer.[1] Now you have all three dials. Tap a replica to make it slow or knock it out.

  • ✓Write with W = 1 and note the clock
  • ✓Write with W = N (all replicas) and compare
  • ✓Make a replica 🐢 slow, then write with W = N again
  • ✓Do a read with R = 2 or more

Find the overlap

Why W + R > N means a fresh read

Here's the core rule: if W + R > N, every read sees the latest successful write.[1] Why? The W replicas that confirmed the write and the R replicas you read from can't all be different people — there aren't enough replicas. At least one replica is in both groups, and it holds the new value.

WW+RR

N = 3, W = 2, R = 2 → 2 + 2 = 4 seats for 3 replicas → one must sit in both.

SettingWhat you get
R = 1, W = NFast reads (writes wait for everyone)
W = 1, R = NFast writes (reads wait for everyone)
W + R > NStrong consistency — usually N = 3, W = R = 2
W + R ≤ NStrong consistency not guaranteed

Five rounds. Read the setup, predict, then watch. When the coordinator gets several answers, it returns the one with the highest version number. (How real systems compare versions is Quest 6.5.)

🔁 Remember Quest 6.1's caveat? There, the book's CP system blocked every node during a split. You were promised that many real systems keep the majority side working. You just saw it: with N = 3, W = 2, R = 2, the side with s0 + s1 can still gather 2 acks and 2 answers, so it keeps serving. A client stuck on s2's side can never collect 2 votes, so its requests fail. That side can't serve data it can't vouch for.
Honest caveat — "W + R > N" is the ideal case. Kleppmann's Designing Data-Intensive Applications (ch. 5, "Limitations of Quorum Consistency") lists edge cases where even W + R > N can return a stale value:[4] a sloppy quorum may write to stand-in nodes outside the usual N (Quest 6.6). Concurrent writes need a rule to pick a winner (Quest 6.5). And a write that failed (too few acks) is not rolled back on the replicas that did store it, like s0 and s1 in round 4. So treat the rule as a strong guarantee about overlap, not an absolute promise.

How fresh is fresh?

Consistency models & tunable consistency

A consistency model is the promise a store makes about what a read can return. The book names three:[1]

💪

Strong

A read always returns the most recent write. A client never sees old data.

?
🌫️

Weak

Later reads may not see the newest value, with no promise about when they will.

?
⏳

Eventual

A kind of weak: given enough time, every update reaches every replica and they all agree.

?

Strong consistency usually means a replica won't accept new reads or writes until every replica agrees on the current write. That stalls requests whenever a node is slow or unreachable, so it's a poor fit for a highly available store. Dynamo and Cassandra choose eventual consistency, and so does the book for this design.[1]

Tunable consistency: choose per request

Real stores don't hard-wire W and R. The caller picks them per request. This is called tunable consistency. In Cassandra you set a consistency level: ONE, QUORUM (a majority, N/2 + 1, rounded down) or ALL.[3] Tap one (3 replicas):

Pick W and R for real products

Then read §4.5 of the Dynamo paper (how the coordinator runs get and put, one page) and the start of §6. 🎓 Level-up note (for later)

The book says "quorum consensus", but Dynamo-style quorums are not a consensus algorithm like Raft or Paxos. They don't make all replicas agree on one order of writes, and Kleppmann shows that even W + R > N isn't enough for the strictest kind of consistency (called linearizability) when network delays vary (DDIA ch. 9).[4] If an interviewer pushes on "is it really strongly consistent?", that's the senior answer: "the overlap guarantees you see the latest acknowledged write in normal operation, but not under every race."
