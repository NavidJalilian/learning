Slice by first letter

The naive shard

By the end of 13.4 the design works. A trie (a tree of letters where each path spells a prefix) keeps the top 5 queries for every prefix, and the query service reads it fast. But the data keeps growing, and one day the trie no longer fits on one server. Time to shard it: split the data across several servers, so each one holds a slice.[1]

The book starts simple. In 13.1 we agreed on English only, lowercase a–z. So shard on the first character of the query. With 2 servers, one takes a–m and the other n–z. With 3: a–i, j–r and s–z. Going one letter deeper. The book calls the first-character split first-level sharding. There are only 26 letters, so it stops at 26 servers. To go past that, shard on the second or even third character. The book's example spreads the queries that start with 'a' over 4 servers: aa–ag, ah–an, ao–au and av–az.[1]
Honest caveats. The letter shares here are made up for the sim, but the shape is realistic: far more English words start with 'c' or 's' than with 'x'. Real query mixes vary by product and language. The sim also assumes a split letter divides its traffic evenly (sa–sm gets as much as sn–sz). In real data, second letters are lopsided too.

The shard map manager

Balance by history, not by alphabet

Stage 1's problem: the alphabet picked the boundaries, but the data is lopsided. The book's fix is to study the historical data: how many queries started with each letter in the past. Then draw the boundaries to match. A component called the shard map manager keeps a lookup database that records which shard holds which prefixes.[1]

Honest caveat. The shard map manager is now on the path of every read and every write. In a real system you would cache the map on each web server and replicate the lookup database, so it can't become a bottleneck or a single point of failure. When the traffic mix shifts, you update rows in the map and move the affected data. The code that routes requests stays the same.

Beyond English

Languages and countries

In step 4 of the interview (the wrap-up), the book lists three follow-up questions an interviewer might ask. Here are the first two:[1]

  • "How would you support other languages?" Store Unicode characters in the trie nodes. Unicode is the encoding standard that gives a number (a code point) to every character in the world's writing systems, modern and ancient.[2]
  • "What if the top queries differ by country?" Build a different trie for each country. To cut response time, store the tries in CDNs (content delivery networks: servers spread around the world so each user is served from one nearby).

Honest caveats. (1) 13.1's storage estimate assumed 1 byte per character. In UTF-8, the most common way to store Unicode text, a character takes 1 to 4 bytes. 4

Trending now

When the news breaks

The third follow-up: "How do you support trending, real-time queries?" A news story breaks and one query suddenly takes off. The book says our design fails here for two reasons. First, the offline workers that rebuild the trie only run once a week (13.3), so they aren't due yet. Second, even if they ran now, building the whole trie takes too long.[1]

The book calls a real-time version beyond its scope, but it gives three ideas:

  • Shrink the working data set by sharding. A small shard rebuilds much faster than the whole trie.
  • Change the ranking model so recent searches count for more than old ones.
  • Treat the data as a stream. Streaming data is produced continuously, so you never have all of it at once. That needs different tools, such as Apache Hadoop MapReduce[4], Apache Spark Streaming[5], Apache Storm[6] and Apache Kafka[7].

    🎓 Level-up note (for later)

    • Hashing is an option too. The trie is stored in a key-value store keyed by prefix (13.3), so hashing each prefix onto shards (World 5's consistent hashing) would spread load evenly. The cost: one subtree ('s', 'su', 'sun') ends up on many machines, so building or updating a branch touches many shards. The book keeps letter ranges and balances them with the map manager.
    • Real-time is its own system. Production autocomplete usually runs a fast path for fresh queries alongside the batch trie and merges the two at query time. The book's three ideas are the right ingredients, but there's no single "rebuild from a stream" switch.
    • Unicode costs bytes. UTF-8 uses 1–4 bytes per character, so 13.1's "20 bytes per query" holds only for plain English.
    • Per-country tries cost storage. N countries means roughly N tries. Smaller countries often share a regional or global trie.
