Slice by first letter

The naive shard

In Quest 13.3 the whole trie lived in one Trie DB, and in 13.4 one Trie Cache served it. At some point it won't fit on one machine. So you shard it: split the data across several servers, each holding one slice.

The book's first idea for an English-only system is simple: split by the first character of the query.[1] Below, the purple bars show what share of searches start with each letter. Past 26, go one letter deeper. With first-letter sharding you run out at 26 servers. After that you shard on the second (or third) character. The book's example splits the "a" queries over four servers: aa–ag, ah–an, ao–au, av–az.[1] But the big lesson is in the gauges: far more words start with c or s than with x, so equal slices of the alphabet are not equal slices of the work.

The shard map manager

Balance by history, not by alphabet

Fixed letter ranges ignore how people actually search. The book's fix: shard by the historical data distribution, meaning how many queries each prefix got in the past.[1] Slices no longer follow a neat rule, so something has to remember who holds what. That's the shard map manager: a small lookup database that maps each prefix range to a shard.

First, the book's example. Suppose "s" gets about as many queries as several quiet letters put together. Pile letters onto the right pan until the scale balances.

Now balance four shards. They start with plain alphabet ranges. Move letter tiles until every shard is under the line, which sits at 110% of the average load. Tap a tile, then tap a shard (or drag it on a computer). Tiles don't need to stay in alphabet order. The map remembers.

The trade-off to name. The map is one more moving part. It must be fast (every request reads it), highly available, and updated carefully when a range moves between shards. In practice servers cache the map, so most lookups never leave the API server.

Beyond English

Languages and countries

The book's wrap-up asks two "what if" questions about going global.[1]

Follow-up 1: other languages. Store Unicode characters in the trie nodes. Unicode is the standard that gives a number (a code point) to every character in every writing system, current or historical.[2] A node can then no longer keep exactly 26 child slots, one per letter. Try it.

Follow-up 2: different countries. People in different countries search for different things. So build a separate trie per country, and store those tries in CDNs (content delivery networks: servers spread around the world, close to users) so suggestions arrive faster.[1]

Which fix does each situation need?

Honest caveats. Unicode breaks the "1 byte per character" estimate from Quest 13.1: UTF-8 stores a character in 1 to 4 bytes (é takes 2, カ takes 3). And one trie per country multiplies storage by the number of countries. You trade disk for lower latency and more relevant results.
4

Trending now

When the news breaks

Follow-up 3: real-time trending queries. A volcano erupts on Tuesday morning. Millions of people type "vo…". Our design rebuilds the trie once a week, on Sunday. The book says the design fails here for two reasons: the offline workers aren't scheduled to run yet, and even if they ran, building the whole trie takes too long.[1]

The book sketches three ideas. 1. Shrink the working data set by sharding, so each piece rebuilds faster. 2. Change the ranking model to give recent searches more weight. 3. Treat the data as a stream: it arrives continuously and you never have all of it at once. That needs different tools, such as Apache Hadoop MapReduce,[3] Spark Streaming,[4] Storm[5] and Kafka.[6] The book stops there and calls the details out of scope.

    🎓 Level-up note (for later)

    Range vs hash sharding. You could hash each prefix to a shard instead. That spreads load evenly with no map, and it works fine for point lookups like "give me the top 5 for vol". The cost: a letter's whole subtree no longer lives on one server, so the simple "letter → shard" rule is gone and a worker can't rebuild one shard's trie on its own. The book picks letter ranges plus a shard map manager, and naming that trade-off is what an interviewer wants to hear.

    Trending in practice. The book's three ideas are a sketch. Production systems commonly run two paths: the big batch trie for long-term popularity, plus a small real-time index fed by a stream (often Kafka) that counts the last minutes or hours. At query time they blend the two lists, with a time-decay score so fresh spikes can rise and fade.

    Countries × shards. Per-country tries and per-letter shards multiply together. Ten countries with 26 shards each is 260 pieces to build, ship to CDNs and keep in sync. Many countries share a language, so some designs build per-language tries and add a small per-country boost on top.
