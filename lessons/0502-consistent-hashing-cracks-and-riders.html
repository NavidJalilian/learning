Crack #1: the lopsided ring

Uneven partitions, with real numbers

Quick recap of the basic ring from Quest 5.1: hash every server and every key onto one circle. A key belongs to the first server clockwise from it.[1]

A server's partition is the stretch of ring between it and the server before it (anticlockwise). Every key in that stretch is its job. You'd like every partition to be the same size. The book's first problem: you can't keep them the same, because you don't choose where a server lands. The hash of its name does. And servers come and go.[1]

Step 1 · Start perfect, then lose a server

That's the book's example. Start perfectly even, remove one server, and its whole partition is handed to the next server clockwise. That neighbour now owns 50%, twice as much as anyone else.[1] No key moved that didn't have to. It's just that they all moved to the same place.
You can't drag in production. A server's spot is hash(name). The hash has never heard of "the gap". It drops the new server somewhere random, which usually isn't the middle of the big arc. Any balance you had came from luck, and luck runs out every time a server joins or leaves.

Crack #2: unlucky keys

Uneven key distribution, and the hot key the ring can't fix

The book's second problem: even if every arc is exactly the same size, the keys themselves can bunch up. A key's position is a hash, so it lands at a random spot. With few keys, one server can catch most of them while another catches none.[1]

This crack heals itself as data grows. Key-count noise shrinks like 1/√(keys per server). With 1,000 keys each, a server is typically about 3% off average. With millions of keys it's a rounding error. At real scale, what's left is crack #1: the size of the arcs.

A different problem: the celebrity key 🌟

So far we counted keys. But servers don't melt from storing keys. They melt from requests. The book's wrap-up says consistent hashing helps with "hotspot" keys (for example, a few celebrity accounts all landing on one shard) by spreading data more evenly.[1] That's true when the heat is spread over many keys that happen to sit together. Here, a single key, user:celebrity, gets 60% of all requests. The bars now show each server's share of request traffic. Try the ring's tricks on it.

4 servers. ⭐ marks the server that owns user:celebrity.
  • ✓Try both ring tricks: virtual nodes and adding a server
  • ✓Then fix the key itself: replicate it
One hot key needs a fix aimed at the key, not the ring. However you slice the ring, one key hashes to exactly one spot, so one server serves it. The usual fixes:
  • Cache it in front of the servers (or even inside the app), so most reads never reach the ring.
  • Replicate it: keep copies on several servers and spread reads across them (what you just did).
  • Split it: store it as key#1 … key#8 sub-keys that land on different servers, and merge on read.

The patch, by the numbers

How many virtual nodes, and what they cost

The book's patch for crack #1 is virtual nodes (also called replicas, or tokens in Dynamo and Cassandra). Each real server is placed on the ring many times: s0#0, s0#1, s0#2… A key walks clockwise to the first virtual node it meets, and is stored on that virtual node's real server. Instead of one big arc that's lucky or unlucky, each server owns many small arcs, and their sizes average out.[1]

The numbers. The book reports a standard deviation (how far a typical server is from the average) of about 10% of the mean with 100 virtual nodes, and about 5% with 200.[1] A handy rule of thumb for random placement: a server's share is the sum of V random arcs, so its spread is about 1/√V.
  • V = 25 → 1/5 = 20%
  • V = 100 → 1/10 = 10%
  • V = 400 → 1/20 = 5%
Halving the spread costs 4× the virtual nodes. (A quick simulation with 10 servers gives about 9% at 100 and about 7% at 200, so the book's 5% is on the optimistic side. Trust the trend, not the exact figure.)

The cost. Every virtual node is one entry in the ring table: a position (an 8-byte token) plus which server owns it, call it ~24 bytes with overhead. Every router or client that looks keys up keeps its own copy, and every time a server joins or leaves, the change has to reach all of them. A lookup is a binary search over the sorted entries: about log₂(entries) comparisons. More virtual nodes also let you handle bigger servers: give a 2× server 2× the virtual nodes.

Who rides the ring

Five real systems, and one that isn't a ring at all

The book closes with a list of real systems that use consistent hashing.[1] The interview-ready detail is what each one hashes and what the hash picks.

Match them: tap a system, then tap the card that describes it. A wrong pair costs a heart.

Build a Maglev table

Maglev is Google's software network load balancer.[8] Every packet of one connection must reach the same backend, so it hashes the connection's 5-tuple (source IP and port, destination IP and port, protocol). The twist: Maglev doesn't use a ring. It fills a fixed-size lookup table. Each backend has its own preference order of table slots, built from an offset and a skip derived from its name. Backends take turns, and on each turn a backend claims its next preferred slot that's still free.

A toy: 7 slots and 3 backends. The real paper uses a table of 65,537 slots (a prime).

Two different deals. Maglev buys near-perfect balance (every backend gets M/N slots, give or take one: here 4 and 3) and pays with a little extra disruption: when a backend leaves, a few slots change hands between survivors too. A ring buys minimal disruption (only the dead server's keys move) and pays with less even balance. Maglev also keeps a connection-tracking table, so live connections usually stay put even when the lookup table changes.[8] Other non-ring options worth naming: rendezvous hashing (each key picks the server with the highest hash(key, server))[10] and Google's jump consistent hash (no table at all, for numbered shards).[9]

🎓 Level-up note (for later)

The HN/N largest arc and the 1/√V spread are idealised maths for random placement. Real systems often place tokens on purpose. Dynamo moved to equal-sized fixed partitions handed out to nodes (its "Strategy 3"), which balanced load better.[2] Cassandra 4.0 cut the default num_tokens from 256 to 16 because its token-allocation algorithm picks positions to balance load, so 16 is enough.[4]

The book's "5% at 200 virtual nodes" is on the optimistic side of a simple simulation (about 6–7%). Teach the trend: 4× the virtual nodes halves the spread. And the book's "consistent hashing mitigates hotspot keys" holds for many keys that cluster, not for one extremely hot key.

Discord and Akamai are described at the level their public write-ups support: Discord's hash ring routes processes across Elixir nodes[5], and Akamai's roots are the Karger et al. caching work at MIT.[7] Their current internals may differ.
