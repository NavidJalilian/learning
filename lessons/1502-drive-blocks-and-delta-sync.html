Read the map in three lanes. File bytes go left: block servers chop them and park them in S3, and old stuff drifts down to cold storage. Everything about files goes through the middle: load balancer, API servers, then the metadata cache in front of the metadata DB. The right lane keeps your other devices up to date. Two separate paths for bytes and metadata is the big idea of this design.
2

Split, squash, lock, ship

The block-server pipeline, in order

When a new file arrives, a block server runs it through four steps.[1] It splits the file into blocks of at most 4 MB (the book copies Dropbox's limit). Each block gets a hash: a short fingerprint computed from its bytes, so the same bytes always give the same fingerprint. The hash and the block's position go into the metadata DB. Each block is then compressed (squashed smaller), encrypted (scrambled so only key holders can read it), and uploaded to S3 as its own object.

Not one squasher for everything. The book picks the compression algorithm by file type: gzip or bzip2 for text, and different algorithms for images and video.[1] Many photo and video formats are already compressed, so squeezing them again gains almost nothing.
Honest detail: what "unique hash" means. The book just says each block has a unique hash value. In practice that's a cryptographic hash such as SHA-256. Dropbox hashes each 4 MB block with SHA-256.[5] A weak hash could give two different blocks the same fingerprint, and the system would mix them up.
3

Only send what changed

Delta sync, predict-then-watch

Big files that change often are the bandwidth killer. Re-upload a whole 40 MB file to fix one typo and you burn the user's data plan. The book's first fix is delta sync ("delta" = the difference): when a file changes, send only the blocks that changed.[1] How do you know which ones changed? Hash each block again and compare with the hashes already stored. Same fingerprint means same bytes, so skip it.

Honest caveat: who does the comparing? In the book, block servers do the chunking. But delta sync only saves upload bandwidth if your device itself knows which blocks changed before sending anything. Real Dropbox clients chunk and hash locally, tell the server their list of hashes, and upload only the blocks the server says it's missing.[3] The book's wrap-up weighs this option too: faster, but the chunking and encryption code then has to live in every client app.

🎓 Level-up note (for later)

Fixed blocks are fragile. You saw it in stage 3: insert one byte near the start and every boundary shifts. The rsync algorithm handles this with a rolling checksum that can find matching blocks at any offset.[2] Many backup and dedup tools instead cut blocks where the content says to (content-defined chunking). The book doesn't cover either.

4 MB is a dial, not a law. It's Dropbox's choice. Bigger blocks mean fewer rows in the metadata DB but coarser deltas (a 1-byte edit re-sends a bigger block). Smaller blocks mean finer deltas but more metadata and more requests.

Where chunking runs is a trade-off. Chunking on the client saves upload bandwidth, but the book's wrap-up points out the cost: the logic must be written for every platform, and encrypting on a device you don't control is harder to trust. Dropbox's 2012 scaling talk is a good look at how this evolved in practice.[4]
