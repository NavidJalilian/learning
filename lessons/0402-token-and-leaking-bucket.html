1

Fill the bucket

Token bucket, hands-on

The book lists five rate-limiting algorithms. This quest covers the two bucket ones. Quest 4.3 covers the three "window" ones.[1]

The token bucket is the simplest and the most widely used. A token is a permission slip for one request. Here's how it works:

  • The bucket holds at most a fixed number of tokens. That number is its capacity, or bucket size.
  • A refiller drops tokens in at a fixed rate. If the bucket is already full, the new token spills over the rim and is lost.
  • Each request has to take one token. If there's a token, the request goes through to the API. If the bucket is empty, the request is dropped (rejected).

One of the book's figures uses a bucket of 4 tokens with a refill rate of 4 per minute. That's what you're driving below. The clock is sped up: each real second is 15 seconds of game time, so a new token arrives every real second.

Two knobs, two jobs. The bucket size (4) is the biggest burst you'll ever let through at once. The refill rate (4 per minute) is the average rate you allow over time. A full bucket can be spent in one go, which is why a token bucket allows short bursts.

Predict the drops

Calculate, then watch the bucket do it

A real limiter doesn't run a timer for every bucket. With millions of users that would be millions of timers. Instead it stores just two numbers per bucket: how many tokens were left, and when it last refilled. When a request arrives, it works out the refill since then in one line:

tokens = min(capacity, tokens + elapsed × rate)
if tokens ≥ 1: take one, allow · else: drop

"elapsed" is the time since the last request, and min keeps the bucket from going over capacity (the overflow you saw in stage 1). This "lazy" refill is cheap and exact. Stripe's Redis-based limiter works this way.[3]

How many buckets?

One bucket per rule, per key

One bucket is never enough. The book's rule: each limit rule gets its own bucket, for each thing you limit by.[1] Different endpoints usually need different buckets. If you limit by IP address, every IP address gets a bucket. And if the whole system has one ceiling, a single global bucket shared by every request does the job.

Here are the book's example rules for a social app:

✍️ Write a post: 1 / second, per user
🤝 Add a friend: 150 / day, per user
❤️ Like a post: 5 / second, per user
🌐 Whole system: 10,000 / second, global
Answer a round to fill the grid. One square = one bucket.
The book's scorecard for token bucket. Pros: easy to implement, memory efficient (two numbers per bucket), and it allows short bursts as long as tokens are left. Con: its two parameters, bucket size and refill rate, can be hard to tune well. Amazon (API Gateway throttling) and Stripe both use it.[4][2]

Hard or soft?

The book's wrap-up names two flavours of limit. Hard: requests can never go over the threshold. Soft: requests may go over it for a short time. Two limiters below both say "10 per minute". Fire 14 requests at each and see which one is which.

The leaking bucket

Same burst, different personality

The leaking bucket (also called the leaky bucket) looks similar, but it doesn't hand out tokens. It holds the requests themselves and lets them out at a fixed rate, like water dripping from a hole in the bottom.[1] It is usually built as a FIFO queue (first in, first out: the oldest request leaves first).

  • A request arrives. If the queue has room, it joins the back of the queue. If the queue is full, it's dropped.
  • At regular intervals, the request at the front is taken out and processed.
  • Two parameters: bucket size (how long the queue can get) and outflow rate (how many requests are processed per second).

Both buckets below hold 4 and work at 1 per second. Both start ready (token bucket full, queue empty). A burst of 8 requests hits each one at t = 0. Then at t = 1.5 s a fresh VIP request arrives. Predict first.

The book's scorecard for leaking bucket. Pros: memory efficient, because the queue has a fixed size; and requests leave at a fixed rate, which suits anything that needs a stable outflow. Cons: a burst fills the queue with old requests, and if they aren't processed in time, recent requests get rate limited. Your VIP just waited 3.5 s behind stale requests, and with one more early arrival it would have been dropped. Plus the same tuning problem: two parameters. Shopify is the book's example user.[5]

🎓 Level-up note (for later)

• The refiller is a mental model. Production limiters don't add tokens on a timer. They store the token count and last timestamp, then compute the refill on each request, the way you did in stage 2. Stripe's sample code does exactly this in Redis.[3]

• There are two "leaky buckets". The book's version is the leaky bucket as a queue: it delays requests and lets them out at a fixed pace. The other is the leaky bucket as a meter: it rejects over-limit requests instead of queueing them, and it is mathematically the same as a token bucket (an equivalent form is called GCRA, the generic cell rate algorithm).[7] Shopify's API limits are meter-style: an over-limit call gets an HTTP 429 error straight away. It is not queued.[5]

• "Amazon uses token bucket" refers specifically to API Gateway's request throttling, where you set a rate and a burst, which are the refill rate and bucket size by other names.[4] It isn't a claim about every Amazon system.
