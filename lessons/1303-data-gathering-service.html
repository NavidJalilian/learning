Quest 13.3 · Design a Search Autocomplete System

The Weekly Harvest

Billions of searches pour in every day. You can't stuff each one into the trie the moment it happens. Instead, you gather them up, count them, and build a fresh trie on a schedule. This quest is the farm behind the dropdown.

🎯

Your win today: you can draw the data gathering pipeline (analytics logs → aggregators → aggregated data → workers → trie DB → trie cache), explain why the trie is not updated on every search, compare document-store vs key-value storage for the trie, and explain weekly rebuild vs in-place updates.

Why not update live?

Predict, then watch the trie choke

In the first sketch (Quest 13.1), every finished search bumped its counter straight away. Now the data lives in a trie: a tree of letters where each node is a prefix, and each node keeps a cached list of the top 5 queries below it (that's Quest 13.2).

So what does one search cost if you write it into the trie live? Take twitter. Its count changes, so every node on its path (t, tw, twi … twitter, plus the root) has to re-check and maybe re-sort its cached top-5 list. That's one rewrite per letter. Meanwhile, the same trie is answering reads: about 48,000 a second at peak, from Quest 13.1's math.

      Store the trie

      Document store or key-value store?

      Workers build the trie, then save it in the Trie DB, the durable copy. The book gives two ways to store a tree in a database:[1]

      • Document store. A new trie is built every week anyway. So take a snapshot, serialize it (turn it into one long piece of text or bytes), and save it as documents. The book's example is MongoDB.[2]
      • Key-value store. Flatten the tree into a hash table. Every prefix becomes a key, and that node's data, its cached top-k list, becomes the value. Then one prefix is one lookup.[3]

      Below is the book's small trie. Like a real trie, each node shows only its own letter. Teal rings mark complete queries and their counts. Tap a node, then pick its key. Map 4 nodes and the workers will finish the rest.

      Honest caveat. The key-value rows lose the tree's shape. That's fine for reads, because a read needs just one row. But you don't rebuild next week's trie from these rows. You rebuild from the aggregated data.

      Swap or patch?

      Create and update the trie

      Create: workers build the trie from the aggregated data. Update has two options in the book:[1]

      • Option 1, the book's choice: build a brand-new trie every week, then swap it in for the old one.
      • Option 2: update single nodes in place. The book says to avoid it because it's slow. It's OK if the trie is small.

      Why slow? Try option 2 yourself. Remember: each node caches the top queries below it.

      🎓 Level-up note (for later)

      • Weekly is a starting point. It's the book's example interval, not best practice. Big search engines refresh much more often and run a separate fast path for fresh and trending queries. Quest 13.5 touches on this.
      • Illustrative numbers. The book's tables use 2019 dates, and their counts are made-up examples, not real search data. The same goes for this quest's log.
      • Two tries in memory. A full swap needs room for the old and new trie at the same time. Bring it up if the interviewer asks about memory.
      • KV rows aren't a tree. Prefix → top-k rows are great for one-lookup reads, but they lose the tree's shape. You rebuild from the aggregated data, not from the rows.
