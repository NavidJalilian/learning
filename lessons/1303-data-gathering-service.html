The Weekly Harvest

Every search leaves a footprint. Gather the footprints, squash them into weekly counts and grow a fresh trie from them, all without slowing down a single keystroke.

Why not update live?

Predict, then watch the trie choke

In the first sketch of this system, the data gathering service (the part that collects what people search for) updated the data the moment someone searched. Now our data lives in a trie, and every node caches its own top-k list (its k most popular queries, from Quest 13.2). So one search for twitch means rewriting twitch, twit, twi, tw, t and the root. Every node on the path.[1]

Meanwhile the same trie must answer reads. The book's estimate is about 48,000 suggestion requests per second at peak, and each must come back in under 100 ms. Below is a toy model: dots are finished searches flying in.

      Squash the logs

      Raw rows into weekly counts

      An analytics log holds one row per search: the query and when it happened. It's append-only (rows are only ever added, never changed) and not indexed (no shortcut for finding rows, so a search means reading everything). The logs are huge and in the wrong shape for building a trie. So an aggregator rolls them up first: one row per query per week, with a count.[1]

      Store the trie

      Document store or key-value store?

      Workers save the finished trie to the Trie DB, the persistent copy that survives restarts. The book gives two ways to store it:[1]

      • Document store. A new trie is built every week anyway, so serialize it (turn the whole structure into one blob of data) and save that snapshot as documents. The book's example is MongoDB.[2]
      • Key-value store. Flatten the trie into a hash table: each prefix becomes a key, and that node's data (its cached top-k list) becomes the value.[3]

      Build the key-value version yourself. Drag a node into the table (or tap it). Then pick its key. Careful: each circle shows only its own letter.

      Why bother flattening? In key-value form, "suggest for be" is one lookup by key: no walking down the tree at all. And because each prefix is its own key, rows can later be spread across machines by key (Quest 13.5). The cost: the tree shape is gone. That's fine, because next week's trie is rebuilt from the aggregated data, not from these rows.

      Swap or patch?

      Create and update the trie

      Create is the easy part: workers build the trie from the aggregated data. Update has two options:[1]

      1. Weekly swap (the book's choice): build a brand-new trie every week and replace the old one.
      2. Patch in place: change individual nodes. The book advises against it because it's slow, though it's OK when the trie is small.

      Try patching first, so you feel why it's slow.

      📈This week, beer jumped from 10 to 30 searches. Tap every node whose cached list must change, then press Done.

      The ripple. Every ancestor caches its children's top queries, so changing one query means rewriting every node from it up to the root. Here that's 5 writes for one count. Now imagine millions of counts changing at once.

      🎓 Level-up note (for later)

      • Weekly is the book's example, not best practice. Big search engines refresh far more often and run a separate fast path for fresh or trending queries (Quest 13.5). Start from weekly in an interview, then say what you'd change for freshness.
      • The numbers are illustrative. The book's example tables use weeks from 2019. They're not real data from Google or anyone else, and neither are the counts in this quest.
      • Swapping needs room for two. During the switchover the old and new tries are both in memory. If the interviewer asks about memory, say so, and mention that sharding (13.5) keeps each piece small.
      • Key-value rows lose the tree shape. That's fine for reads, which are single lookups. But you rebuild from the aggregated data, not from the key-value rows.
