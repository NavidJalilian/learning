Anatomy of a Snowflake

UUIDs were too long and the ticket server was one box that could die. Twitter's answer fits everything into a single 64-bit number. Build its layout, mint IDs on a slowed-down clock, crack one open to read its birth date, and do the math behind "69 years".

🎯

1

Divide the 64 bits

Divide and conquer, one field at a time

Recall the brief from Quest 7.1. IDs must be unique, numbers only, fit in 64 bits, sorted by date, and we need over 10,000 new IDs a second.[1]

Twitter's Snowflake uses divide and conquer. Don't run one shared counter. Cut the 64 bits into sections, and give each section one job.[1][2] Here are the five parts and what each one must be able to hold:

  • Sign bit: always 0. The book says it's kept for future use. In a signed 64-bit integer (like Java's long), the top bit marks negative numbers, so a 0 keeps every ID positive.
  • Timestamp: milliseconds since a start moment you pick, called the epoch. Gets every bit the other parts leave over.
  • Datacenter ID: which datacenter made the ID. Up to 32 datacenters.
  • Machine ID: which server inside that datacenter. Up to 32 per datacenter.
  • Sequence number: counts IDs made on one machine in the same millisecond. Up to 4,096 of them. It resets to 0 every millisecond.

Your job: tap the parts in order from left to right, then give each one a size. The leftmost bits are the most significant. They're worth the most, like the thousands digit in 4,321. Hint: n bits can count 2n different values.

Mint an ID

Watch the bits fill in

Making an ID means gluing four numbers together. Two tools do it. << (shift left) slides a number's bits to the left and fills the gap with zeros. | (bitwise OR) merges bit patterns that don't overlap.

id = (timestamp << 22) | (datacenter << 17) | (machine << 12) | sequence

Why 22? That's how many bits sit to the right of the timestamp: 5 + 5 + 12. The datacenter and machine IDs are set when the server starts. After that they normally stay fixed. The book warns that changing them needs careful review, because a mistake here means duplicate IDs.[1] Only the timestamp and the sequence change while it runs.

Decode the past

Figure 7-7: from bits back to a date

Now run it backwards. >> (shift right) slides bits right, and the ones that fall off the end are gone. & (bitwise AND) with a mask keeps only the bits you want. 31 is 11111 in binary (five 1s), and 4,095 is twelve 1s.

timestamp = id >> 22 · datacenter = (id >> 17) & 31 · machine = (id >> 12) & 31 · sequence = id & 4095

The timestamp counts from Twitter's default epoch, 1288834974657 ms (4 Nov 2010, 01:42:54 UTC).[1][3] The book's Figure 7-7 decodes one example. We'll do the same with this ID:

🎓 Level-up note (for later)

Not every "snowflake" is 1 | 41 | 5 | 5 | 12. Twitter's own code matches the book: 5 bits of datacenter ID plus 5 bits of worker ID.[3] Instagram used 41 bits of time, a 13-bit shard ID and a 10-bit sequence, all generated inside PostgreSQL.[4] Discord uses a 42-bit timestamp counted from the start of 2015.[5] Sony's Sonyflake counts time in 10 ms units (39 bits, about 174 years), with an 8-bit sequence and a 16-bit machine ID.[6] Same idea, different bit budgets.

"Sorted by time" is only rough across machines. You saw it in stage 2. Inside one millisecond, IDs order by datacenter and machine number, not real time. Clocks that drift apart between machines blur the order further. That's Quest 7.4.

69 or 69.7? The book divides by 365 days a year and rounds down to "about 69 years". The exact figure is 69.7 years, so Twitter's epoch runs out in July 2080.
