Quest 15.3 · Design Google Drive

The Metadata Ledger

The file bytes live in cloud storage as blocks. Everything that says which blocks make up which version of which file lives in one ledger. Keep it honest, draw its tables, and settle a fight over the same spreadsheet.

🎯

Your win today: you can explain why Drive's metadata needs strong consistency (and a relational DB), sketch the user / device / namespace / file / file_version / block schema, and say exactly what happens when two people edit the same file at once.

1

No two truths

Strong consistency, spot-the-bug

In Quest 15.2 you chopped files into blocks. Those blocks are just bytes. The metadata (data about the data: file names, versions, which blocks belong to which version) sits in a separate metadata database, with a cache in front of it. A cache is a fast in-memory copy of hot rows, so most reads never touch the database.

The book's rule for this ledger is strong consistency by default: every client sees the same, latest version of a file. It is not acceptable for your laptop and your phone to show two different versions of the same file at the same moment.[1] The catch: in-memory caches are eventually consistent by default. Their copies may lag behind for a while and only catch up "eventually".

Spot the bug

The API server's code. One line changes the truth but leaves an old copy behind. Tap it.

Two rules from the book. For strong consistency with a cache in the picture: (1) the cache's replicas and its master must hold the same data, and (2) the cache entry is invalidated (deleted) whenever the database is written, so the next read has to fetch the fresh row.[1]
Why the book picks a relational database. Relational databases give you ACID out of the box. Atomicity: a write happens completely or not at all. Consistency: rules like "a version must point at a real file" always hold. Isolation: two writes at once don't trample each other. Durability: once it says "saved", it survives a crash. Many NoSQL stores don't give you these by default, so you'd have to write that safety into the sync logic yourself.[1]

Draw the tables

The metadata schema, build-and-trace

A schema is the list of tables and their columns. The book shows a simplified one with just the six most important tables.[1] Each table already has its primary key (🔑, the column that uniquely names a row). Your job: fill in the rest, link them, then use them.

  • user: basic profile info (name, email, photo).
  • device: each phone or laptop. One user has many devices. It stores a push ID for sending push notifications.
  • namespace: a user's root directory, the top folder everything else hangs under.
  • file: everything about the latest state of a file.
  • file_version: the version history. Existing rows are read-only, so the history can't be rewritten.
  • block: everything about one block of one version. Join a version's blocks in the right order and you get that version back.

🎓 Level-up note (for later)

  • "Relational because ACID" is the book's simplification. At huge scale, teams run sharded MySQL with their own layers on top (Dropbox built one called Edgestore) or globally consistent stores like Google Spanner. Some NoSQL stores now offer transactions too. The real point: metadata needs transactions and strong consistency, whatever gives you them.
  • Invalidate-on-write still has a tiny race. A reader can miss the cache, read the old row, and put it back into the cache just after the delete. Production systems add versioned cache entries or leases to close that gap.
  • The schema is deliberately small. It has no sharing or permissions tables, even though sharing is in scope. If the interviewer asks about access control, say so and sketch one (e.g. a table of who can access which namespace or file).
  • "First processed wins" is not merging. Real-time co-editing (Google Docs) uses operational transforms or CRDTs, which are out of scope here.
  • Even the block store got stricter: Amazon S3 has offered strong read-after-write consistency since December 2020.[4]
