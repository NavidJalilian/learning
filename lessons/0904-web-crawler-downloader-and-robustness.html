1

Read the house rules

robots.txt · the Robots Exclusion Protocol

The HTML Downloader is the box that actually fetches web pages over HTTP. Before it touches a site, a polite crawler first reads that site's robots.txt: a plain text file at the root of the site, like shop.example/robots.txt. The rules it follows are called the Robots Exclusion Protocol.[1]

The file is split into groups. Each group starts with User-agent: (which bot the rules are for; * means "any bot") and lists paths:

  • Disallow: /cart/: don't fetch any URL whose path starts with /cart/.
  • Allow: …: an exception that re-opens part of a blocked path. When two rules match, the longer, more specific one wins.[2]

One rule trips people up: a bot that has its own group follows only that group and ignores the * group completely.[3] The book shows part of a big online retailer's real file, with paths blocked for Googlebot. Ours below is made up.

# shop.example/robots.txt
User-agent: *
Disallow: /cart/
Disallow: /search
 
User-agent: SpiderBot
Disallow: /private/
Allow: /private/press/
We are:
SpiderBot: not yetOtherBot: not yet
Mark every URL Allowed or Blocked for the bot you are, then press Check. Do it for both bots.

So the crawler caches each site's robots.txt and downloads a fresh copy now and then. The book keeps it in a cache and refreshes it periodically.[1]

Honest caveat: it's a sign, not a lock. Good crawlers obey robots.txt, but nothing forces a bad one to. It also doesn't hide a page: a blocked URL can still show up in search results if other sites link to it. The protocol was only written up as a formal standard in 2022 (RFC 9309), which says a crawler generally shouldn't trust a cached copy for more than 24 hours.[2]
2

Split the work

Speed-up 1 · distributed crawl

The book's crawler has to fetch about 1 billion pages a month. That's roughly 400 pages per second on average and 800 at peak.[1] One fetch takes hundreds of milliseconds, and most of that time the thread just waits for the network. So one thread manages only a few pages a second.

Speed-up 1 is the distributed crawl: spread the crawl jobs over many servers, and run many threads (workers running side by side) on each one. The URL space is cut into pieces, so every downloader owns its own subset of URLs.[1] The rough math: pages/s ≈ servers × threads ÷ seconds per fetch.

How does a URL know which downloader it belongs to? A common choice is to hash the host name (the wiki.example part). Then every URL from one host lands on the same downloader, which also makes it easy for that one server to stay polite to that host.

Why it's only rough. The formula assumes every thread is busy all the time. In real life, politeness (one request at a time per host, with gaps) and network bandwidth cap you first. Many modern crawlers also use asynchronous I/O (one thread juggles many open connections) instead of one thread per fetch.
3

Stop asking for directions

Speed-ups 2–4 · DNS cache, locality, short timeout

Three more speed-ups from the book:[1]

  • Cache the DNS resolver. DNS turns a host name into an IP address. One lookup takes about 10 to 200 ms. Many DNS interfaces are synchronous (the caller is stuck until the answer comes back), and while one thread waits on a lookup, other threads can be blocked behind it. So keep your own cache of host name → IP. The book refreshes it on a schedule with cron jobs.
  • Locality. Put crawl servers in several regions, close to the sites they crawl. A shorter distance means faster downloads. The book applies the same idea to most parts: crawl servers, cache, queue, storage.
  • Short timeout. Some servers answer very slowly or never. Set a maximum wait. If the host hasn't answered by then, drop that page and crawl something else.

Honest caveats. Real DNS answers come with a TTL (time-to-live) that says how long they may be cached, and real resolvers follow it rather than a cron schedule. Big crawlers often run their own asynchronous resolver. The Mercator crawler, which the book cites, wrote a custom multi-threaded resolver because the standard library call was synchronous.[5][4] And pair a short timeout with retry and back-off: a host that timed out once may just be busy.
4

Built to survive

Robustness · four defences

At web scale, something is always broken. The book lists four defences:[1]

  1. Consistent hashing spreads hosts across downloader servers. A server can be added or removed and only a small slice of hosts moves.
  2. Save crawl state and data. Keep writing the crawl's progress and data to storage. A crashed or interrupted crawl restarts by loading what was saved, not from scratch.
  3. Exception handling. Errors are normal on the web. A bad page or a failed fetch gets caught and dealt with, without crashing the whole system.
  4. Data validation. Check data at each step, so bad input can't cause system errors further down.

You are the chaos monkey. Press a disaster, then pick the shield that saves the crawl. A wrong shield shows what would have happened and costs a heart.

🎓 Level-up note (for later)

Crawl-delay isn't standard. You'll see Crawl-delay: 10 in many robots.txt files. It isn't part of RFC 9309. Some crawlers honour it, and Google ignores it and sets its own pace from how the server responds.[3]

Listen when a site says "slow down". A 429 Too Many Requests, or a 503 with a Retry-After header, is the server asking you to back off.[6] A short timeout plus retries with growing gaps (back-off) is both faster and more polite than hammering.

robots.txt failures have rules too. RFC 9309 says that if robots.txt returns a 4xx error (like 404), the crawler may treat the whole site as allowed. If it returns a 5xx server error, the crawler should assume everything is blocked for now.[2]
