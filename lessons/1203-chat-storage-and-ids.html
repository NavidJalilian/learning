Quest 12.3 · Design a Chat System

The Message Vault

Tens of billions of chat messages arrive every day. Most of them are read once and never again, but every one of them has to stay findable. Pick where they live, design the tables, and give every message a number that keeps it in order.

Two kinds of data

Know the read/write pattern first

In Quest 12.2 the high-level design had a box called KV store. Time to open it. A chat app stores two very different kinds of data:[1]

  • Generic data: user profiles, settings, friend lists. It's small, structured, and has to be correct. The book puts it in a relational database (tables, SQL, transactions), with replication (copies on several machines) for availability and sharding (splitting rows across machines) for scale.
  • Chat history: the messages themselves. This is the unusual part, and it goes in a key-value store: a database that stores values under a key and finds them by that key, very fast, without SQL joins.

🗃️ Relational DB

    🔑 Key-value store

      Why is chat history special?

      Before you pick a database, look at how the data is read and written. The book lists four facts about chat history:[1]

      1. It's huge. In 2016, Facebook Messenger and WhatsApp together handled about 60 billion messages a day.[2]
      2. Recent chats get almost all the reads. People rarely scroll back to old conversations.
      3. But old messages must stay reachable. Search, "show my mentions", and "jump to this message" all need random access: going straight to one message anywhere in the history.
      4. Reads and writes are about equal: roughly 1:1 for 1-on-1 chat. Most apps read far more than they write. Chat doesn't.

      Why a key-value store?

      The long tail problem

      The left chart shows how often messages of each age get read. There's a tall head (today's messages) and a long tail: years of old messages that are rarely read but must stay reachable. That tail is most of the data.

      The right panel is a single relational database. To find one message fast, it keeps an index (a sorted lookup structure, like a book's index). Lookups are fast while the index fits in RAM (memory). Once it's bigger than RAM, parts of it live on disk, and disk is much slower. Drag the slider to add years of history.

      The book's four reasons for a key-value store[1]
      1. Easy horizontal scaling: add machines and the data spreads across them.
      2. Very low latency (wait time) for reads by key.
      3. Relational databases handle the long tail badly: once indexes grow large, random access gets expensive.
      4. Proven chat apps use them: Facebook Messenger used HBase,[3] and Discord used Cassandra.[4]
      Honest caveat. The real trick in this sim is partitioning by key, so each lookup touches one small piece. You can also shard a relational database by channel, and some big chat apps do. Facebook later moved Messenger off HBase onto MySQL (MyRocks), and Discord moved from Cassandra to ScyllaDB.[5] "Key-value store" is a sensible interview default, not a law of nature.

      Design the tables

      1-on-1 and group message tables

      The book gives two message tables: one for 1-on-1 chat and one for group chat.[1] A group chat is called a channel. Build them: tap a column, then tap the table it belongs in. Some columns go in both tables. Two of them belong in neither.

      Part 1 · Schema builder
      Why these keys? In the 1-on-1 table the primary key (the column that uniquely identifies a row) is message_id, and it alone decides message order. In the group table the primary key is the pair (channel_id, message_id). channel_id is the partition key: the column that decides which machine stores the row. Every query in a group chat works inside one channel, so the whole channel's history sits together on one partition. Inside it, rows are kept sorted by message_id (the sort key, which Cassandra calls a clustering key).

      Mint the IDs

      Unique and sortable by time

      Since message_id decides the order, it needs two properties:[1] it must be unique, and it must be sortable by time (a newer message always gets a higher ID). The book weighs three ways to make one:

      1. auto_increment: MySQL can number rows 1, 2, 3 for you. But NoSQL databases (like Cassandra or HBase) usually don't offer it.
      2. A global 64-bit generator like Snowflake: one ID scheme for every message everywhere (you built it in Quest 7.3).
      3. A local sequence number: each channel counts its own messages 1, 2, 3. IDs are unique only within that channel.

          Watch the 1-on-1 table. The book keys the 1-on-1 table by message_id alone. With local IDs, Alice–Bob's message #3 and Carol–Dan's message #3 would clash. So if you choose local IDs, treat every 1-on-1 chat as a two-person channel and key it by (channel_id, message_id) too. Interviewers like it when you spot that.

          🎓 Level-up note (for later)

          • Hot partitions. Discord's real key is (channel_id, bucket), where a bucket is a fixed time window (about 10 days). That stops one busy channel from growing into one giant partition. The book's plain channel_id key would make huge, hot partitions for very large channels.[4]
          • Who hands out the next number? A local sequence still needs one safe source per channel, such as a single owner per channel or an atomic counter in Redis or the database. If two chat servers both mint "the next ID" for the same channel, you get duplicates. The book calls local IDs "easier" and skips this part.
          • Sync cursors. In 12.4 each device remembers one cur_max_message_id. With per-channel IDs, one number can't cover every channel. A device needs a cursor per channel, or each user's inbox needs its own sequence. Raise it if the interviewer pushes.
          • Discord uses global IDs. Its message_id is a Snowflake, so it sorts by time across every channel. Both of the book's schemes are workable.
          • Storage moves. Facebook moved Messenger from HBase to MyRocks (MySQL on RocksDB) around 2018. Discord moved from Cassandra to ScyllaDB in 2022.[5]
