Roll a UUID

128 random-ish bits, no coordination

Quick recap from Quest 7.1. The interviewer's IDs must be:

The book's second candidate is the UUID (universally unique identifier). It's a 128-bit number, written as 32 hex digits (0–9 and a–f, 4 bits each) in groups of 8-4-4-4-12. The book's example is 09c93e62-50b4-468d-bf8a-c07e1040bfb2.[1]

The common kind, version 4, is pure dice: every web server rolls its own, and nobody has to talk to anybody. There's no coordination (servers checking with each other before acting). Roll a few.

👎 128 bits, but we need 64. They don't go up with time. They can be non-numeric. (A UUID is a number underneath, but it's usually stored and passed around as a 36-character string with letters and dashes.)
2

The birthday odds

How unlikely is "unlikely"?

Random IDs can clash. How often? It's the birthday paradox: in a room of just 23 people, there's a 50% chance two share a birthday. The trick is that every pair of people is a chance to match, and pairs grow much faster than people.

For UUIDs the "days of the year" are the 2122 possible random values (128 bits minus the 6 fixed ones you found in stage 1). With n UUIDs made, the chance of any duplicate is about:

P(duplicate) ≈ 1 − e−n² / (2 × 2122)
while P is small, that's roughly n² / (2 × 2122)

The book borrows a line from Wikipedia: you'd have to make 1 billion UUIDs every second for about 100 years before the odds of a single duplicate reach 50%.[2] Check that claim yourself.

Real-world catch. The math assumes a good random source. Duplicate UUIDs seen in practice almost always come from a broken one, like a virtual machine cloned together with its random-number state, or a generator seeded with something guessable such as the time.

The ticket booth

Flickr's central counter

The third candidate goes the other way: one place hands out every number. Flickr described this in a 2010 blog post and called it a ticket server.[3] It's a single MySQL database whose only job is auto_increment (a column the database fills with the next number, 1, 2, 3…, on every insert). Every web server that needs an ID asks it for the next one.

Flickr's trick keeps the table at one row forever. REPLACE INTO deletes the row and inserts it again, which bumps the counter:

-- bump the one-row counter
REPLACE INTO Tickets64 (stub) VALUES ('a');
-- read back the number you just got
SELECT LAST_INSERT_ID();

Run some traffic through it. Then break it.

👎 A single point of failure (SPOF): one part whose crash takes the whole feature down. Adding more ticket servers fixes that but brings new problems, like keeping them in sync. Flickr's own post goes one step further than the book: two servers, odd and even, and they accept that IDs come out only roughly in order.

🎓 Level-up note (for later)

UUIDv7 fixes one con, not all of them. The book predates RFC 9562 (2024), which standardised UUID version 7: a 48-bit Unix timestamp in milliseconds, then random bits.[4] v7 IDs do sort by time. They're still 128 bits, so they still fail this prompt's 64-bit rule.

Random keys hurt databases. Random v4 UUIDs as primary keys land all over a B-tree index (the sorted tree most databases use to find rows), so inserts split pages and fight for cache. That's a practical reason teams avoid them, beyond the book's list.

The numbers are rounded. The book's "about 100 years" at 1 billion per second works out to about 86 years with the birthday formula.

Real ticket systems batch. Instead of one round trip per ID, a server can grab a block of numbers (say 1,000 at a time) and hand them out locally. Fewer trips, but IDs from different servers interleave out of order.
