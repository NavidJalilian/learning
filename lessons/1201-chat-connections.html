Now the core idea. Phone A never connects to phone B. A doesn't know where B is, and B might be switched off. Every message goes through a chat service in the middle, and it has three jobs:[1]

  1. Receive messages from the people sending them.
  2. Find the right recipients and relay the message to them.
  3. Hold the message on the server if a recipient is offline, and deliver it when they come back.

Your call

Which leg is the hard one to build with plain HTTP?

Tap an arrow in the diagram, or a button.

Why sending is easy. HTTP is client-initiated: the client always speaks first. That's perfect for the sender. A opens a connection and posts the message. With the keep-alive header, the same TCP connection is reused for the next message, so A doesn't repeat the connection setup (the TCP handshake) every time. The book notes that Facebook's chat sent messages over plain HTTP in its early days.[1] The receiving side is the problem: the server has news for B, but HTTP gives the server no way to speak first.
2

Polling

Are we there yet? Are we there yet?

The simplest fix: B's phone asks the server "anything new for me?" on a fixed timer. That's polling.[1] It works, but most of the time the answer is "no". Every "no" still costs a request, server work and phone battery. And a message can sit on the server for up to one whole interval before B's next ask.

You can't win both. A shorter interval cuts the wait but multiplies the empty requests. A longer one saves requests but makes messages sit on the server. For chat, where people expect replies in about a second, polling is a bad deal. These timings are this sim's numbers, not the book's.
3

Long polling

Hold the line, but it still leaks

Long polling makes the server wait before it answers. B sends a request, and the server holds it open until a message shows up or a timeout (a time limit) runs out. Then B sends a new request straight away.[1] Far fewer empty answers, and messages go out as soon as they arrive.

B asks→server holds…→message or timeout→server answers→B asks again

The book still lists three drawbacks.[1] Each scene below shows one going wrong. Tap a drawback card, then the scene that shows it. One jargon word: a round-robin load balancer hands each new request to the next server in turn, without caring who the request is for.

Honest caveat. "The server can't tell if the client left" is a little strong. A server does notice a clean close, or a write that fails. The real trap is a quietly dead connection: the phone lost signal and never said goodbye, so the request looks alive for a long time. WebSocket has the same trap. That's why real systems add heartbeats, small "I'm still here" pings. You'll build them in Quest 12.5.
4

WebSocket

One pipe, both directions

WebSocket is the book's pick for pushing messages from server to client.[1] The client opens it with an ordinary HTTP request that asks to upgrade the connection. The server agrees, and from then on the same connection stays open and is bi-directional: either side can send at any moment.[2] It runs on the normal web ports, 80 and 443, so it usually gets through firewalls.

    The book goes one step further: WebSocket for sending too. HTTP would work for sending, but one connection that carries both directions makes the design and the code simpler on both the phone and the server.[1] The price: every online user now holds a long-lived connection to one particular server. That server has to remember it, so managing connections on the server side becomes the critical problem. That is exactly where Quest 12.2 picks up.
    Honest caveat: keep a fallback. Port 443 usually gets through, but some corporate proxies still break WebSocket. Libraries such as Socket.IO start on HTTP long polling and upgrade to WebSocket only when it works,[5] and production chat apps keep a fallback like that.

    Boss: The Lag Wraith

    Pick the right connection style

    Picking a transport is a trade-off, not a reflex. Polling is fine for rare updates nobody is waiting on. Long polling is the fallback when WebSockets are blocked. WebSocket fits real-time, two-way traffic. Six situations: pick one for each.

    🎓 Level-up note (for later)

    • There's a fourth option: Server-Sent Events (SSE). The server pushes a stream of events to the browser over plain HTTP.[6] The book skips it. It's great for one-way feeds such as live scores. Chat needs two-way traffic, so WebSocket stays the natural pick.
    • Long polling did run at huge scale. Facebook's chat delivered messages to browsers over HTTP long polling, with Erlang "channel" servers holding the open requests.[4] The drawbacks are real costs, not deal-breakers.
    • Dead connections need heartbeats either way. A phone that loses signal sends no goodbye. Long polling and WebSocket both need periodic pings to notice (Quest 12.5).
