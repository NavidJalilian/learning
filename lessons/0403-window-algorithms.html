Exploit the edge

Fixed window counter and its loophole

Quest 4.2 counted requests with buckets. This quest counts them with windows: slices of time, each with its own counter.

The simplest is the fixed window counter. Cut the timeline into equal windows that start on the round minute (or second, or hour). Keep one counter per window. Every request adds 1. When the counter reaches the limit, new requests are dropped until the next window starts and the count goes back to 0.[1] In the book's first picture the windows are 1 second long and the limit is 3 per second, so a 4th request inside the same second is dropped.

Here the limit is 5 requests per minute. Tap the timeline to send a request at that moment. Then drag the purple 60-second ruler (or use the slider) to count the allowed requests in any one-minute span.

That's the book's picture. 5 requests land between 2:00:30 and 2:01:00, and 5 more between 2:01:00 and 2:01:30. Each window only ever saw 5, so the limiter was happy both times. But the one-minute span from 2:00:30 to 2:01:30 carried 10: twice the limit.[1] Anyone who times calls around the round minute gets double the quota.
So why does anyone use it? It's light on memory (one small counter per user per window) and easy to explain. And some products want a quota that resets on the round minute, hour, or at midnight. The weakness is only this one: a burst at a window's edge can let through more than the quota.[1]

Keep a log

Sliding window log, step by step

The sliding window log closes the edge loophole by remembering when each request happened, not just how many came in a window.[1] Each user gets a log of timestamps, usually kept in a cache such as Redis. Redis has a type called a sorted set: each member carries a number (its score) and the set stays ordered by that number.[5] Use the timestamp as the score and you get a time-ordered log you can trim from the old end.[3]

Every new request runs three steps. The book's example uses a limit of 2 requests per minute. Predict each verdict, then watch the log do it.

Blend two windows

Sliding window counter: calculate and check

The log is exact but heavy. The sliding window counter is a hybrid of the two ideas so far.[1] It keeps only two fixed-window counters per user (this minute and last minute) and estimates how many requests fall in the last 60 seconds:

rolling ≈ current + previous × overlap

current = requests so far in this minute. previous = requests in the whole previous minute. overlap = the share of the rolling 60-second window that still sits inside the previous minute. If you're 30% into this minute, 70% of the rolling window is still in the previous one. Cloudflare runs the same formula in production.[2]

The blind spot. The formula only knows the previous minute's total. It assumes those 5 requests were spread evenly, so it counts 70% of them: 3.5. But they all came in the last second, so all 5 sit inside the rolling window. The real count is 5 + 3 = 8, over the limit of 7, while the estimate (6.5, rounded to 6) says "allow". That's why the book calls it an approximation that only suits a not-so-strict look-back window.[1] In practice it's close: Cloudflare found only 0.003% of 400 million requests were wrongly allowed or wrongly limited.[2]
Why it's popular. Two small counters per user is as cheap as a fixed window. And because it blends in the previous minute, a burst at the edge can't double the quota the way it did in stage 1. The book lists both as pros.[1]

🎓 Level-up note (for later)

Rounding is a choice. The book rounds 6.5 down to 6 and says you could round either way. Real systems vary: Cloudflare compares the unrounded weighted rate to the limit.[2] 0.003% is one company's traffic. It's measured on Cloudflare's own mix. Very bursty clients (all of last minute's calls in its final second) push the estimate further off, as you saw in stage 3. Not every log keeps rejects. The book's sliding log stores rejected timestamps too. Some implementations only log accepted requests. That saves memory, but a client that keeps hammering isn't penalized for its rejected attempts. Google Cloud's guide to rate-limiting strategies is a good next read on these trade-offs.[4]
