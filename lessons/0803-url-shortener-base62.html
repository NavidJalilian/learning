Quest 8.3 · Design a URL Shortener

Count in Base 62

Hashing gave you short codes that can collide. Now try the other road: give every link a unique number and simply write that number in base 62. It never collides. It does have one weak spot.

🎯

Your win today: you can convert an ID to base 62 by hand (11157 → 2TX), explain why it never collides, and compare it with hash + collision resolution, including its weak spot: codes that are easy to guess.

1

The 62-digit abacus

Divide by 62, keep the remainders

In Quest 8.2 you built the short code by hashing the long URL. The book's second approach is base conversion.[1] Every new long URL gets a unique whole number, its ID (the row's primary key). Then you write that number in base 62, and that's the code.

Why 62? A code may use the digits 0–9, the letters a–z and the letters A–Z. That's 10 + 26 + 26 = 62 characters, so one character can stand for any value from 0 to 61. The book maps them like this:[1]

0–9 → 0–910–35 → a–z36–61 → A–Z
How place values work. In base 10 the places are worth 1, 10, 100… (each one 10× the one to its right). In base 62 they're worth 1, 62, 3,844 (that's 62²)… To convert a number: divide it by 62. The remainder (what's left over) is the rightmost character. Then divide the quotient (the whole-number answer) by 62 again for the next character. Stop when the quotient reaches 0.

Convert the book's example, ID 11157. Type the quotient and the remainder for each step (a calculator is fine), then tap the character for the remainder on the keyboard.

Decode it back

Calculate-and-check

Going back is the reverse. Turn each character into its value, multiply it by its place value (1, 62, 3,844…), and add everything up. Here are three codes. Work out the ID behind each one.

Why this can never collide. Base 62 is just another way of writing a number, like Roman numerals. Every ID has exactly one code and every code has exactly one ID, so the mapping is one-to-one. If no two links share an ID, no two links can share a code.[2]

Watch the code grow

Length isn't fixed

A hash-based code is always the same length: you cut the hash to 7 characters. A base-62 code is as long as the number needs, so it grows with the ID.[1] Your IDs come from a unique ID generator (the whole of Chapter 7). Here it's a simple counter: 1, 2, 3…

4

The guessing game

Spot the security hole

The book flags one real problem with this approach. If the ID goes up by 1 for every new link, anyone can work out the next short URL, and that is a security concern.[1] Time to see why. You play the attacker.

You shortened a link an hour ago and gottinyurl.com/2TXThousands of links have been made since.
Links found: 0
🛡️ Switch sides: you're the defender now. Before encoding, run each ID through a reversible scramble: a function with a secret key that shuffles IDs into a big space (all 3.5 trillion 7-character codes) and can be undone by the server. IDs are still unique, so codes still never collide. They just stop being neighbours.
Your link: ID 11157 → 2TX. Press "Try the next code".
  • ✓As the attacker, walk the sequence and find 5 other people's links
  • ✓As the defender, turn on scrambling and let the attacker try 5 more guesses
This really happens. In 2016, researchers scanned the code spaces of public URL shorteners. They found links to cloud-storage files that anyone could open and edit, and map directions that revealed where people live and which clinics they visited.[3] Other fixes: make codes longer (a bigger space is harder to hit), rate-limit the redirect endpoint so one client can't try millions of codes, and never treat a short link as a password for private data.

Sort the showdown

Hash + collision vs base 62

Quick recap of the other road from Quest 8.2: hash the long URL (CRC32, MD5 or SHA-1), keep the first 7 characters, and check the database. If that code is taken (a collision), add a fixed string to the URL and hash again until the code is free.[1]

      🎓 Level-up note (for later)

      Which ID generator? The book's example ID 2009215674938 is about 41 bits, which conveniently encodes to 7 characters. A Snowflake ID from Chapter 7 is 64 bits and encodes to 11.[5] To keep codes at 7 characters, real systems use a counter-style generator, such as Flickr's ticket servers,[4] or hand each web server a pre-allocated range of IDs to use up locally.

      The alphabet order is a convention. The book puts a–z before A–Z. Other tools put A–Z first.[2] Any fixed order works, as long as encode and decode agree.

      Unique IDs don't de-duplicate long URLs. If the same long URL is shortened twice, it gets two IDs and two codes. To give each long URL one code, you still look it up first (the book's flow does exactly that).

      Scrambling isn't encryption. This page's scramble (multiply and add, modulo 62⁷) shows the idea, but someone could recover the secret from a few known codes. A real system would use a proper keyed cipher sized to the code space, or random IDs with a uniqueness check.
