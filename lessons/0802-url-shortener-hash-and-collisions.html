Quest 8.2 · Design a URL Shortener

Seven Characters or Bust

You have a napkin full of numbers: 100 million new links a day, 365 billion over ten years. Now give each one a home in a table, decide how long the short code must be, and build a hash-based way to make codes that never clash.

🎯

Your win today: you can explain why the short code needs 7 base-62 characters (627 ≈ 3.5 trillion > 365 billion), how hash + collision resolution works, and why a Bloom filter saves database lookups.

1

Out of RAM, into a table

Data model

In the high-level design, every shortURL → longURL pair sat in one big hash table in memory (a hash table is a lookup structure: give it a key, get the value back fast). That's fine on a whiteboard. In real life it breaks: memory is limited and expensive, and ten years of links is about 36.5 TB (365 billion rows × ~100 bytes).[1]

The book's fix is plain: store the pairs in a relational database (rows and columns, like a spreadsheet with rules). Build the table. Tap a column to add it (or drag it in on desktop). Tap a column in the table to take it out again.

2

How many characters?

Find the smallest n with 62n ≥ 365 billion

The short code (the book calls it the hashValue) uses three groups of characters: digits 0-9, lower case a-z and upper case A-Z. That's 10 + 26 + 26 = 62 possible characters per position.[1]

Each extra character multiplies the number of possible codes by 62. So n characters give 62n codes. We need room for 365 billion URLs (100 million a day for ten years). The question is the smallest n where 62n ≥ 365 billion.

The book's answer: n = 7. 626 is about 56.8 billion, which is short. 627 is about 3.5 trillion, so 7 characters cover 365 billion with roughly 9.6× to spare. Drop the upper-case letters and you're down to 36 characters, and 367 ≈ 78 billion isn't enough. You'd need 8 characters. A bigger alphabet buys a shorter code.
3

Hash it and chop it

CRC32, MD5, SHA-1, then the first 7 characters

Now we need a way to turn a long URL into a 7-character code. The book's first idea: run it through a well-known hash function. A hash function turns any input into a fixed-length fingerprint, and the same input always gives the same output. The book tries three: CRC32, MD5 and SHA-1.[1]

4

Collision lab

Append a predefined string and try again

Collisions will happen, so the book adds a loop around the hash:[1]

  1. Hash the long URL and keep the first 7 characters.
  2. Look that code up in the database.
  3. Taken? Append a predefined string (a fixed piece of text the system always uses) to the input and hash again.
  4. Repeat until the code is free, then save the row.

To make collisions easy to see, this lab shrinks the problem: codes are just 2 characters from a 6-letter alphabet (a to f), so there are only 6 × 6 = 36 slots. Eight links are already stored. Add more and watch the loop work. Every "is it taken?" check is one database query.

Why it climbs. If a fraction f of the slots is taken, each try lands on a free slot with chance (1 − f). On average that takes 1 / (1 − f) tries. At 50% full that's 2 lookups. At 80% full it's 1 / 0.2 = 5. At 90% it's 10. The salted input is only fed to the hash. The row still stores the original long URL.
Honest caveat: it's not rare at real scale either. The real space is 627 ≈ 3.5 trillion. By year ten, 365 billion of those are used, about 10%. So roughly 1 new URL in 10 collides on its first try. This is the birthday effect:[3] clashes show up far sooner than intuition says. Retries are routine, so every extra lookup matters.
5

The Bloom bouncer

Skip the DB when the answer is "definitely not"

Every collision check costs a database query. The book's fix is a Bloom filter: a small, space-saving structure that tests whether something is in a set.[1][2] You met one in Quest 6.7. It's a row of bits (0 or 1) plus a few hash functions:

  • Add a code: each of 3 hash functions picks a bit, and all 3 bits are set to 1.
  • Check a code: look at its 3 bits. Any bit is 0? Then it was definitely never added. All are 1? It's probably there, but other codes might have set those bits.

Think of it as a bouncer in front of the database. "Definitely new" means skip the query and use the code. "Maybe taken" means ask the database. This filter has 32 bits and 3 hash functions.

Why it fits this design. A basic Bloom filter can add items but can't remove them (clearing a bit could erase other codes too). That's fine here: our short URLs are never deleted. And the filter never gives a false negative: if a code was added, its bits are 1 forever, so the filter can never wrongly say "definitely not".
Honest caveat: small, but not a toy. At a 1% false-positive rate a Bloom filter needs about 9.6 bits per item.[2] For 365 billion codes that's around 440 GB. Far smaller than the 36.5 TB of data, but it still has to be split across machines (or kept per database partition) and rebuilt when a server restarts.

🎓 Level-up note (for later)

  • The hex shortcut quietly shrinks the space. "First 7 characters" of a hex hash gives only 167 ≈ 268 million codes, under 3 days of traffic. A real design takes enough hash bits (about 42 for 7 base-62 characters) and writes them in base 62.
  • Same URL, same code. Hashing is deterministic, so two users who shorten the same URL get the same short link and share its click stats. Handy for de-duplication, but salt with the user ID if links must be private to each user.
  • Close the race in the database. Two servers can both ask "is abc1234 free?", both hear "yes", and both insert. A unique index on shortURL makes the database reject the second insert, and that writer simply retries.
  • Birthday math. With 10% of a space used, about 1 in 10 new inserts clashes on the first try.[3] Plan for retries as normal traffic.
