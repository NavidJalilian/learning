Follow the request

Everything on one machine

Day one of a new app. One server runs everything: the web app, the database and the cache.[1] Users reach it from a web browser or a mobile app.

A few words first. An IP address is a server's number on the internet, like 15.125.23.214. DNS (Domain Name System) is the internet's phone book: you give it a name like api.mysite.com and it gives back the IP. HTTP is the request-and-response language browsers and apps use to talk to servers.[2]

Split off the data

Web tier, data tier, and which database

Users pile in and one box can't keep up. The first fix in the book: give the database its own server. Now there are two tiers (layers): a web tier that handles requests, and a data tier that stores data. Each one can now grow on its own.[1]

Drag the database out of the box (or tap it).

Which database?

Two big families. Relational databases (RDBMS, queried with SQL: MySQL, Oracle, PostgreSQL) keep data in tables of rows and can join tables together, for example orders with customers. They've been around for over 40 years. Non-relational databases (NoSQL: CouchDB, Neo4j, Cassandra, HBase, Amazon DynamoDB) usually can't join.[1]

The book's rule. Relational is the default for most developers. NoSQL may be the right pick if: (1) you need super-low latency (very fast answers), (2) your data is unstructured or has no relationships, (3) you only need to serialize and deserialize it (turn it into JSON, XML or YAML text and back), or (4) you store a massive amount of data.

Up or out?

Vertical vs horizontal scaling

Two ways to handle more traffic. Vertical scaling ("scale up") means a bigger machine: more CPU, more RAM. Horizontal scaling ("scale out") means more machines in a pool.[1] Scaling up is simple, and while traffic is low it's a fine choice.

What you just saw, in the book's words. Scaling up has a hard limit: you can't add CPU and memory to one server forever. And it has no failover or redundancy (no spare to take over): if that one server goes down, the whole site goes down with it.[1] That one server is a single point of failure: one part whose failure stops everything.[3] Users connect straight to it, so if it's offline they can't reach the site, and if too many arrive at once it slows down or refuses them. Scaling out fits large systems better. But it needs something to spread the traffic.

Hire a bouncer

The load balancer

A load balancer (LB) sits in front of your web servers and spreads incoming requests across them.[4] Users now connect to the LB's public IP (the book's figure uses 88.88.88.1). The web servers only get private IPs like 10.0.0.1. A private IP works between servers on the same network, but the internet can't reach it. That's safer, and the LB talks to the servers over those private IPs.[1]

Honest caveat: who balances the balancer? One LB is itself a single point of failure. Real setups run LBs in redundant pairs, or use a managed cloud LB that is redundant under the hood. The book's diagram shows one box to keep things simple.

🎓 Level-up note (for later)

  • Scaling up is underrated. Many big sites ran on surprisingly few large machines for years, and a bigger box is often the cheapest first fix. Scaling out adds moving parts you have to run and debug.
  • The LB can be a single point of failure too. Real setups run load balancers in redundant pairs or use a managed cloud LB.
  • SQL vs NoSQL is blurrier today. PostgreSQL can store and index JSON, and distributed SQL databases (Google Spanner, CockroachDB) scale out across many machines. Pick on how you read and write the data and how consistent it must be, not on the label.
