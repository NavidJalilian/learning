1

Where do counters live?

Redis, INCR and EXPIRE

Every algorithm from Quests 4.2 and 4.3 boils down to one idea: count. Keep a counter for each user (or IP address, or API key). If the counter goes over the limit, refuse the request.[1]

So where does the counter live? The book rules out the database. A database keeps its data on disk, and disk is slow. This check runs on every single request, so it has to be fast. The book picks an in-memory cache instead: it's fast, and it can delete data on a timer by itself. The popular choice is Redis, a key-value store that keeps everything in memory. Two commands do the work:[1]

  • INCR key adds 1 to the number stored at that key. A missing key counts as 0, so the first INCR returns 1.[2]
  • EXPIRE key 60 gives the key a TTL (time to live). After 60 seconds Redis deletes the key on its own.[3]

The request first reaches the rate limiting middleware, a layer of code that sits in front of your API servers. In the book's flow, the middleware reads the counter from Redis. If the limit is reached, the request is rejected. If not, it goes on to the API servers, and the counter is incremented and saved back. Limit here: 5 requests per 60 s. Book flow vs. real code. The book reads the counter, checks it, and increments only when the request is allowed. That's what the sim does. Many real limiters skip the read and run INCR first, then compare the number it returns. That's one round trip instead of two, but rejected attempts get counted too. Reading and then writing in two steps also opens the door to race conditions, which is Quest 4.5's topic.

Write the rules

Lyft-style rule config

Counters need rules: what to count, and how many is too many. The book points to Lyft, which open-sourced its rate-limiting service. Rules are written in configuration files and saved on disk.[1][4]

A rule has a domain (which part of the product it covers) and a descriptor: a key naming a kind of request and a value picking one specific kind. Then comes the rate_limit: a time unit (second, minute, hour or day) and requests_per_unit. The file is written in YAML, a format where indentation shows what belongs to what.

Turn each English rule into YAML. When it's right, test it.

Where it lives now. Lyft's service moved under the Envoy project: envoyproxy/ratelimit. Its README still uses this same domain / descriptors / rate_limit layout.[4]
3

Tell the client

429, headers, and how a good client backs off

When a request is over the limit, the API answers with HTTP status 429 Too Many Requests. Depending on the use case, the request may also be put in a queue to run later. The book's example is orders that got rate limited because the system was overloaded: you'd rather keep them than lose them.[1]

How does a client know it's close to the limit? From HTTP response headers, the small Name: value lines sent with every response. The book uses three:[1]

X-Ratelimit-LimitHow many calls the client may make in each time window.
X-Ratelimit-RemainingHow many allowed requests are left in the current window.
X-Ratelimit-Retry-AfterHow many seconds to wait before trying again without being throttled. Sent with the 429.

Be the API. The limit is 5 requests per 60-second window, and the window started at t = 0 s. Fill in each response, and leave a header blank if it isn't sent. Request #1 is done for you.

The client side

Request #6 got a 429 with X-Ratelimit-Retry-After: 35. Two different apps get that same response. The impatient one retries every half second. The polite one waits the 35 seconds plus a little jitter (a small random extra wait, so thousands of clients don't all retry in the same instant).[8]

The book ends the chapter with advice for people writing clients. Four of these six are on its list. Tap those four, then check.

Honest caveat: header names vary. X-Ratelimit-* is a common habit, not a standard. GitHub, for example, sends x-ratelimit-limit, x-ratelimit-remaining and x-ratelimit-reset, where reset is a clock time, not a number of seconds.[7] The standard header for "wait this long" is plain Retry-After.[5] The IETF is drafting standard RateLimit and RateLimit-Policy headers.[6] In an interview, the book's names are fine. Just show you know the idea.

🎓 Level-up note (for later)

Key design matters for the bug in stage 1. If the key has the time window built into its name (say rl:user42:14:03 for the minute 14:03), a missing EXPIRE doesn't lock anyone out. Next minute uses a fresh key. Instead the old keys pile up forever and slowly eat Redis's memory. Either way, make INCR and EXPIRE atomic: a Lua script, a MULTI/EXEC transaction, or set the TTL only when INCR returns 1 inside the same script.[2] Backoff, done well, usually means exponential backoff (double the wait after each failure) with full jitter, as AWS showed.[8] When the server sends a Retry-After, honour it first.
