Ring Math

You've seen the hash ring as a picture. Now put numbers on it: how many keys % N really moves, how big the ring is, how code finds a server, and exactly which keys move when a server comes or goes.

🎯

Your win today: you can put numbers on the rehashing problem (adding 1 server to N moves about N/(N+1) of keys with % N, but only about 1/(N+1) on a ring), explain the hash space and how arcs become ownership shares, sketch the lookup as a binary search over sorted positions, and walk an interviewer through exactly which keys move, and from which server, when a node joins or leaves.

Do the rehash math

Put an exact number on "most keys move"

The book starts with N cache servers. To pick a server for a key, you compute serverIndex = hash(key) % N.[1] A hash turns the key into a big, random-looking number. % N keeps the remainder after dividing by N, so you always get a server number from 0 to N−1.

Part B · Does it get better with more servers?

Here's the general rule. When you go from N to N+1 servers, a key stays put only if hash % N happens to equal hash % (N+1). For random hashes that happens for 1 key in N+1. Everything else moves. Before you see the curve, make a call.

with % N?of keys move
on a ring?of keys move
Modulo gets worse as you grow. The ring gets better. With % N, adding one server moves N/(N+1) of keys: 4→5 moves 80%, 9→10 moves 90%, 99→100 moves 99%. Shrinking is just as bad: N→N−1 moves (N−1)/N, so 4→3 moves 75%, exactly what your table showed. Consistent hashing promises that only about k/n keys move on average (k = number of keys, n = number of slots or servers).[3] So the (N+1)th server takes about 1/(N+1) of keys, and removing one of N servers moves about 1/N: just the dead server's own share.
Honest caveat. These clean numbers assume hashes are uniformly random and, for the ring, that every server owns an equal slice. That even split needs virtual nodes (Quest 5.2). On a basic ring with one random position per server, a new server might land in a huge gap or a tiny one, so the share that moves can be far above or below 1/(N+1).

Bend the number line

Hash space, hash ring, and what an arc is worth

The hash space is every value a hash function can output. The book's example is SHA-1, whose output runs from 0 to 2160−1. That's about 1.46 × 1048 possible values.[1] Picture it as a very long number line. Now join its two ends.

One number line, from 0 to 2¹⁶⁰−1.

That circle is the hash ring. Servers are hashed onto it (by IP address or name), and keys are hashed onto the same ring with the same function. There's no % N step anymore. A server's partition is the arc that ends at it: from the previous server (anticlockwise) up to and including the server itself. Its share of keys is that arc's length over the whole ring:

share = ((posserver − posprevious) mod S) / S   S = size of the hash space

The mod S handles wrap-around: if the previous server sits just before the top and this one just after it, the plain difference is negative. On a ring of 2160 positions nobody can see anything, so this toy ring has 256 positions (0 to 255). The maths is identical.

So why such a huge space? Two keys (or two servers) landing on the exact same spot would be a tie the ring can't break.

With a trillion keys (n = 1012), the chance that any two share a SHA-1 position is about n² / 2161 = 1024 / 2.9 × 1048 ≈ 3 × 10−25. That will never happen. Real systems pick other sizes: Amazon's Dynamo hashes keys with MD5, a 128-bit space,[5] and Cassandra's default Murmur3 partitioner uses 64-bit tokens from −263 to 263−1.[6] Ring size changes the resolution, not the idea.
"Isn't SHA-1 broken?" For security, yes: researchers have produced SHA-1 collisions on purpose. But placing keys on a ring isn't a security feature, so it doesn't matter here. Real systems usually prefer fast non-cryptographic hashes such as Murmur3 (Cassandra) or have used MD5 (Dynamo).

Clockwise, in code

Server lookup is a binary search with a wrap

The book describes lookup as "start at the key and walk clockwise until you hit a server."[1] Real code never walks. It keeps every server position (a token) in a sorted array and does a binary search for the first token that is ≥ the key's hash. If the hash is bigger than every token, the walk wraps past the top of the ring, so the answer is the first (smallest) token.

Toy ring, 0 to 99. Four tokens: s0 at 12, s1 at 40, s2 at 71, s3 at 93. For each key, tap the token that owns it, then watch the search run.

tokens = [12, 40, 71, 93] · lo / mid / hi are the search pointers

Two details that matter. A key that lands exactly on a server's position belongs to that server (the ≥ rule). And the ring is tiny metadata, just a sorted list of positions. Every client or router keeps a copy, and it only changes when servers join or leave. Tom White's well-known Java version does the same thing with a sorted map: look for the first entry at or after the hash, and if there isn't one, take the first entry.[4]

Who has to move?

The book's method for finding affected keys

When a server joins or leaves, you need to know exactly which keys move, because those are the ones you copy (or, in a cache, the ones that will miss). The book gives a rule for each case:[1]

  • A server joins: start at the new server and go anticlockwise until you reach the previous server. Every key in that arc moves to the new server. They all come from the new server's clockwise neighbour, which used to own that arc.
  • A server leaves: start at the leaving server and go anticlockwise to the previous server. Every key in that arc moves to the leaving server's clockwise neighbour.

Nothing else on the ring changes. Grab the highlighter. Each round: tap every key you think will move (on the ring or the chips), answer the server question, then press Apply.

"Move" means different things. In a cache, a moved key just means one miss, then a refill from the database. In a database, the keys in the affected arc must actually be copied to the new owner before it starts answering for them. The book's chapter stops at deciding which keys move. The good news is the rule also tells you where to copy from, and the copy is limited to one arc.

🎓 Level-up note (for later)

The neat 1/(N+1) only holds when every server owns an equal slice. On a basic ring with one random position per server, slices vary a lot, so a joining server might take far more or far less than its fair share. That's one reason real systems use many virtual nodes (Quest 5.2). Also, "which keys move" is only step one of a real migration. In a store like Cassandra, a joining node streams its new ranges from the current owners before it starts serving them.[6] And if you ever change the hash function itself, every key and every server lands somewhere new, so treat it like a full data migration.
