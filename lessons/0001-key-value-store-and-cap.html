The Key-Value Vault

Build a tiny database, overflow it, split it across servers — then cut the network and decide what breaks.

🎯

1

Meet the vault

What a key-value store is

A key-value store is the simplest database there is: one giant dictionary. Every key is unique, and it points to exactly one value. It speaks two commands:[1]

  • put(key, value) — store this value under this key
  • get(key) — give me back whatever is under this key

Keys can be plain text (last_logged_in_at) or a hash (253DDEC4). Shorter keys are better — less memory, faster to compare. Values can be anything (a string, a list, an object) and the store treats them as an opaque blob: it never looks inside. Redis, Memcached and Amazon's Dynamo all work this way.

On one server, the obvious build is a hash table in memory: run the key through a hash function, which turns it into a number that picks a "bucket" to put the pair in. Try it 👇

// type a command, or tap one below
❯
hash(key) % 8 → bucket

The vault fills up

Why one server isn't enough

Memory is fast, but small. Your app gets popular and the data keeps coming. The book gives two tricks to squeeze more into one server:[1]

  • Compression — shrink the values.
  • Hot in memory, cold on disk — keep only frequently used data in fast memory; park the rest on the slower, bigger disk.

Three promises: CAP

The rule every distributed store lives by

Spreading key-value pairs across many servers gives you a distributed key-value store (also called a distributed hash table). To make it survive crashes, each piece of data is copied to several servers — these copies are called replicas. Now three promises compete:

C

Consistency

Every client sees the same, latest data, no matter which node it asks.

C
A

Availability

Every request gets an answer, even if some nodes are down.

A
P

Partition tolerance

The system keeps running when the network between nodes breaks (a "partition").

P

The CAP theorem: a distributed system can't guarantee all three at once.[2] And since networks do break, P isn't optional — so the real question is: when the network splits, do you keep C or keep A?

The Split

Predict, then watch it happen

Your data — a bank balance — is copied to three replicas: n1, n2, n3. Each round, predict what happens, then watch. Right calls earn XP; wrong ones cost a heart.

Mode CPAP🟢 network healthy
balance = 100 on all replicas.
Honest caveat — the book simplifies here. The book's CP system blocks writes on n1 and n2 too. Many real CP systems (ones using majority voting, like Raft) let the majority side (n1 + n2) keep working and only make the cut-off minority (n3) refuse. Same principle — never serve data you can't vouch for — but less downtime. You'll meet majority voting ("quorum") in Quest 6.4.
🧪 Sandbox unlocked. Break things on purpose. Try writing to both sides during a split in AP mode, then heal — what does the system do with two different values?

🎓 Level-up note (for later)

"Pick 2 of 3" is a useful first model, not the whole truth. Its own author says it's misleading[3], and real databases rarely fit cleanly in a CP or AP box[4] — many let you choose per request. That's the "tunable consistency" requirement in the book, and it's coming in Quest 6.4.
