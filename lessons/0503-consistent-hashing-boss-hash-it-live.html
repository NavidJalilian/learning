Honest caveats. (1) The book says 100–200 virtual nodes bring the spread of load down to about 10%–5% of the average. That 5% is on the optimistic side: with random placement the spread shrinks roughly like 1 ÷ √(virtual nodes), so halving it costs four times as many. (2) Every virtual node is a ring entry that every client stores and that each membership change must ship around: 60 servers × 200 = 12,000 entries. Cheap here, but not free. (3) Replicas on the next distinct servers clockwise (Quest 6.3, Copies Everywhere) only matter once this cache becomes a store.

Honest caveats from the curveballs. (1) The book doesn't cover how to change a hash function or copy data when a node joins a database; the migration and streaming answers here are common practice, not the book's text. (2) "Hash a stable server ID" is our advice; the book hashes servers by IP address or name. (3) For a single hot key, the book's wrap-up says consistent hashing helps with hotspots. That is true when the hot data is many keys that happen to bunch on one shard; one very hot key still lives on exactly one server.

🎓 Level-up note

Three things a strong candidate adds that the chapter doesn't. Membership: the ring is only as right as the server list; clients need one source of truth (ZooKeeper, etcd, or gossip) and must tolerate a few seconds of disagreement. Data movement: for a cache, a moved key is just a miss; for a database, the new owner must receive its arcs before it serves them, which is a copy protocol of its own. Alternatives: rendezvous hashing (every client scores every server per key and picks the top one), jump consistent hash (no ring, near-zero memory, but servers can only be added or removed at the end of a numbered list), and Maglev's fixed-size lookup table (very even, a little extra movement on change). Then run this interview out loud once with a 45-minute timer.
