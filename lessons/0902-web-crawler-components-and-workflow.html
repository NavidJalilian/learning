1

Pick your seeds

Where does the crawl start?

A crawler needs somewhere to begin. Those first addresses are the seed URLs. If you only had to crawl one university's website, the seed is easy: its home page.[1]

For the whole web it's a judgement call. You want seeds whose links fan out to as much of the web as possible. The book's suggestion: carve the web into pieces and seed each piece. You can cut by locality (each country has its own popular sites) or by topic (shopping, sports, healthcare…). There's no single right answer, and the interviewer doesn't expect one. They want to hear you think about coverage.

Try it. This toy web has 60 pages in six regions: 3 countries × 2 topics. Pages mostly link to pages in their own region. Dashed lines are the rare links between regions. Tap up to 4 pages to pin as seeds, then crawl for 3 hops (a hop = follow every link one step). Big dots are hubs, pages with lots of outgoing links.

Meet the eleven boxes

Who does what in the pipeline

The book's high-level design has eleven parts.[1] Most names explain themselves once you know the job. Two jargon words first: a queue is a line where the first thing in is the first thing out (FIFO). DNS is the internet's phone book: it turns a name like www.wikipedia.org into an IP address a computer can connect to.

A job appears below. Tap the box that does it. Each box you place shows a tiny example of it at work.

Two design details worth saying out loud. The Content Parser is its own box because parsing is slow work, and you don't want it holding up the downloaders. Content Storage keeps most pages on disk, because there are far too many for memory, and caches the popular ones in memory so they can be read fast.

Be the URL Extractor

Pages often link with relative paths, meaning paths that only make sense next to the page's own address. The extractor turns each one into a full (absolute) URL. You're parsing this page:

https://en.wikipedia.org/wiki/Spider

Beyond the book: normalise, too. The book only mentions making links absolute. Real crawlers also normalise (canonicalise) every URL before checking it: lower-case the host, drop the #fragment and the default port, resolve .. segments, sometimes sort query parameters. Otherwise one page sneaks in under many spellings.[5]
3

Have I seen this page?

Content Seen? · compare fingerprints, not characters

The same content turns up under different URLs all the time: http and https versions, / and /index.html, mirror sites, tracking parameters. The book cites a figure of about 29% of pages being duplicates.[1] Storing them all wastes disk, and crawling their links again wastes time.

The naive check is to compare a new page against every stored page, character by character. The book's point: with billions of pages that's hopeless. Instead, compute a hash of each page: a short, fixed-size number (a fingerprint) that's the same whenever the bytes are the same. Keep the fingerprints in a set and look the new one up. Same fingerprint → same content → throw the page away.

What the race shows. The slow lane has to open every stored page for every new page, so its cost grows with the store. Honest caveats. A plain hash only catches byte-for-byte copies. Search engines catch near-duplicates (pages that differ by an ad, a date or a session ID) with fancier fingerprints such as shingling or SimHash, which give similar pages similar fingerprints.[4] And the 29% figure comes from an SEO-industry estimate, not a careful count of the whole web. Treat it as "a lot, roughly a third".
4

Have I seen this URL?

URL Seen? · hash table or Bloom filter

URL Seen? asks a different question: has this address already been fetched, or is it already waiting in the frontier? Skip this check and the same URL gets queued over and over. That piles load on websites, and a pair of pages that link to each other (A → B → A) traps the crawler in an endless loop.[1]

The book names two usual tools. A hash table stores every URL (or its fingerprint) and answers exactly, but it eats memory. A Bloom filter is a row of bits plus a few hash functions.[3] To add a URL, hash it with each function and switch those bits on. To check a URL, look at its bits: if any is off, the URL was definitely never added; if all are on, it was probably added.

How big does it get?

Beyond the book, but interviewers love it. Memory to remember every URL, three ways. Assumptions: about 100 bytes per raw URL, 8-byte fingerprints in a hash set (before the table's own overhead, often 1.5–2×), and a Bloom filter sized for a 1% false-positive rate, which needs about 9.6 bits per URL.[3]

The book's crawler fetches about 1 billion pages a month (quest 9.1).
Honest caveat: Bloom filters at web scale. You can't delete from a plain Bloom filter, and its false-positive rate climbs as it fills. So real crawlers size it for the expected count, split it across machines, and rebuild it now and then. Every false positive is a brand-new URL that silently never gets crawled.

🎓 Level-up note (for later)

Three places where real crawlers go further than the whiteboard. Near-duplicates: exact hashes miss pages that differ by a timestamp, so production systems use shingling or SimHash.[4] URL normalisation happens before URL Seen?, or the same page gets queued under many spellings.[5] The URL-seen set at web scale is sharded across machines. Mercator kept a small in-memory cache of recent URLs in front of a big on-disk set, because most links point to pages seen recently.[2]
