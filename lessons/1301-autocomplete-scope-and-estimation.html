Quest 13.1 · Design a Search Autocomplete System

Every Keystroke Counts

You type "tw" and a box already guesses "twitter". Before you design the machine behind it, find out what it must do and how hard it gets hit. Every letter you type is a request.

🎯

Your win today: in the first 5 minutes you can pin down what autocomplete must do (prefix match, top 5, ranked by popularity, under 100 ms), work out ~24,000 QPS / ~48,000 peak / 0.4 GB a day out loud, and explain why a frequency table queried with LIKE 'prefix%' collapses at that scale.

1

Ask before you build

The requirements interview

Autocomplete goes by many names: typeahead, search-as-you-type, incremental search. As you type, a dropdown suggests the full queries you most likely mean.[1]

The interviewer has just said: "Design search autocomplete." That's all you get. Below are nine questions you could ask. Seven change the design. Two waste the interviewer's time and cost a heart. Each useful answer gets pinned to your board.

    What "fast" means

    Non-functional requirements

    Stage 1 covered what the box does. Non-functional requirements say how well it must do it. The first one is speed. Suggestions have to keep up with typing. The book borrows a target from Facebook's write-up on its typeahead: answer within about 100 milliseconds, or the box starts to stutter.[1][2]

    Test it. A ghost typist types dinner, one key every 150 ms. Each key sends a request. Each bar below is one request, from the moment it's sent until its answer comes back. If an answer arrives after the next key, it's out of date: stale.

      Five qualities, one line each

      The book lists five non-functional requirements.[1] Tap a word (or drag it), then tap the line it belongs to. A wrong match bounces back.

      • ✓Play at 100 ms or faster: every answer beats the next key
      • ✓Play above 100 ms and catch a stale answer
      • ✓Match all five qualities to their meaning
      Honest caveat. 100 ms is a rule of thumb from Facebook's article, not a standard. It lines up with long-standing usability research that about 0.1 s is the limit for a response to feel instant.[3] Real typists aren't metronomes, and fast ones type faster than 150 ms per key.
      3

      Envelope math

      Calculate, then check

      Back-of-the-envelope estimation means rough maths to get the size of the system right, not the exact digits.[4] The book's assumptions:[1]

      10,000,000 DAU10 searches / person / day20 bytes / query1 request / character typed20% of queries are new86,400 s / day

      Why 20 bytes? An average query is about 4 words of about 5 characters each, so roughly 20 characters. Plain ASCII text uses 1 byte per character. And the box sends a request for every character. Watch "dinner":

      Requests sent: 0

      Fill in each row. Answers within about 10% count: this is envelope math. Use Hint if you're stuck. It shows the formula, never the answer. A first wrong answer on a row costs a heart; after that, retries are free.

      📄 For the cheat sheet

      ~20requests per search
      ~24kQPS on average
      ~48kQPS at peak
      0.4 GBnew data per day
      Honest caveats. (1) Real clients usually debounce: they wait until the user pauses for a few tens of milliseconds before sending, so real request counts are lower. The book's one-request-per-character is a deliberately pessimistic upper bound. (2) 0.4 GB counts only the new query strings. It leaves out the counters, raw logs and the lookup structures added in later quests, which are much bigger.

      Two boxes and a table

      The high-level design, and where it breaks

      The book's first sketch has just two services.[1] The data gathering service collects the queries people type and keeps a running count for each one in a frequency table (two columns: query, frequency). The query service takes a prefix and returns the 5 most frequent queries that start with it.

      Toy model, real shape. The costs in this sim are made up so the effect is visible. The shape is real: the work per request grows with the rows that match, and total load is that work times the request rate. With an index (a sorted lookup structure) on query, LIKE 'tw%' can jump straight to the tw rows. '%tw%' can't. But the database still has to sort every match by frequency on every keystroke. The book's verdict: fine while the data is small, a bottleneck once it's large.[1]

      🎓 Level-up note (for later)
      
      
        
        
      • Rounding. 10,000,000 × 10 × 20 ÷ 86,400 is about 23,150. The book says ~24,000. Rounding up is normal in envelope math, so say so out loud: "about 23 thousand, call it 24."
        • 
        
      • Debouncing. The 20-requests-per-search figure assumes a request on every keystroke. Real clients usually wait for a short pause in typing before sending, so the real count is lower. The book's number is a safe upper bound.
        • 
        
      • Storage. The 0.4 GB a day counts only new query strings. Frequency counters, raw query logs and the per-node top-5 lists you'll add later are much bigger.
        • 
        
      • 100 ms. It comes from Facebook's typeahead article. It's a good rule of thumb, not a universal standard.
