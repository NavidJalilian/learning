Honest caveat: the header names are a convention. X-Ratelimit-Limit, -Remaining and -Retry-After are what the book uses, and many APIs send similar ones, but they aren't a standard: each API picks its own names and meanings (GitHub, for example, sends x-ratelimit-reset, a clock time, instead of a retry-after in seconds). The status code is standard: 429 is defined in RFC 6585[8]. Plain Retry-After is a standard HTTP header, and the IETF is drafting standard RateLimit headers[9].

Boss: the curveball barrage

Step 3 · "what happens when…?"

Now the interviewer stops nodding and starts poking holes. Nine curveballs, mixed from every quest in the chapter. Each right answer costs 1.5 minutes; a wrong one costs a heart and an extra minute of backtracking.

Honest caveats from the curveballs. (1) INCR and EXPIRE are two separate commands. If the limiter crashes between them, the key never expires. Send them together in a MULTI transaction or a Lua script; Redis's own docs show this rate-limiter pattern[7]. (2) "Fail open" isn't in the book; it's how teams meet the book's fault-tolerance requirement. Stripe describes catching errors so that a bug or a Redis outage fails open and the API keeps working[3]. For abuse-prone endpoints like login, some teams choose to fail closed instead.

🎓 Level-up note

What the book glosses over. (1) A single Redis is both the hot path and a single point of failure. Real deployments shard it and add replicas, and accept that a failover can lose a few counts. (2) "Distributed limit" usually means approximately global: with edge servers syncing eventually, a client can briefly exceed the limit, which makes it a soft limit in practice. (3) Off-the-shelf options exist. Lyft's open-source ratelimit service (the source of the book's YAML rule example) runs beside the Envoy proxy and keeps its counters in Redis, and Google Cloud's rate-limiting guide walks through where each layer belongs. Saying "I'd evaluate the gateway we already run before building one" is the same advice the book gives.
