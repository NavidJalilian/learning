Hot Memory, Near Edge

1

The read-through loop

Cache tier basics

Every time a page loads, your web server usually asks the database for something: a profile, a product, a price. Asking again and again for the same data is slow, and it keeps the database busy.[1]

A cache is temporary storage that keeps results that were expensive to get, or data asked for often, in memory (RAM). The next request for the same thing is answered from memory, which is much faster. In the book, the cache tier is its own layer of cache servers that sits between the web servers and the database. It gives you three wins: faster pages, less work for the database, and a layer you can scale on its own.[1]

The book's strategy is called read-through: the web server asks the cache first. If the data is there (a hit), it returns it. If not (a miss), it reads the database, stores a copy in the cache, then returns it. You are the web server now. Serve 6 requests by pressing the steps in the right order.

2

Five cache questions

When, how long, how fresh, what if it dies, what to evict

Adding a cache raises five questions. The book lists them as things to think about before you use one:[1]

1When to use it

For data that's read often and changed rarely. Cache memory is volatile: a restart wipes it. So the real copy of important data stays in a persistent store, like the database.

2Expiration

Expired data is removed. Too short and the DB is hit too often. Too long and the data goes stale (out of date).

3Consistency

The DB and the cache must agree. A write to both isn't one transaction, so they can drift. Across regions it's harder still.[2]

4Failures

One cache server is a single point of failure (SPOF): if it dies, everything behind it suffers. Run several, across data centers, and give them spare memory.

5Eviction

When the cache is full, adding an item pushes another out. LRU is the most popular rule. LFU and FIFO are others.

Honest caveat: invalidation and stampedes. A common pattern on write is: update the database, then delete the cache key so the next read refills it. Races can still leave an old value behind, which is why teams keep a TTL as a safety net. Facebook's Memcache paper is a long story about exactly this.[2] And when a hot key expires, or a cache node dies, thousands of requests can miss at once and stampede the DB. That's the thundering herd, and one reason the book says to run several cache servers.

Edge of the map

How a CDN serves a file

A CDN (content delivery network) is a set of servers spread around the world that hand out static content: files that are the same for everyone, like images, videos, CSS and JavaScript. When a user visits, the CDN server closest to them answers. The farther a user is from the CDN servers, the slower the page loads.[1]

The CDN servers are called edges. The place where the real file lives is the origin: your web server, or file storage such as Amazon S3. The page links to the file through the CDN's domain, for example https://mysite.cloudfront.net/image.png. Here's the book's six-step flow. Predict each request first, then watch.

  1. A user requests image.png through a CDN URL.
  2. The edge doesn't have it, so it asks the origin.
  3. The origin returns the file, optionally with a TTL in an HTTP header.
  4. The edge caches it and sends it to the user. It stays until the TTL runs out.
  5. Another user asks the same edge for image.png.
  6. The edge serves it from its cache, as long as the TTL is still valid.

4

CDN gotchas

Cost, expiry, fallback, invalidation

The book flags four things to watch once a CDN is in place:[1]

  • Cost. A third party runs the CDN and charges for data moved in and out. Caching files that are rarely asked for costs money and gains little.
  • Cache expiry. For content that changes with time, pick the expiry with care. Too long and it's stale. Too short and edges keep re-fetching from the origin.
  • CDN fallback. If the CDN goes down, clients should spot the problem and load the files from the origin.
  • Invalidating files early. To replace a file before its TTL ends, call the vendor's invalidation API, or use object versioning: change the URL, e.g. image.png?v=2, so edges see a brand-new object.

🎓 Level-up note (for later)

  • Read-through vs cache-aside. The book's "read-through" (your app checks the cache and loads on a miss) is usually called cache-aside. In a strict read-through, the cache does the DB load itself. There are also write-through and write-back caches, which handle writes differently.[3]
  • Invalidation on write is the hard part. Update the DB, then delete the cache key. Races can still leave a stale value behind, so keep TTLs as a safety net.
  • Thundering herd. When a hot key expires or a cache node dies, many requests miss at the same moment and hit the DB together. Fixes include letting only one request refill a key (request coalescing), adding a little randomness to TTLs, and serving the old value while one request refreshes it.
  • Eviction policies have trade-offs. LRU is simple and good for most workloads. LFU keeps long-term favourites but is slow to forget them. Real systems often use tuned variants.[4]
  • Version with hashes, not query strings. Many CDNs ignore the query string in the cache key by default, so teams put a content hash in the file name (app.3f9a1c.js).
  • CDNs do more than static files now. They can cache dynamic responses and run code at the edge. The book leaves that out to keep things simple.[5]
  • Latency numbers in the sims are illustrative. RAM is far faster than disk, and a nearby edge is far faster than a distant origin. The exact milliseconds here aren't measurements.
