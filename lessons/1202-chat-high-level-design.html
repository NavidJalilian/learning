Three kinds of service

Stateless, stateful, third-party

In Quest 12.1 you opened the pipe: every phone keeps a WebSocket (a connection that stays open both ways) to the chat service. Now zoom out. The book splits the whole system into three groups:[1]

  • Stateless services. "Stateless" means the server keeps nothing about you between requests, so any copy can answer. Login, signup, user profile, group management: a request goes in, a response comes out. They sit behind a load balancer (a front door that spreads requests over many identical servers). They can be one big app (a monolith) or many small microservices. Many can be bought off the shelf rather than built.
  • Stateful service. "Stateful" means a server holds something about you, so you have to keep talking to that same server. Here that's the chat service: your phone holds one open connection to one chat server and normally stays on it while that server is up.
  • Third-party integration. A service someone else runs. The big one is push notifications, so you still hear about a message when the app isn't running (that's Chapter 10, Quest 10.1).

One stateless service is special: service discovery. Its job is to tell your phone which chat server to connect to. Hold that thought for stage 4.

Can one box do it?

The book's memory math

Before scaling out, ask the honest question: could one server hold everyone? The book's numbers: about 1 million users connected at the same time (that's 2% of the 50 million daily users), and roughly 10 KB of server memory per open connection. The book stresses that 10 KB is a very rough figure that depends a lot on your programming language.[1]

Honest caveat: "how many per box" varies a lot. Real memory per connection depends on encryption (TLS) buffers, the language runtime and the operating system's socket buffers. In 2012 WhatsApp reported over 2 million connections on a single Erlang/FreeBSD server.[3] So the memory math is a sanity check, not the reason to scale out.

Build the switchboard

The adjusted high-level design

Here is the cast of the book's adjusted design (its figure 12-8):[1]

  • Chat servers send and receive messages.
  • Presence servers track who is online or offline (the green dot, Quest 12.5).
  • API servers handle everything else: login, signup, changing your profile and so on.
  • Notification servers send push notifications.
  • A key-value store (a database that looks data up by a key, like a giant dictionary) keeps chat history, so a user who comes back online sees everything they missed.

Phones reach the chat and presence servers over WebSocket, and everything else over plain HTTP through the load balancer. Other data, such as profiles and friend lists, lives in a relational database (Quest 12.3).

Who picks your server?

Service discovery with ZooKeeper

There are many chat servers. Which one should your phone connect to? That's the job of service discovery: it recommends the best chat server for you, using things like where you are and how full each server is. The book's example is Apache ZooKeeper,[2] an open-source coordination service. Every available chat server registers with it, and it picks one for each client by preset rules.[1]

Part 3 · A server dies

The book's wrap-up: if a chat server goes offline, service discovery hands its clients a new chat server to connect to.[1] A WebSocket can't be moved to another machine, so every phone on the dead server has to reconnect. Here's a separate toy cluster: server B holds 300 phones. Setting up a connection is expensive (encryption handshake, login check, fetching missed messages), so each server can safely accept about 60 new connections per second. The black line on each meter marks that limit.

Honest caveat: the book skips the stampede. When a server with hundreds of thousands of connections dies, all of those phones try to reconnect at once. Engineers call this a thundering herd. Real systems make each client wait a random, growing delay before retrying (exponential backoff with jitter) and keep spare capacity for exactly this moment.

🎓 Level-up note (for later)

  • 10 KB per connection is a round number. Kernel socket buffers, TLS state and your runtime decide the real figure. WhatsApp's 2 million on one box shows how far a tuned stack can go.[3]
  • ZooKeeper is only the book's example. Many teams use Consul, etcd, or their own "gateway assignment" service, often behind a layer-4 load balancer (one that routes raw TCP connections without reading them). What matters is the idea: a registry of healthy servers plus a placement rule. In ZooKeeper, servers usually register as ephemeral entries, which vanish by themselves when a server stops checking in.[2]
  • "Which server is Bob on?" To deliver a message, some part of the system has to find the chat server holding Bob's connection. Real systems often keep a session (route) table mapping each user to their gateway. The book leaves this implicit in its 1-on-1 flow (Quest 12.4).
  • Reconnect storms are a real outage cause. Randomised exponential backoff on clients, plus spare capacity and rate limits on the servers, keep one dead box from knocking over its neighbours.
