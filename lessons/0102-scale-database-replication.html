One writer, many readers

Master/slave in one picture

In Quest 1.1 you put a load balancer in front of two web servers, so the web tier survives losing a server. The data tier doesn't. There is still one database. If it dies, every web server is left with nothing to talk to. That is a single point of failure (SPOF): one part whose failure takes everything down. The book points out that this design has no failover (switching to a backup) and no redundancy (spare copies).[1]

The fix is database replication: keep copies of the same data on more than one database server.[2] The book's setup has one original, the master, and several copies, the slaves. The rules:[1]

  • The master handles the writes: every statement that changes data (INSERT, UPDATE, DELETE).
  • Each slave receives a copy of the master's data and handles reads only (SELECT).
  • Most apps read far more than they write, so you usually run more slaves than masters.
Words. Master/slave is the book's wording and the older term. Most docs today say primary/replica (or leader/follower). Interviewers accept either. This quest says master and replica.

Why bother?

Three wins of replication

The book lists three advantages of replication.[1] Learn to tell them apart, because interviewers like to ask "which one does that give you?"

  • Better performance. All writes go to the master, and reads are spread over many replicas. More queries run in parallel (at the same time on different machines).
  • Reliability. If one database server is destroyed (the book's example is a natural disaster such as a typhoon or an earthquake), the data is not lost, because copies live on servers in other places.
  • High availability. Because the data is in several places, the site keeps working when one database goes offline. It just reads from another server.

The difference between the last two: reliability is about data surviving. Availability is about the site still answering.

Pull the plug

When a replica or the master dies

Replication only helps if you know what happens when a server dies. The book covers two cases:[1] a replica goes offline, or the master goes offline. One more word first. A replica copies the master's changes a moment after they happen, so it can be a few writes behind. That gap is called replication lag. Each replica below shows how many writes behind it is.

The book's honest note. In real systems, promoting a new master is harder than it looks, because a replica's data may not be up to date. The missing data has to be patched by running data recovery scripts. Other setups, such as multi-master (several servers accept writes)[3] and circular replication (each server copies from the one before it, in a loop)[4], can help, but they are more complicated. The book leaves them out of scope, and so do we.[1]

    🎓 Level-up note (for later)

    • Failover is more than "promote a replica". You have to detect the failure reliably, make sure the old master can't come back and keep accepting writes (two masters at once is called split brain, and blocking the old one is called fencing), and repoint every client. Managed services such as Amazon RDS Multi-AZ and tools such as Orchestrator (MySQL) and Patroni (PostgreSQL) automate this.
    • Async vs sync. With asynchronous replication (the common default) the master confirms a write before any replica has it, so a promoted replica can be missing writes the user was told had succeeded. Synchronous or semi-synchronous replication waits for a replica too. That narrows the gap, but every write gets slower.
    • Read-your-writes. Lag also means a user may not see their own change. Common fixes: send that user's reads to the master for a short while after they write, or read from a replica that has caught up to their write.[5]
    • Replication scales reads, not writes. Every write still lands on one master, and every replica replays it. When writes outgrow one machine, you need sharding. That's Quest 1.5.
