Quest 10.3 · Design a Notification System

Never Lose a Ping

A notification can arrive late. It can even arrive out of order. What it must never do is vanish. Crash workers, lose network replies, race two workers on the same event, and sort failures until you can promise exactly that.

🎯

Your win today: you can explain why notifications may be delayed or reordered but never lost, why exactly-once delivery is impossible, how dedupe by event ID and retries work (and where they still leak), and which metric tells you to add workers.

1

Delayed, reordered — never lost

The notification log

In Quest 10.2 you split the system into notification servers, one message queue per channel, and workers that pull messages off a queue and hand them to a provider like Apple's APNs (Apple Push Notification service). Now the hard part: what happens when a worker dies halfway through?

The book sets one firm rule. A notification may be delayed or arrive out of order, but it must never be lost. To keep that promise, the system saves notification data in a database, the notification log, and adds a retry mechanism.[1] The reason is simple. If the only copy of a notification sits in one worker's memory, a crash deletes it for good.

There's a second lever. When a worker takes a message, it must at some point acknowledge ("ack") it, which tells the queue "done, delete it". It can ack before it sends, or only after the send has worked. Set the two toggles, predict, and crash the worker.

The order of the steps matters. The log only saves you if the write reaches disk before the queue is acked, and if some job re-scans entries still marked pending. The book's design has the log. Most real systems also do the simpler thing: ack only after the provider accepts, so the queue itself hands the message out again after a crash. Delivering until you're sure it got through, even if that sometimes means twice, is called at-least-once delivery. Stage 2 shows its catch.

The exactly-once myth

Why duplicates happen

Will a user get each notification exactly once? The book's answer is no. Usually it arrives once. But because the work is spread over several machines and a network, a duplicate can slip through.[1]

The Two Generals problem. Look at runs B and C from the worker's side. "APNs never got it" and "APNs delivered it, but I never heard back" look exactly the same: silence. No number of extra messages can fix that over a network that can drop any message. This is a classic result called the Two Generals problem.[3] So you must choose. Retry when unsure and risk a duplicate (at-least-once). Or never retry and risk a loss (at-most-once). For notifications, the book's rule picks "never lost", so you take at-least-once and work to make duplicates rare. Tyler Treat's essay, which the book cites, puts it bluntly: you cannot have exactly-once delivery.[2]

The dedupe gate

Seen this event ID before?

The book's way to cut duplicates is dedupe (short for de-duplication). Every notification event carries an event ID. When an event arrives, the worker checks whether it has seen that ID before. If it has, it throws the event away. If not, it sends it.[1]

Dedupe makes duplicates rare, not impossible. Three leaks, none of them spelled out in the book:
  1. Check-then-add races, as you just saw. Use one atomic step. In Redis that's SET notif:e5 sending NX EX 60: NX means "only if it doesn't exist yet" and EX sets an expiry in seconds.[7]
  2. A crash between send and "mark sent". The 60-second claim expires, so a retry can still go out (good, nothing is lost). But the phone already had it, so that retry is a duplicate. The gap from stage 2 never fully closes.
  3. The seen-set grows forever unless entries expire. Keep IDs only as long as retries can still arrive, say a day.
One more: the ID must be minted by the caller, once per real-world event. Otherwise a retry arrives with a fresh ID, sails through the gate, and the dedupe check is useless.
4

Retry, then raise the alarm

What to retry and what to drop

The book's retry rule: when a third-party service fails to send, the notification goes back on the message queue to try again. If the problem keeps happening, an alert goes out to developers. In the final design, workers retry a set number of times.[1]

Real systems add one more question: is this failure worth retrying? A transient failure (a timeout, a 5xx server error, a 429 Too Many Requests) might succeed a moment later. A permanent one (a dead device token, a phone number that doesn't exist) will fail the same way forever, so the fix is to clean up the bad data. And once a message runs out of retries, it goes to a dead-letter queue (DLQ): a side queue where failed messages wait for a human, instead of looping forever.[6]

The retry storm

"Retry" hides a trap. A provider has an outage, and 1,000 sends fail at the same moment. It comes back up, but it can only take 60 calls per quarter-second. With exponential backoff, each retry waits twice as long as the one before (1 s, 2 s, 4 s…). With jitter, each message picks a random wait between zero and that number.[5] Run the storm both ways. Why jitter wins. Without it, every failed message waits exactly the same time, so they all come back at once. The provider gets hit by a wall of 1,000 calls, rejects most of them, and the survivors all come back together again. Backoff alone just spaces the walls out. Jitter turns each wall into a gentle slope, so the provider can clear the backlog. AWS uses this pattern across its services and SDKs.[4]

Watch the queue

The one graph that says "add workers"

The book names one key metric to watch: the total number of notifications waiting in the queue (the queue depth). If it's large, the workers aren't keeping up, so you add more workers to stop the delay growing.[1] The rule underneath is plain arithmetic. If messages arrive faster than workers can send them, the queue grows, and it keeps growing for as long as that lasts.

You run the email queue for one day. Each worker sends 20 emails per second. Your target: the oldest waiting email should be under 60 seconds old at the end of each phase. Set the workers, then run the phase.

Two refinements the book doesn't spell out. First, the age of the oldest message (often called consumer lag) tells you how late users' notifications actually are. A raw count can't: 10,000 waiting emails is fine if you send 5,000 a second, and terrible if you send 20. Second, a growing queue doesn't always mean "too few workers". If the provider is slow or throttling you, more workers just make more failed calls. Check the error rate before you scale. RabbitMQ monitoring guides track exactly these: messages ready, messages unacknowledged, and consumer throughput.[8]

🎓 Level-up note (for later)

"Exactly-once" in product docs is narrower than it sounds. Amazon SQS FIFO queues drop a repeated message ID only inside a 5-minute window. Kafka's exactly-once covers reading and writing Kafka topics, not a call out to APNs. Neither can stop a duplicate push once a request has left your system. That's the stage 2 gap again. "Never lost" also stops at the provider. Once APNs or FCM accepts a push, delivery to the phone is out of your hands: if the device is offline for a long time, the provider may keep only the latest notification or let it expire. And a permanent error like APNs's 410 (the device token is no longer active) means "stop sending to this token", not "try again".[9]
