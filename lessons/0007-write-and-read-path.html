1

Every node, same job

The whole architecture in one picture

First, a 60-second recap of quests 6.2–6.6 as one diagram.[1] Clients talk to the store with just two calls: get(key) and put(key, value). Whichever node the client reaches becomes the coordinator — the node that acts as a middleman (a proxy) between the client and the store: it forwards the request to the replicas and sends the answer back.

Nodes sit on a ring (consistent hashing), each key is copied to several nodes, and there is no boss node — the system is fully decentralized, so adding or moving nodes can happen automatically. Tap any node to make it the coordinator for put(cat, 🐱).

Any node can coordinate because every node carries the same set of jobs — the Dynamo paper calls this symmetry.[2] No special node means no single point of failure (one machine whose death takes everything down). Install each job into the node 👇

2

The write path

Commit log → memtable → SSTable

Now zoom into the storage engine of one node. The book's write path is based on Apache Cassandra's.[1][3] When a put lands on a node:

  1. Commit log — the write is added to the end of a log file on disk. It's append-only: nothing is ever edited, new lines only go at the end.
  2. Memtable — the write goes into a table in memory (the "memory cache"), kept sorted by key. Now the client gets its OK.
  3. Flush — when the memtable is full (hits a size threshold), it's written to disk in one go as an SSTable — a sorted-string table: a file of <key, value> pairs sorted by key. Then a fresh, empty memtable takes over.

Why the log first? Memory is fast but forgets everything when the power dies. The log is the safety net: after a crash, the node re-reads it and rebuilds the memtable. Why is it fast? Every disk write is an append — written at the end of a file, one after another (sequential) — never a hunt for an old record to change. Fire some writes 👇

Crash test

Predict, then pull the plug

Four rounds on a fresh node. Each time, predict what happens, then watch the machine do it. Right calls earn XP; wrong ones cost a heart.

Honest caveat — "in the log" isn't always "on the disk" yet. Operating systems buffer file writes in memory. Cassandra's default (commitlog_sync: periodic) acknowledges the write right away and forces the log to disk every 10 seconds.[5] So one node crashing can lose the last few seconds — the copies on other replicas (quest 6.3) cover that. The stricter batch/group modes wait for the disk before saying OK: safer, slower.
4

The Bloom filter

A tiny "definitely not / maybe" oracle

Reads have a problem. After a few flushes, a key could be in any of many SSTables — and every file you open is a slow disk read. You want to skip the files that definitely don't have the key.

A Bloom filter does exactly that.[4] It's a short row of bits (all 0 at the start) plus a few hash functions — functions that turn a key into a number, here a bit position 0–15.

  • Insert a key: compute its positions, set those bits to 1.
  • Check a key: if any of its positions is 0 → definitely not in the set. If all are 1 → maybe (other keys could have set those bits).

Each SSTable gets its own filter, built when the file is written.[6] This one uses 16 bits and 2 hash functions. Insert three keys:

The read path

Chase a get() through the node

Put it together. The book's read path:[1]

  1. Check the memtable. Key there? Return it — done.
  2. Not there? Ask each SSTable's Bloom filter, newest file first.
  3. Open only the files that say maybe, and look for the key.
  4. Return the result to the client.

This node has a memtable and three SSTables, each with its own Bloom filter (the little bit strip). Watch the disk reads counter — that's what we're trying to keep low.

Honest caveat — real Cassandra merges. The book's read path stops at the first file that has the key, newest first (the simple model in DDIA, too[7]). Real Cassandra can store one row's columns across several files, so it merges the pieces from the memtable and every "maybe" SSTable, keeping the newest timestamp for each.[6] Same idea, more bookkeeping — and the reason background compaction keeps the file count low.

🎓 Level-up note — updates, deletes and compaction

Because SSTables are immutable (never edited after they're written)[3], an update just writes a newer copy of the key into a newer file, and a delete writes a tombstone — a time-stamped "this key is deleted" marker.[8] Old copies pile up, so a background job called compaction merges SSTables, keeps only the newest version of each key and eventually drops tombstones (after a grace period, default 10 days, so every replica hears about the delete). That's the LSM-tree family: cheap writes, paid for with background merging.[7]
